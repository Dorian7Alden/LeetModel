## Prompt 约束与措辞校验

> 设计状态：已完成实现并经验收。


### 一、Prompt 版本

V4 新增：

- `phase2-suggestion-planner-v4.st`
- `phase2-subtask-suggestion-v4.st`
- `phase3-suggestion-synthesizer-v4.st`

V3 Prompt 保持不变。


### 二、角色调整

V4 不再使用“开出手术刀级药方”“提升至一等奖水准”等结果导向角色。
角色定义为：

> 数学建模论文诊断与完善顾问。基于题面、论文事实、评审依据和知识来源，
> 帮助作者识别确定性缺漏与可进一步讨论的方向，同时尊重建模方法的多样性。


### 三、生成顺序

1. 判断问题是否确定。
2. 选择 `guidanceType`。
3. 描述当前论文事实。
4. 说明为什么值得处理。
5. 只提出与类型匹配的补充方向。
6. 说明适用性和取舍。
7. 给出不绑定唯一模型的验收标准。
8. 返回证据标识。


### 四、允许与禁止措辞

#### 允许

- “补充变量的单位与定义说明。”
- “进一步说明该假设在什么条件下可能失效。”
- “若希望检验现有结论的稳定性，可考虑增加一个基准对照。”
- “可以从参数扰动区间、响应指标或结论翻转边界三个方面补充。”

#### 禁止

- “必须改用 XGBoost。”
- “一定要采用遗传算法。”
- “唯一正确的做法是……”
- “把现有模型替换成……即可解决。”
- “参数必须设置为 0.01。”
- “按照本建议修改即可达到一等奖水平。”


### 五、确定性措辞校验

`OPTIONAL_EXPLORATION` 和 `COMPLETENESS_ENHANCEMENT` 的 Markdown 字段不得包含：

- `必须改用`
- `一定要采用`
- `唯一正确`
- `直接替换为`
- `照此修改即可`
- `保证获奖`
- `必然提升`

命中禁用表达的候选项先尝试一次带错误说明的结构化重试；仍不合格时丢弃单项。

`REQUIRED_FIX` 可以使用“需要修正”“应补充”，但必须有确定性评审问题与真实论文证据。


### 六、公式、算法和参数

- 只有确定性数学错误才允许给出明确修正后的公式。
- 主观完善不得直接提供替换模型公式，只能说明应补充的变量关系、约束类别或验证维度。
- 参数阈值必须来自题目、论文或锁定知识来源，并注明是示例、经验范围还是硬性规则。
- 代码只用于解释确定性实现缺失，不生成整套可替换算法。


### 七、输出校验

- `guidanceType` 与措辞相容。
- `REQUIRED_FIX` 必须引用至少一个 `ISSUE` Finding。
- `OPTIONAL_EXPLORATION` 可以不引用评审问题，但必须有论文证据和知识依据。
- Markdown 字段不得为空或只有标题。
- 每条建议必须独立可理解。
- 不输出思考链，只输出结论、理由、边界和依据。
