## 检索缓存与前置路由

### 成本痛点与降本思路

知识检索的核心运行开销主要集中在：
1. **Embedding API 费用**：每次用户提问均需发起单次向量化请求；
2. **下游 LLM Prompt Token 消耗**：召回冗余知识切片直接导致下游业务大模型输入费用激增；
3. **ES 算力开销**：全库 kNN 向量扫描消耗 CPU 与内存。

通过**两级缓存**与**元数据前置过滤（Pre-filtering）**构建高性价比防线。

### 两级缓存架构（Redis）

```mermaid
flowchart LR
    Q[用户 Query] --> Hash[SHA-256 哈希计算]
    Hash --> L1{L1: 结果缓存 Result Cache}
    L1 -- 命中 --> Ret[直接返回 KnowledgeCitation 列表<br/>耗时 <5ms / 0 Token]
    
    L1 -- 未命中 --> L2{L2: 向量缓存 Embedding Cache}
    L2 -- 命中 --> ReuseVec[复用 1024 维向量<br/>节省 Embedding API 费用]
    L2 -- 未命中 --> ApiCall[调用 AI 网关生成 Embedding]
    
    ApiCall --> SetL2[写入 L2 缓存 (TTL: 7天)]
    ReuseVec --> ES[Elasticsearch 混合检索]
    SetL2 --> ES
    ES --> SetL1[写入 L1 缓存 (TTL: 2小时)]
    SetL1 --> Ret
```

1. **L1 结果缓存（Result Cache）**：
   - Key 格式：`lm:kr:result:<workflow>:<md5(query + category + topK)>`；
   - 缓存高频提问的最终 `List<KnowledgeCitationDTO>` 快照，TTL 设为 2 小时；
   - 当底层发生全量索引切换时，通过 Redis Key 模式匹配批量失效。
2. **L2 向量缓存（Embedding Cache）**：
   - Key 格式：`lm:kr:vec:<model_version>:<sha256(query)>`；
   - 缓存标准化 query 的 `List<Float>` 稠密向量，TTL 设为 7 天；
   - 杜绝相同或相似语义问题的重复模型调用支出。

### 分类元数据前置过滤（Category Pre-filtering）

利用知识库现有的树状清晰目录，在请求中传递 `category`（如 `题型方法/优化模型`）：
```json
{
  "bool": {
    "filter": [
      { "term": { "category": "题型方法/优化模型" } }
    ],
    "must": [
      { "knn": { ... } }
    ]
  }
}
```
前置过滤直接将 ES 检索空间减枝 80% 以上，从物理层面隔绝跨领域语义误召回。
