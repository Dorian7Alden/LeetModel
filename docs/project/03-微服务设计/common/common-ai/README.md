# common-ai

> `common-ai` 是业务服务调用 AI 网关的公共客户端模块。

`common-ai` 是随 ai-review-service 等业务服务一起运行的 Java Jar，不是独立进程，没有自己的端口和数据库。它相当于项目内部使用 AI 网关的统一 SDK。

## 职责边界

- 负责 AI 调用请求、响应、流式事件、错误和追踪信息契约。
- 负责 AI 网关客户端、统一异常转换和测试替身。
- 不直连模型供应商，不持有模型密钥。
- 不定义业务 Prompt、工作流、RAG 和质量评价规则。

## 与 ai-gateway-service 的区别

| 对比项 | common-ai | ai-gateway-service |
|--------|-----------|--------------------|
| 形态 | 被其他 Maven 模块依赖的公共 Jar | 独立启动和部署的微服务 |
| 运行位置 | 运行在调用方业务服务进程内 | 运行在自己的服务进程内 |
| 主要入口 | Java 接口 `AiClient` | 内部 HTTP 接口 `/internal/ai/**` |
| 主要职责 | 统一请求响应对象、HTTP 客户端、错误转换和测试替身 | 路由、能力校验、供应商适配、密钥、稳定性、用量与成本治理 |
| 是否调用供应商 | 否 | 是 |
| 是否持有密钥 | 否 | 是，通过安全配置读取 |
| 是否拥有数据库 | 否 | 目标设计中独占 `lm_ai` |

典型调用路径如下：

```text
ai-review-service 业务代码
  -> common-ai 的 AiClient
  -> ai-gateway-service 的内部 HTTP 接口
  -> DeepSeek、Kimi 等模型供应商
```

如果没有 common-ai，每个业务服务都要重复维护 AI 网关 DTO、HTTP 调用和错误转换。如果没有 ai-gateway-service，供应商密钥、路由、协议适配和成本治理就会分散到各业务服务。两者分别解决客户端复用和运行时集中治理问题，不能互相替代。
