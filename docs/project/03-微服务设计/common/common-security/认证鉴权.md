## 认证鉴权模块

> 创建日期：2026-07-26

---

### 一、目标

构建认证鉴权公共模块 `common-security`，提供 JWT 无状态认证和 RBAC 注解鉴权能力。

---

### 二、认证 vs 鉴权

| 阶段 | 英文 | 问题 | 实现方式 |
|------|------|------|---------|
| 认证 | Authentication | "你是谁" | JWT 签发 + 验签 + Redis 黑名单 |
| 鉴权 | Authorization | "你能做什么" | @SaCheckRole / @SaCheckPermission 注解 |

流程：登录 → JWT 签发 → 请求携带 Token → 验签确认身份 → 查 RBAC 数据 → 校验角色/权限

---

### 三、模块结构

`common-security` 实现认证鉴权核心逻辑，包含 Sa-Token JWT 无状态模式配置、Spring Security 基础配置、RBAC 角色枚举、用户上下文工具、权限数据适配器、认证鉴权异常处理器和 Token 工具类。

职责边界如下：

- Gateway 使用 Sa-Token 完成外部请求的登录态校验。
- 业务服务使用 Sa-Token 注解完成接口级角色和权限校验。
- Spring Security 只提供密码编码等基础能力，关闭默认登录入口并放行业务请求，不建立第二套登录态。
- user-service 拥有 RBAC 数据，common-security 只消费角色权限查询结果。

---

### 四、关键设计决策

#### 4.1 JWT 无状态 + Redis 黑名单

- 登录时不存 Redis Session，JWT 签名自验证（轻量、高性能）
- Redis 仅存黑名单——登出/踢人时加入，解决 JWT 无法主动失效的问题
- `StpLogicJwtForStateless(secretKey)` 构造器注入密钥

**实现口径（2026-09-19 补齐）**：

- Sa-Token 1.38 的 JWT 无状态模式不提供内置黑名单：`StpLogicJwtForStateless.logout()` 只清理本地 cookie 与 storage，`kickout` 在没有服务端会话时不产生跨实例效果。因此黑名单由 `common-security` 自建，不能通过追加 `sa-token-redis-*` 依赖解决。
- 键结构：`auth.token-blacklist.key-prefix` + Token 的 SHA-256 指纹（`TokenFingerprint`）。Redis 与日志只出现指纹，不保存 Token 原文。
- 有效期：写入时 TTL 取该 Token 的剩余有效期，并由 `auth.token-blacklist.max-ttl-seconds` 封顶，避免黑名单无界增长。
- 存储位置：安全状态 Redis `6379`，与业务缓存 Redis `6380` 物理隔离，淘汰策略固定 `noeviction`。
- 校验点有两处：网关 `TokenBlacklistGlobalFilter`（响应式，非阻塞查询）与业务服务 `SaInterceptor` 的认证函数。只做网关会被“绕过网关直连服务端口”绕开。
- 降级：Redis 不可用时由 `auth.token-blacklist.fail-closed` 决定拒绝还是放行，默认 `false`（fail-open，可用性优先），两种情况都会累加降级计数并记录 WARN。
- 超时：`auth.token-blacklist.redis-timeout-ms`（默认 300 毫秒）同时作用于 Lettuce 的命令超时、连接超时与网关的响应式超时。Redis 故障时 Lettuce 会先重连而不立即报错，若不显式限时，请求会挂到默认 60 秒命令超时，把 fail-open 变成事实上的全站阻塞。
- 观测：`auth_token_blacklist_revoked_total`、`auth_token_blacklist_hit_total`、`auth_token_blacklist_degraded_total` 三个低基数计数器，不带用户与 Token 标签。
- 范围边界：只实现 Token 粒度的登出失效；按用户批量下线（踢人）不在当前范围内，因为无状态 JWT 无法枚举某用户已签发的 Token，必须另外引入吊销水位或版本号口径。

#### 4.2 权限数据降级策略

- 用户服务不可用时，权限数据按空角色和空权限处理
- 认证鉴权异常处理器将权限不足转换为 403，保证安全不倒置

#### 4.3 异常处理分层

- common-core 处理业务异常（`BusinessException` → Result）
- common-security 处理认证鉴权异常（`NotLoginException` → 401, `NotRoleException` → 403）
- 两者互补，不相互覆盖

#### 4.4 Sa-Token 1.38.0 适配

- 类名 `SaTokenForJwt` 已移除，改用 `StpLogicJwtForStateless(String secretKey)`
- 行为配置通过 `cn.dev33.satoken.config.SaTokenConfig` 对象注入
- 避免与库内置类冲突，配置类命名为 `SecuritySaTokenConfig`

#### 4.5 Redis 缓存基础设施

- `RedisCacheConfig` 配置 `RedisCacheManager`，使 `@Cacheable` / `@CacheEvict` 等 Spring Cache 注解可用
- Key 使用 String 序列化（可读性好），Value 使用 Jackson JSON 序列化
- 序列化时写入类型信息（`activateDefaultTyping`），解决泛型反序列化问题（`List<User>` → `List<LinkedHashMap>`）
- 默认 TTL 30 分钟，TTL 加随机 10% 偏移防缓存雪崩

#### 4.6 统一响应边界

- Sa-Token 认证和鉴权异常由安全异常处理器转换为统一 `Result`。
- Spring Security 不再用自身的 `Authentication` 拦截业务请求，避免产生空响应体的 403。
- `Result.isSuccess` 是服务端便捷判断方法，不参与 JSON 序列化，响应结构固定为 `code`、`message`、`data`、`timestamp`。
