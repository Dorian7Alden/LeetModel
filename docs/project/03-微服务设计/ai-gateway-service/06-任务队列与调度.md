## 任务队列与调度

> 实施状态：S5 已完成。无队列基线、优先级、公平算法、容量、持久化、限流退避、同步 Chat/Embedding 入队、租约恢复和只读运维入口均已落地。

### 设计目标

在不同耗时、优先级和实时性要求的原子调用之间进行可控调度，使供应商容量有限时仍能保证系统稳定和任务可解释。

### 已确认边界

- 不同 AI 业务的大任务特征不同，不能全部按同一种优先级和等待策略处理。
- 队列调度面向原子 AI 调用，不接管业务服务内部的完整工作流编排。
- 调度不能为了尽快完成任务而更换已锁定的精确模型。

### 固定优先级

| 优先级 | 业务调用 | 可信映射 |
|--------|----------|----------|
| P0 | 客服 Chat、客服 RAG Query Embedding | `ai-assistant-service + CHAT_REPLY/RETRIEVE_CONTEXT` |
| P1 | 正式论文评审、正式改善建议 | `ai-review-service + FORMAL_REVIEW`、`ai-suggestion-service + GENERATE_SUGGESTION` |
| P2 | 管理员单次模型测试 | `admin-service + ADMIN_MODEL_TEST` |
| P3 | 批量质量评价、隔离评审实验、未知来源安全默认 | `ai-review-service + EXPERIMENT_REVIEW` 或未命中规则 |
| P4 | RAG 批量索引 Embedding | `ai-assistant-service + INDEX_DOCUMENTS` |

调用方声明的 `priority` 不具有授权作用。网关按可信服务身份与稳定 `operationCode` 重算有效优先级；声明不匹配时覆盖并记录 `DECLARATION_OVERRIDDEN`，未知组合固定降为 P3 并记录 `UNKNOWN_SOURCE`。RAG 查询是客服回答的实时前置步骤，因此属于 P0；知识库索引属于 P4，二者不能只因同属 RAG 而共享优先级。

### 公平与防饥饿算法

单实例调度器使用固定 31 槽加权轮转，完整周期的槽位数为 `P0=16、P1=8、P2=4、P3=2、P4=1`。每次领取从持久化游标位置向后查找第一个有候选任务的槽，空优先级可跳过；同一有效优先级内按 `queuedAt、taskId` 排序。该算法让持续 P0 积压获得超过一半的派发机会，同时 P3/P4 每周期仍至少获得 2/1 个机会。

等待老化每 30 秒把任务提升一个有效级别，最高到 P1；P0 只来自可信实时操作，后台任务永远不能靠等待进入 P0 保留级别。示例：P4 在 30/60/90 秒后依次按 P3/P2/P1 参与选择；新到达的 P1 排在已老化且更早入队的任务之后，因此有限积压最终会执行。deadline 已过的任务不参与选择，直接进入 `EXPIRED`。

确定性测试固定验证 31 槽权重、P4 老化上限、同级 FIFO 和过期过滤。容量许可和 P0 保留并发在下一节单独约束，不能用改变权重的方式临时扩容。

### 容量、背压与同步等待

S5-01 只证明本机双并发下四类调用可用，没有证据表明 Chat 与 Embedding 拥有独立上游容量。因此首版使用一个全局执行池，不按模型或协议拆池：

| 参数 | 首版值 | 约束 |
|------|--------|------|
| 单实例上游并发 | 4 | 所有 Chat 与 Embedding attempt 合计 |
| 非 P0 并发上限 | 3 | 永久为 P0 保留 1 个许可；不抢占已运行请求 |
| 总排队上限 | 500 | 超限立即拒绝，不创建不可执行任务 |
| 非 P0 排队上限 | 450 | 为 P0 保留 50 个队列名额 |
| P0/P1/P2/P3/P4 最大排队时间 | 10s / 60s / 30s / 5m / 10m | 还要受调用方 deadline 的更短值约束 |
| 同步结果等待上限 | 120s | 同时受调用方 deadline 约束；不是上游重试期限 |

任务在准入时同时检查全局上限、P0 保留名额和 deadline。拒绝使用稳定错误 `AI_QUEUE_FULL`；派发前超过排队上限或 deadline 使用 `AI_QUEUE_EXPIRED`。同步连接使用异步 Servlet/`CompletableFuture` 等待结果，释放容器请求线程；超过等待上限时返回 `AI_RESULT_PENDING` 与原 `callId/taskId`，不取消已经 `RUNNING` 的 attempt。

调用方断连只停止结果等待，不改变 `RUNNING` 任务。调用方重试必须携带原幂等键：网关返回同一任务的终态结果或继续等待，绝不创建第二个上游调用。若任务仍在 `QUEUED/LEASED`，显式取消可以阻止派发；若已经 `RUNNING`，只有 new-api 提供可核验取消结果时才能视为停止计费。

参数先作为单实例安全基线，不外推为生产容量。只有采集到 Chat/Embedding 独立限流或资源隔离证据后才评估分池；多实例全局容量在引入分布式许可前不得简单乘以实例数。

### 同步调用接入

`POST /internal/ai/chat` 与 `POST /internal/ai/embeddings` 保持原有路径和 `Result` 响应包装，但控制器返回异步结果，不占用 Servlet 请求线程等待上游。入口先序列化受控请求并按 `callerService + idempotencyKey` 准入；已有任务直接复用，只有首次请求创建 `taskId` 与 `callId`。派发器反序列化任务载荷后只调用一次原 Chat/Embedding 执行服务，并把任务的 `callId` 贯穿响应与 `ai_call_log`。

有效优先级只由可信上下文重算：客服回答与 RAG Query 为 P0，正式评审/建议为 P1，索引 Embedding 为 P4。全局四个执行许可中非 P0 最多占三个，因此大批索引不能占用客服保留许可。结果等待受调用 deadline 与 120 秒上限共同约束；等待超时只返回 `AI_RESULT_PENDING`，任务继续以数据库状态为准，相同幂等键不会产生第二次上游调用。调度可用 `AI_SCHEDULING_ENABLED=false` 紧急关闭，但默认开启。

### new-api 限流反馈

new-api 最终返回 429 时，适配器解析标准 `Retry-After` 秒数或 HTTP 日期并转为不含响应正文的限流信号。当前调用明确以 `UPSTREAM_RATE_LIMITED` 失败，LeetModel 不在内部重试它；调度器只推迟后续任务的派发。

有 `Retry-After` 时采用其值但单次最多 30 秒；缺失时按连续 429 次数使用 1、2、4、8、16、30 秒有界指数退避。退避期间不领取新任务，已运行任务不被取消。恢复后每次成功只降低一级限流计数，并以 250ms 起的短间隔逐级放量；计数归零后恢复正常 31 槽调度。这样不会复制 new-api 渠道重试，也不会在恢复瞬间一次性冲出全部积压。

### 租约恢复与未知结果保护

恢复器每 5 秒扫描最多 100 个 `LEASED/RUNNING` 过期租约。没有 attempt 的 `LEASED` 任务可条件重排；最新 attempt 仍为 `PREPARED` 时，先在同一事务内把 attempt 标为确定失败，再按任务版本重排。两种情况都以数据库事实证明 HTTP 尚未发送。

派发前必须成功完成 `PREPARED → DISPATCHING`，否则不得调用上游；上游返回后先记录 `ACKNOWLEDGED`，再保存任务结果。`DISPATCHING/ACKNOWLEDGED` 后租约过期或结果持久化发生冲突时，attempt 进入 `UNKNOWN`，任务进入 `FAILED`，稳定错误为 `AI_UPSTREAM_RESULT_UNKNOWN`，并写入不可自动消费的 dead-letter 原因。恢复器永远不把这类任务放回队列，因此进程重启、数据库短故障或连接断开不能产生不可解释的第二次扣费。

取消排队任务会直接进入 `CANCELLED`；运行期取消只设置标记，等待当前上游 attempt 返回并保存事实。公平周期在持续 P0 候选存在时仍会选择 P3/P4，P0 同时拥有一个不可被后台占用的运行许可；这两层约束分别防止后台饥饿和客服被积压阻断。

### 运维边界

- 多实例共享全局执行许可仍需独立设计；当前数据库条件领取只解决任务不被多个实例同时领取，不把单实例并发上限误当成全局上限。
- 队列查询与取消统一经 admin-service 代理，管理员不得直接修改 `ai_call_task` 或 `ai_call_attempt`。

### 与主流程的关系

原子任务进入队列后，调度器根据固定逻辑模型、任务等级、deadline 和 LeetModel 可用派发容量选择执行时机，再交给 new-api；具体渠道由 new-api 决定。
