## 安全激活、在途快照与回滚

### 任务卡

目标：管理员切换或回滚 AI 客服生产工作流时，要么完整生效，要么完全不改变生产指针；已经开始的客服回复不得混用两个配置。

入口：管理员先创建服务端变更预览，再对同一变更请求执行确认；正式客服发送消息和失败重试从生产配置快照执行。

主流程：预检查并冻结变更请求，管理员核对差异和影响后确认，业务服务在一个事务内重检并条件更新当前指针、写审计和变更结果，新任务读取新指针，旧任务继续使用已保存快照。

完成标准：预检查、原子激活、缓存策略、旧版本保留、观察期、回滚、并发冲突和失败边界均可直接映射到实现；没有半生效状态。

修改范围：AI 客服生产配置的安全状态机和任务快照设计。

非目标：本任务不实现数据库、接口、页面、自动回滚、自动按评价结果激活或多服务配置中心。

### 状态与参与对象

生产治理包含四类对象：

| 对象 | 可变性 | 用途 |
|------|--------|------|
| 工作流发布项 | 定义发布后不可变，状态可停用 | 说明可选择的业务流程、Prompt、模型配置和 RAG 模式 |
| 生产配置 | 全部字段不可变 | 把发布项绑定到精确 `productionConfigVersion` 和可空 `ragIndexVersion` |
| 当前指针 | 可变，带单调 `revision` | 唯一表示新任务应读取的生产配置 |
| 变更请求与审计 | 只追加结果，不覆盖历史 | 保存第二次确认的上下文和实际生效事实 |

变更请求状态为 `PENDING`、`APPLIED`、`CONFLICT`、`REJECTED` 或 `EXPIRED`，终态不可再次应用。动作只有 `ACTIVATE` 与 `ROLLBACK`。激活绑定一个已发布工作流及所需索引；回滚绑定一个历史 `productionConfigVersion`，不是把字段手工抄回去。

### 第一步：预览与预检查

管理员提交动作、目标、当前 `expectedRevision` 和 10 至 500 字的真实原因。业务服务按当前操作者生成不可猜测的 `changeRequestId`，有效期 10 分钟，并返回来源/目标差异、影响范围和观察提示。

预检查必须全部通过：

1. 当前指针和 `expectedRevision` 一致，目标不是当前配置。
2. 目标工作流存在且状态为 `ENABLED`，其 Prompt 与模型配置引用完整。
3. `NONE` 模式禁止携带 RAG 索引；`FIXED_INDEX` 模式必须提供合法物理 `ragIndexVersion`，并确认索引存在、可读、Embedding 维度和版本元数据一致。
4. 目标 `modelExecutionConfigVersion` 在 AI 网关目录中仍可执行；检查只验证 LeetModel 配置，不读取或改变 new-api 渠道。
5. 回滚目标曾经实际生效、仍由相同功能拥有，且其依赖当前仍可用。
6. 原因、操作者、动作和目标与服务端变更请求完整绑定，admin 不能在确认阶段替换字段。

预览不移动生产指针。相同不可变字段可以复用已有生产配置；新组合在业务库创建不可变配置后才成为预览目标，但尚不代表已生产生效。

### 第二步：确认与原子激活

确认只提交 `changeRequestId`，操作者仍由 admin 登录上下文注入。业务服务在一个本地数据库事务内执行：

1. 对变更请求加行锁，校验 `PENDING`、操作者和过期时间。
2. 重新执行目标可用性检查，防止预览后依赖失效。
3. 使用 `UPDATE ... WHERE revision = expectedRevision` 条件移动唯一当前指针，并把 revision 加一。
4. 条件更新成功时，同事务写 `APPLIED`、来源/目标、前后 revision、操作者、原因和审计记录。
5. 条件更新为零时，同事务把请求记为 `CONFLICT`，不写成功审计，不改变当前配置。

依赖重检失败记为 `REJECTED`；已过期记为 `EXPIRED`。指针、请求结果和成功审计使用同一个 `lm_ai_assistant` 事务，不调用跨服务分布式事务。AI 网关检查发生在事务前后各一次的预检查层，不在持有数据库锁时发起慢网络调用；进入事务后再次核对本地冻结结果和 revision。若外部可用性在提交后瞬间变化，当前配置仍完整生效，运行按普通依赖失败处理并允许人工回滚，不存在字段只更新一半。

### 缓存策略

首版每个新客服回复直接读取本服务数据库中的当前指针与不可变配置，不建立进程缓存。因此激活提交后，任意实例下一次任务读取都能看到数据库已提交 revision，不需要广播失效，也没有缓存半生效窗口。

若以后实测数据库读取成为瓶颈，缓存键必须包含 revision，并通过提交后事件主动失效、短周期轮询兜底；缓存只可优化读取，不能成为权威状态。该优化不属于 S10。

### 在途任务快照

“任务开始”定义为客服回复取得生产配置并准备创建唯一 `PROCESSING` 回复记录的时刻。快照包含：

- `productionConfigVersion` 与读取时的生产 revision。
- `workflowVersion`、`promptVersion`、`modelExecutionConfigVersion`。
- 可空的 `ragIndexVersion` 和 RAG 模式。

受控工具调用实施后，工具版回复快照还要包含已确认的 `toolsetVersion`。同一次回复的规划调用、题目工具、知识讲解工具和最终回答必须使用同一个工具集快照；管理员切换生产配置不能改变在途回复可见的工具。

这些字段与回复占位记录一起保存，然后工作流只接受该快照，不再读取当前指针。即使管理员在 RAG 检索和 Chat 调用之间切换，当前回复仍使用同一个工作流、Prompt、模型配置和物理索引。AI 调用上下文保存相同字段用于 callId 审计。

同一用户请求的并发发送复用唯一回复记录及其快照。失败回复重试沿用原快照；若其版本已经停用或依赖不可用，重试显式失败，不静默替换为当前版本。迁移前无法还原的旧消息只使用迁移时明确补记的 bootstrap 无 RAG 快照。

### 观察与回滚

成功激活返回新 revision、`observationUntil` 和检查清单，默认观察 10 分钟。管理页在观察期展示该次生产变更，并联查 AI 调用状态、失败、耗时和 callId；首版不根据少量流量自动判定健康，也不自动回滚。人工发现依赖或质量异常时，对最近一个仍可执行的历史配置创建 `ROLLBACK` 预览并走同样的二次确认和条件更新。

回滚只影响确认提交后的新回复。已经保存快照的在途或失败待重试回复仍保持原版本，避免一次业务任务跨版本。旧配置、审计和历史消息永久保留；版本停用只阻止新激活，不删除解释历史所需的数据。

### 关键异常结果

| 场景 | 结果 |
|------|------|
| 两个管理员基于同一 revision 同时确认 | 一个条件更新成功，另一个为 `CONFLICT` |
| 预览后工作流停用或固定索引消失 | 请求为 `REJECTED`，指针不变 |
| 变更请求过期、换操作者或重复确认 | `EXPIRED` 或拒绝，不能复用 |
| 激活事务写审计失败 | 整个事务回滚，指针保持旧值 |
| 激活后 AI 网关或 new-api 故障 | 新任务按完整新快照失败并可追踪，管理员走回滚；不临时混用旧版本 |
| 回滚目标依赖已不可用 | 预检查拒绝，继续保持当前完整配置 |

安全性依赖条件更新和不可变快照，而不是依赖页面及时刷新。页面显示的 revision 只是帮助管理员理解冲突，服务端始终重新校验。
