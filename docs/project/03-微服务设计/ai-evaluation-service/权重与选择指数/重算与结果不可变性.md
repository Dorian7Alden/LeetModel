## 重算与结果不可变性

S8-04 允许管理员为一个已完成评价任务选择另一份权重方案，基于完全相同的可信原始指标追加新结果版本。重算只改变决策偏好，不重新运行模型、不改写原始指标、不覆盖首版或任何历史结果。

### 重算门禁

任务必须同时满足：

- 状态为 `COMPLETED`，存在数据集标识与不可变 `datasetVersion`。
- 存在功能、工作流版本、模型执行配置版本以及可解析的工作流快照。
- 指标定义快照可解析，且其中 `metricSetVersion` 与任务一致。
- 存在原权重方案标识/版本，可解析的方案快照版本与任务一致。
- `rawMetricsJson` 可解析，且内部指标集版本与任务一致。

新方案必须是另一份仍为 `ACTIVE`、同 `featureCode`、同 `metricSetVersion` 的方案。原方案重复重算没有新决策信息，直接拒绝。历史旧任务、缺失快照、损坏 JSON、口径漂移或未完成任务统一返回 `41114`，不能通过临时默认值绕过。

### 追加与并发

重算入口为 `POST /internal/evaluations/tasks/{taskId}/score-results/recalculate`，请求包含新 `weightSchemeId` 和 `operatorId`。评价服务执行以下步骤：

1. 读取并验证任务全部比较口径快照。
2. 读取新活动方案并快照为结果自己的 `weightSchemeSnapshotJson`。
3. 将任务 `rawMetricsJson` 原文写入新结果，不重新聚合或序列化原始事实。
4. 按 S8-03 相同规则生成逐项原值、归一化值、权重和贡献。
5. 在事务内锁定任务行，读取最大 `SCORE_RESULT_Vn`，分配 `n + 1` 后只执行插入。

任务行锁使同一任务的并发重算获得单调且不重复的版本；`uk_task_score_version` 是数据库最终兜底。重算路径没有 UPDATE 或 DELETE 历史结果、结果明细、任务原始指标和旧 `overallScore`。每版结果保存 `calculatedBy`，首版自动计算保持为空。

### 验收基线

- 单元测试证明相同原始 JSON 原文进入新结果、新方案与操作者被记录，V1 后追加 V2，旧口径、原方案和指标集漂移均拒绝。
- 2026-08-30 评价模块 84 项、admin-service 8 项测试零失败，各自直接依赖同步通过。
- MySQL 8.0.33 V1→V8 临时库中，V1 与 V2 的方案、指数和操作者不同，但 `raw_metrics_snapshot_json` SHA-256 完全相同；最大版本查询从 1 得到下一版 2，历史 V1 保持不变，验收库随后删除。
