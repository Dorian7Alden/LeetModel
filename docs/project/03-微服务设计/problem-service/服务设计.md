## 题目服务

> 创建日期：2026-07-26
> 最后更新：2026-08-23

---

### 一、职责

problem 服务运行在 8083 端口，负责题目、标签和题目外部链接的管理，以及题目分页筛选和公开浏览。

当前不实现 Elasticsearch 全文搜索和 AI 题目推荐。这两项能力需要完成独立设计后再开发。

---

### 二、数据边界

problem 服务拥有独立数据库 `lm_problem`，业务数据不跨服务共享。

#### problem

题目主表继承 BaseEntity，使用雪花 ID、时间自动填充和逻辑删除。

| 字段 | 类型 | 说明 |
|------|------|------|
| title | VARCHAR(255) | 题目标题 |
| content_file_id | BIGINT | 题目描述文件 ID |
| contest_type | VARCHAR(20) | MCM_ICM 或 CUMCM |
| difficulty | TINYINT | 1 为简单，2 为中等，3 为困难 |
| average_score | DECIMAL(5,2) | 平均得分，默认 0.00 |
| status | TINYINT | 0 为草稿，1 为已发布，2 为已下线，3 为已归档 |
| creator_id | BIGINT | 创建者用户 ID |

#### tag

标签采用扁平化设计，只保存名称。标签属于 problem 服务，不建设跨服务通用标签系统。

#### problem_tag

题目与标签的多对多关联表，`problem_id` 与 `tag_id` 组成唯一约束。

#### problem_link

题目与外部链接是一对多关系。链接保存标题、地址、说明和排序权重，用于引用数据集、视频和文档。

### 三、接口

#### 管理接口

管理接口统一使用 `/api` 前缀，并在服务内通过 Sa-Token 校验 admin 角色。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/problems | 分页查询题目，支持状态、难度、赛事类型、标签和标题关键词筛选 |
| GET | /api/problems/{id} | 查询题目详情 |
| POST | /api/problems | 创建题目 |
| PUT | /api/problems/{id} | 更新题目 |
| DELETE | /api/problems/{id} | 逻辑删除题目 |
| GET | /api/tags | 查询全部标签 |
| POST | /api/tags | 创建标签 |
| PUT | /api/tags/{id} | 更新标签 |
| DELETE | /api/tags/{id} | 删除标签 |

删除题目时同步清理题目标签关系和外部链接，题目主记录执行逻辑删除。删除不存在的题目返回题目不存在。

删除标签前检查题目引用。仍被题目使用的标签拒绝删除，删除不存在的标签返回标签不存在。

#### 公开接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/public/problems | 分页浏览已发布题目 |
| GET | /api/public/problems/{id} | 浏览题目详情 |

公开列表和公开详情都只允许访问已发布题目。草稿、下线和归档题目在公开接口中统一表现为题目不存在。

#### 内部接口

| 方法 | 路径 | 调用方 | 说明 |
|------|------|--------|------|
| GET | /internal/problems/count | admin 服务 | 获取题目数量 |

跨服务契约由 common-api 中的 ProblemFeignClient 维护。

### 四、鉴权边界

网关负责统一登录校验、公开路径放行和路由转发。problem 服务依赖 common-security，在服务内继续执行角色校验并通过 UserContext 获取当前用户 ID。

采用网关与服务双层校验是当前代码的实际实现。网关保护外部入口，服务内校验避免绕过网关直接访问服务端口时失去角色约束。

---

### 五、查询方案

当前分页查询使用 MyBatis-Plus 访问 MySQL：

- 状态、难度和赛事类型使用等值条件
- 标签通过关联表子查询筛选
- 关键词通过题目标题 LIKE 查询
- 分页结果批量查询标签，避免逐条加载标签
- 详情单独加载标签与外部链接

当前关键词筛选只是基础标题匹配，不属于 Elasticsearch 全文搜索。

---

### 六、数据完整性

- 创建和更新题目时校验标签 ID 全部存在
- 重复标签 ID 在写入关联表前去重
- 创建和更新请求校验标题、赛事类型、难度、状态和文件 ID
- 外部链接校验标题、HTTP 地址、说明长度和排序权重
- 分页查询校验赛事类型、难度、状态、标签 ID 和关键词长度
- 题目关联数据的删除与题目逻辑删除处于同一事务

---

### 七、关键决策

#### 固定属性使用字段

难度和赛事类型是稳定、有限的属性，直接保存在题目表中。这样可以减少关联查询，并保持数据约束清晰。

#### 标签保持服务内聚

标签目前只有 problem 服务消费，因此不提前抽取公共标签模块，避免数据模型泄漏和跨服务编译耦合。

#### 外部链接使用一对多

外部链接只服务于所属题目，不需要跨题复用，因此不抽象独立链接资源和多对多关系。

#### 服务内保留鉴权

problem 服务需要管理员角色校验和创建者身份，因此依赖 common-security。只依赖 common-core 的旧方案不再采用。

#### 搜索和推荐延后

Elasticsearch 搜索涉及索引模型、数据同步、失败补偿和一致性策略。AI 推荐涉及能力归属、输入输出契约和推荐逻辑。两项功能在设计定稿前不进入实现。

### 九、测试策略

Service 层单元测试使用 Mockito 隔离 Mapper，不启动 Spring 容器，不连接 MySQL 和 Nacos。测试覆盖分页筛选结果组装、题目创建、详情、更新、删除、标签创建、更新和删除，以及主要业务异常分支。

请求参数校验测试直接使用 Jakarta Validation，覆盖状态范围、空白标题、嵌套链接和分页筛选参数。

Spring Boot 上下文测试保留，用于验证完整环境中的 Bean 装配和配置加载。
### 0—1 实现边界

题目必须归属赛事，并记录题目年份、题面语言和完成时长。赛事由题目服务维护，题目只保存赛事 ID，不再重复保存赛事类型。

公开能力包括已发布题目的列表、详情、基础条件筛选和随机题目。团队服务通过内部接口读取已发布题目的标题和完成时长，用于创建队伍和计算练习截止时间。

Elasticsearch 搜索和 AI 推荐不属于首版。
