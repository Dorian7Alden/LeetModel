## 版本与数据模型

评审版本不是模型名称或 Prompt 文本的别名，而是一套具有明确说明、公共输入、统一最终得分和独立中间流程的业务能力。系统使用公共控制表管理版本与任务，使用版本独立表保存各版本业务结果。

### 表结构分层

| 表 | 类型 | 职责 |
|----|------|------|
| `review_version` | 公共版本总表 | 定义版本标识、名称、说明、流程摘要、状态和创建时间 |
| `review_task` | 公共任务表 | 记录提交、版本、Prompt 快照、公共状态、当前执行轮次和最终时间 |
| `review_task_log` | 公共追加日志表 | 记录每个执行轮次的步骤、状态、时间、摘要和错误信息 |
| `review_v1_result` | V1 独立结果表 | 保存统一最终得分、V1 评语 JSON 和调用关联标识 |
| `review_v2_*` | V2 独立业务表 | V2 进入设计后定义结果与中间步骤，不复用 V1 业务表 |
| `review_v3_*` | V3 独立业务表 | V3 进入设计后定义结果与中间步骤，不复用 V1 业务表 |

公共表不是把不同版本的业务数据混在一起。它们只保存所有版本都必须具备的控制面事实，使用户查询任务状态时不需要先判断版本再访问不同任务表。

### 版本总表

`review_version` 至少表达：

- 唯一且不可变的 `versionCode`，例如 `BASIC_REVIEW_V1`。
- 面向开发者和管理端展示的版本名称。
- 版本定位和适用场景说明。
- 可直接理解版本差异的流程摘要，不能要求阅读源码才能知道版本做了什么。
- 当前公共输入和最终得分契约版本。
- 启用状态、创建时间和更新时间。

版本记录用于说明和选择固定代码工作流，不用于建设动态工作流平台。流程摘要发生实质变化时应建立新版本，不能静默修改历史版本语义。

### 公共任务表

`review_task` 保存所有版本一致的字段：提交标识、版本标识、Prompt 快照、状态、当前执行轮次、创建时间、开始时间、完成时间和最后错误摘要。

任务状态统一使用等待、执行中、已完成和失败。任务创建时必须锁定提交、版本和 Prompt 快照，后续版本配置变化不能影响已经创建的任务。

同一提交与同一版本只能有一个公共任务。重试增加执行轮次，不创建第二个业务任务。

### 公共任务日志表

`review_task_log` 是追加式业务执行日志，不等同于应用文本日志。每条日志至少关联任务、版本和执行轮次，并记录步骤编码、步骤说明、状态、开始结束时间、耗时、非敏感输入输出摘要、AI 网关调用标识与错误信息。

日志不得保存 API Key、完整 PDF、页面 Base64、完整 Prompt 或供应商原始响应。完整业务结果进入版本结果表，供应商调用细节归 ai-gateway-service。

### 版本独立表

每个版本必须拥有独立结果表；存在版本专属中间产物时继续建立该版本前缀的独立表。不同版本中语义相同的字段保持相同名称和类型，例如任务标识、提交标识、最终得分、创建时间和更新时间。过程字段按版本需要独立设计，不强求一致。

V1 只需要 `review_v1_result`。该表与一个公共任务一对一，使用 `score` 保存统一最终得分，并保存 V1 自己的结构化评语 JSON、模型标识和 AI 网关调用标识。V1 维度评语、优点、问题和建议不构成跨版本公共契约；是否额外拆列以实际查询需求为准，不为未来统计提前增加字段。

### 查询规则

用户首先查询 `review_task` 获得统一状态和版本说明。任务完成后，ai-review-service 根据任务锁定的版本选择对应结果读取器，统一返回最终 `score`，并按用户页面需要附带该版本可展示的过程或评语结果。排行榜只读取 `score`；Controller 不直接感知 `review_v1_result`、`review_v2_result` 等物理表差异。
