## 输入输出

所有 AI 评审版本共享相同的公共输入，并在流程结束时收敛为相同的最终结果契约。统一的是评审任务的入口和最终得分，不是每个版本的全部过程输出。

### 公共输入

一个任务只处理某次提交对应的一份 PDF，公共输入包含：

- `submissionId`：提交标识，用于从 submission-service 获取锁定的 PDF 快照及队伍、题目关联信息。
- `versionCode`：评审版本标识，任务创建后不可改变。
- `reviewPrompt`：本次评审使用的提示词快照。它由评审版本配置产生，不接受普通用户任意改写。
- `paper`：提交对应的原始 PDF。PDF 的对象路径由 submission-service 提供，文件仍归 submission-service 所有。

不同版本可以将 PDF 转换为页面图像、文本或结构化章节，也可以拆分成多个小任务或多轮对话。这些都属于版本内部流程，不改变公共输入。

### 统一最终结果

所有版本结束时都必须产生合法 JSON，并包含同名、同类型、同语义的最终得分字段：

```json
{
  "score": 82.5
}
```

固定规则：

- `score` 是所有评审版本共同的最终业务结果，表示论文总分。
- `score` 为 `[0,100]` 范围内的十进制数。
- `score` 缺失、无法转换或越界时，任务不能完成。
- 排行榜和其他下游能力只依赖统一最终得分，不读取版本专属中间结果。
- 若未来修改最终得分的字段名、类型、范围或业务含义，必须升级公共结果契约并提供兼容读取方案。

### 版本过程输出

每个版本可以定义自己的过程 JSON、步骤结果和版本专属最终补充信息：

- V1 可以在一次模型调用中同时生成 `score`、总体评语、维度评价、优点和问题。
- 后续版本可以由多个小任务分别生成章节分析、证据检查、单项评分或多轮对话记录，最后再汇总出 `score`。
- 过程字段不要求跨版本保持一致，也不进入公共最终结果契约。
- 所有 AI 原始输出和中间输出仍必须是合法 JSON，并由所属版本负责结构校验。
- 版本专属过程结果写入对应版本的独立表，不塞入公共任务表，也不要求 Controller 或排行榜理解其结构。

统一最终结果解决跨版本消费问题，版本独立过程输出保留不同工作流的表达能力。不能因为下游只读取 `score`，就省略版本内部必要的结构校验、日志和结果留存。
