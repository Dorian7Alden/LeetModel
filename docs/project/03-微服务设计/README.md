## 职责边界维护规则

### 归属判断

- 先确定数据所有者。拥有数据库、业务事实和状态流转的服务，是对应能力的默认归属方。
- 再确定业务规则所有者。功能应放在能独立校验规则、完成事务并解释结果语义的服务中。
- 不按页面、使用者身份或 Controller 数量拆分微服务。普通用户和管理员可以调用同一领域服务的不同接口。
- 纯聚合、路由和治理能力不拥有业务事实，不得把下游服务数据复制为新的事实源。
- 当前从 0 到 1 阶段优先追求职责和数据边界清晰，不因预测的响应时间或跨服务调用开销过早合并已经具有独立语义的服务。
- 性能优化延后到功能闭环完成之后，以真实监控和测试结果为依据。

### README 维护

每个微服务目录的 README 必须维护以下内容：

- 服务定位与核心业务目标。
- 服务负责的能力与规则。
- 服务明确不负责的事项。
- 服务拥有的数据、配置和业务事实。
- 上游、下游与跨服务调用边界。
- 当前服务完整的功能清单，包括尚未展开设计或实现的功能。
- 当前服务下的功能设计文档索引。

新增或调整功能时，必须先更新服务 README 的职责边界和功能清单，再更新或新增功能文档。尚未进入详细设计的功能只列入清单，不创建空文档。如果变更影响多个服务的调用关系、数据所有权或服务拆分，还必须同步更新架构设计。

### 功能目录

每个微服务按功能建立子目录，统一采用以下结构：

```text
service-name/
├── README.md
├── 服务级说明.md
└── 功能名/
    ├── README.md
    └── 原子文档.md
```

- 微服务根目录保存服务级 README，以及不属于单一功能的公共说明、整体边界和跨功能决策文档。
- 针对某个具体功能的描述文档不得直接散落在微服务根目录。
- 功能目录 README 只说明功能目标、范围和文档导航。
- 功能的输入输出、执行流程、规则、状态、异常和取舍分别写入短小的原子文档。
- 一篇原子文档只回答一个明确问题。出现多个并列主题时继续拆分，不用固定行数机械判断。
- 尚未开始设计的功能只出现在服务 README 的功能清单中，不创建空目录。
- 不属于具体功能的文档不强行建立功能目录，直接存放在微服务根目录并由服务 README 导航。
- 不再新增笼统的 `服务设计.md`。现有综合文档应在对应功能重新设计时逐步拆分，确认内容已迁移后再删除。

### 文档归类

- 单一微服务内的功能设计放入对应服务目录。
- 跨多个微服务的完整调用链、全局状态流转和服务拆分决策放入架构设计。
- 不可独立运行的公共 Jar 放入 `common` 目录下对应的 Maven 模块目录。
- 一份功能文档只维护一个主题，不在多个服务目录复制同一份设计。
- 服务 README 负责服务概述、职责边界、数据归属和文档导航。
- 一组相关功能需要共享输入、输出或版本约束时，先建立功能概述文档，再为各个具体功能或版本建立独立文档。
- 微服务设计文档只保留功能级流程、边界、规则和取舍，表结构、接口字段和代码执行细节以实现为准。

### 跨服务协作

- 跨服务只通过明确的 API、Feign 契约或业务事件协作，不直接访问其他服务数据库。
- 接口提供方负责校验自己拥有的业务规则，调用方不复制该规则。
- 调用方只保存必要的关联标识和快照，不将其他服务的数据镜像为本地主数据。
- 聚合查询发生局部失败时必须显式标记数据不可用，不使用零值或空集合伪装真实结果。
