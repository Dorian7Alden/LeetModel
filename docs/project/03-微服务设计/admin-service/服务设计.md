## 管理后台服务

> 创建日期：2026-07-30
> 最后更新：2026-08-24

---

### 一、职责

管理后台服务通过 Feign 聚合各业务服务的数据，并为管理功能提供面向客户端的统一入口。不拥有自己的数据库，不存储业务数据。

---

### 二、架构模式

```
admin (聚合层, 端口 8084)
  ├── Feign → user (用户统计)
  ├── Feign → problem (题目统计)
  ├── Feign → team (团队统计)
  ├── Feign → ai-review-service（评审任务与评审结果）
  ├── Feign → ai-evaluation (质量评价与版本对比)
  └── Feign → ai-gateway (模型调用统计)
```

采用聚合层模式。admin 服务本身无数据库，所有数据通过 Feign 同步调用各业务服务获取。仪表盘查询允许局部降级，管理写操作失败时必须明确返回服务异常。

---

### 三、拆分决策

当前不建设管理后台父项目以及按业务领域复制的多个管理微服务。管理员是接口使用者，不是新的数据所有者。微服务仍按领域数据和业务规则拆分。

#### 服务边界

| 职责 | 归属 |
|------|------|
| 管理端统一入口、跨服务聚合与管理视图组装 | admin 服务 |
| 领域数据查询、管理写操作、数据校验与事务 | 数据所属业务服务 |
| 单领域实时统计 | 数据所属业务服务 |
| 跨领域统计视图 | admin 服务 |
| 管理员身份与权限校验 | API 网关与业务服务共同防护 |

admin 服务不代替业务服务执行领域规则，不直连业务数据库，不在本地复制用户、题目、团队或评审数据。

#### 接口分类

各业务服务按用途划分接口：

| 接口类型 | 使用者 | 设计要求 |
|----------|--------|----------|
| 普通业务接口 | 普通用户 | 只返回用户场景需要的数据，执行用户权限与数据范围校验 |
| 管理业务接口 | 管理员 | 使用独立路径和响应契约，执行管理权限校验 |
| 内部服务接口 | admin 服务或其他受信服务 | 只暴露跨服务协作所需能力，不面向外部客户端 |

普通端与管理端需要的查询语义完全一致时，可以共用应用服务方法。当权限、可见数据范围、操作语义或响应字段不同时，应使用独立 Controller 和契约，但底层业务规则仍由同一领域服务维护。

#### 统计分层

| 统计类型 | 处理方式 |
|----------|----------|
| 单领域实时统计 | 由数据所属服务基于自有数据计算 |
| 跨领域管理看板 | admin 服务调用多个服务并聚合展示 |
| 大规模历史分析 | 达到拆分条件后再建设独立分析服务和读模型 |

#### 后续拆分条件

仅当管理能力出现以下情况时，再评估拆分新服务：

- 形成不属于现有业务服务的独立数据模型。
- 大量历史聚合已明显影响业务数据库和 admin 服务。
- 统计任务具有与普通管理请求明显不同的负载、存储或可用性要求。
- 管理能力已形成可以独立开发、发布和扩容的交付边界。

仅因为管理员权限更高、每个业务模块都有管理接口，不构成拆分管理微服务的理由。

### 五、关键设计

- **独立服务不独立数据库**：admin 作为纯聚合层，不持有任何业务数据。这种设计的面试价值：讲清楚"聚合层 vs 独立数据源"的权衡（实时性 vs 解耦 vs 性能）。
- **Feign 降级保护**：DashboardController 通过 `safeGet()` 包装每次 Feign 调用，单个服务异常不影响其他统计项的返回。Fallback 返回 0。
- **RBAC 管理边界**：admin-service 负责管理员鉴权和请求转发，RBAC 数据校验与事务由 user-service 负责。
- **管理接口降级**：服务不可用不能伪装成空数据，避免管理员把故障误判为业务数据为空。
- **权限实际执行**：用户查询接口校验 `user:read`，用户修改接口校验 `user:update`，RBAC 管理接口继续要求 `admin` 角色。
- **AI 评审权限暂缓**：上述既有 RBAC 规则不在当前 AI 评审功能设计中扩展。AI 监控、实验和质量接口当前不设计角色、权限码或身份校验，待核心功能稳定后再统一接入。
- **AI 监控边界**：admin 只负责聚合和展示，通过 AI 网关内部接口查询 Token、成本、延迟、成功率和实验数据，不直接访问 `lm_ai`。
- **质量数据来源**：ai-evaluation-service 拥有 AI 质量指标、归一化结果和综合得分，AI 网关拥有调用、成本和耗时数据，admin 负责聚合展示。
- **评审实验边界**：admin 负责提供管理端入口和聚合视图，ai-review-service 负责产生各评审版本结果，ai-evaluation-service 负责固定样本、重复运行口径和质量对比。
- **质量评价演进**：当前只实现第一版 AI 裁判能力，不提前建立复杂版本边界。后续调整评价指标、基准或权重时，由 ai-evaluation-service 记录调整原因和影响。
- **横向对比口径**：同一批评审结果必须使用同一质量策略版本、质量参数和裁判模型进行对比。
- **防重语义**：一键测试命中相同实验指纹时返回已有实验，不重复产生模型费用。需要再次执行时由管理员明确新建轮次。
- **独立开发约束**：当前不建设用户评价、管理员逐条人工复核或持续人工标注流程，质量结论以自动指标为主。


### 六、AI 评审管理视图

管理端的 AI 评审功能按五个视图组织：

| 视图 | 核心内容 |
|------|----------|
| 总览 | 评审任务量、成功率、平均耗时、Token、正式评审成本和质量检查成本 |
| 版本对比 | 在同一质量策略口径下展示三个工作流版本的质量、稳定性、调用次数、Token、成本和耗时 |
| 一键实验 | 选择论文样本、评审策略和共享参数，显示防重结果、执行进度与对比结果 |
| 质量异常 | 自动门禁失败、结构错误、分数矛盾、评语空泛、证据不足与稳定性异常 |
| 任务追踪 | 从实验、评审任务、工作流步骤、质量任务一直追踪到单次模型调用和失败原因 |

版本对比默认使用实验数据，因为它保证输入和参数一致。生产运行数据只用于监控趋势，不直接用于断言版本质量优劣。
