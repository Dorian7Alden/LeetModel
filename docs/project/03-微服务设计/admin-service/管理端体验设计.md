## 管理端体验设计

### 设计目标

管理端应围绕管理员要完成的任务组织界面，而不是把每个后端资源机械地映射为一个一级菜单。重构保留现有后端契约与数据边界，只调整前端信息架构、操作层级和数据表达。

### 信息架构

| 工作域 | 主任务 | 整合的既有入口 |
|------|------|------|
| 概览 | 判断平台是否健康并快速进入异常区域 | 首页概览 |
| 访问控制 | 查找用户、控制账号状态、配置角色与权限 | 用户、角色、权限、授权 |
| 内容中心 | 维护题目及其分类语境 | 题目、标签、赛事 |
| 业务运营 | 观察从组队到提交、评审、建议和排行的业务链 | 队伍、提交、评审、建议、排行 |
| AI 中枢 | 观察调用质量、执行评价并治理生产版本 | AI 调用、质量评价、生产版本 |

旧路由继续保留并重定向到对应工作域。这样可以兼容已有书签和文档链接，同时只向管理员呈现五个稳定入口。

### 交互层级

访问控制以用户列表为默认工作面。账号状态和角色分配保留为行内操作；角色定义、权限目录和角色授权属于低频配置，通过页面头部按钮打开抽屉，不再占用一级导航。

内容中心以题目列表为默认工作面。标签是题目的检索与分类元数据，通过内容中心内的辅助操作层维护；赛事作为题目归属的基础数据放在同一区域，并支持带重复编码校验的编辑。题目预览使用详情接口读取完整 Markdown，并经过现有安全渲染函数净化后展示。

业务运营和 AI 中枢使用工作域内视图切换。切换只改变当前观察面，不制造新的一级导航层级。页面头部先表达核心状态和统计，再呈现可筛选明细，避免所有数据都退化为独立表格。

### 视觉与布局

- 侧栏固定为视口高度，品牌区、导航区和底部状态区分层，导航区独立滚动。
- 桌面端使用清晰的工作域标题、说明和状态提示；侧栏收起后保留图标与提示。
- 主内容区限制舒适阅读宽度并保留横向数据表的可用空间。
- 小于桌面宽度时侧栏默认压缩，头部隐藏低优先信息，工具栏允许换行。
- 数据表达组合使用指标卡、状态标签、进度或占比、图表与明细表，不用单一表格承担所有判断。

### 边界与取舍

本轮不改变 user-service、problem-service、submission-service 和 AI 相关服务的数据所有权。工作域摘要只消费已有接口；赛事更新仍由 problem-service 校验，提交 PDF 地址仍由 submission-service 按需签发，admin-service 只负责管理端转发。部分服务不可用时沿用明确的不可用提示，不用零值伪装成功。旧页面实现暂时作为工作域内部组件复用，待交互稳定后再决定是否进行纯结构性拆分。

### 验收重点

1. 常见桌面高度下不再出现无法访问的侧栏条目，极小高度仍可滚动。
2. 用户角色授权和题目标签维护不需要离开所属工作域。
3. 题目 Markdown 能安全渲染，空题面和详情接口失败均有明确状态。
4. 旧管理地址可以稳定落到新的工作域和正确内部视图。
5. 管理端生产构建通过，并在桌面和窄视口完成关键路径浏览器复验。

### 实现与验收

2026-08-30 完成首轮实现。管理端一级导航已收敛为五个工作域，原有十五组资源路由通过重定向保留兼容。访问控制、内容中心使用主工作面与抽屉式辅助任务；业务运营以五步链路和内部视图切换串联业务数据；AI 中枢用成功率、Token、耗时、评价任务和生产工作流快照表达运行姿态。

题目列表通过管理详情接口读取完整题面，使用 `renderSafeMarkdown` 统一执行 Markdown 转换和 DOMPurify 净化。题目标题和行内预览操作均可打开发布预览，空题面显示明确空状态。

验收结果：

- `npm run build` 通过，Vite 完成 2378 个模块转换；保留项目既有大 chunk 警告，没有新增构建错误。
- 真实管理员账号从登录入口进入管理端，概览展示十个可用领域指标、业务量图、AI 状态图和工作域入口。
- 访问控制的角色抽屉、内容中心的标签兼容路由、题目 Markdown 预览、业务运营视图切换、AI 质量评价切换均使用真实接口数据通过。
- `820x640` 视口下侧栏自动收起，导航容器为独立 `overflow-y: auto`；`390x844` 视口下页面无整页横向溢出，侧栏和内容区宽度分别为 72 与 318 像素。
- 浏览器关键路径未产生 console error 或 warning。

### 第二轮反馈与验收

2026-08-30 根据体验反馈完成第二轮收敛：亮色主题下的侧栏改为低对比灰蓝色；用户列表默认每页 10 条并展示总数、页容量、页码和跳转；角色授权改为以角色职责、权限覆盖度、业务分组和未保存状态为核心的策略工作台；概览业务量图固定展示全部横轴标签。

内容与运营能力补齐了两个真实闭环。赛事名称和编码可在内容中心直接编辑，problem-service 负责字段规范化、存在性和编码唯一性校验。提交列表通过管理端按需获取 submission-service 生成的临时对象地址，并在抽屉内预览 PDF；临时地址不写入提交列表或持久快照。

数据表达增加以下视图：

- 排行榜按 0–100 的每个整数分数生成直方图，并以 0–59、60–69、70–79、80–89、90–100 展示非空分段占比。
- AI 调用页展示当前查询样本的模型调用占比、模型平均响应时间，以及系统累计成功/失败比例，并明确每张图的统计口径。
- AI 中枢新增版本目录，展示 owner 服务真实发布的功能、版本、状态、兼容性和输入输出契约；尚未发布统一目录的 SUGGESTION 明确显示“目录待接入”，不虚构版本。

第二轮验收结果：

- `mvn -pl problem-service,submission-service,admin-service -am test` 通过，共 71 项测试；覆盖赛事更新规范化、重复编码和缺失赛事，以及提交 PDF 临时地址生成。
- `npm run build` 通过，Vite 完成 2380 个模块转换；仅保留项目既有大 chunk 警告。
- 真实浏览器使用管理员数据验证了用户两页分页、角色授权工作台、赛事编辑表单、提交 PDF 预览入口、真实排行榜样本图表、AI 调用三类图表和三条已发布工作流版本。
- SUGGESTION 当前没有 owner 版本目录，页面明确展示待接入状态；这是契约缺口的真实表达，不以硬编码数据掩盖。
- VIP 高级模型分层记录为后续候选能力。本轮不实现；进入设计前需统一模型路由、配额与计费、失败降级、运行快照和越权防护。

### 第三轮反馈与验收

2026-08-30 完成管理数据完整性与默认分析视图修正。提交 PDF “不存在”的根因不是对象缺失，而是提交列表把 19 位雪花 ID 作为 JSON 数字交给浏览器后发生精度舍入。提交快照和按需预览契约现只对标识字段使用字符串序列化，计数和耗时等度量仍保持数值；同样的保护覆盖全局排行中的题目标识。

AI 调用页改用服务端分页并展示总量、页容量、页码与跳转。功能、操作、评价任务、供应商、模型和状态筛选均支持历史值下拉与精确输入；筛选项最多返回 200 个去重值。模型占比、成功失败和平均响应时间使用完整筛选结果聚合，不再从当前页或最近 50 条推算，因此 CHAT 和 EMBEDDING 模型同时可见。模型选择还合并 New-API 实时 `/models` 目录，已确认 `gemini-3.7-flash-high` 可用，并在网关能力目录中显式允许。

排行榜未选择题目时默认聚合 submission-service 的全量成功提交事实、ai-review-service 每个提交的最新完成评审，以及 ranking-service 当前上榜快照，展示总体指标、题目提交热度、题目平均分和题目统计表。选择题目进入既有逐分直方图与分段占比，清空选择返回全局视图；两类视图切换时销毁并重建 ECharts 实例。

第三轮验收结果：

- `mvn -pl common/common-api,submission-service,ai-gateway-service,ranking-service,admin-service -am test` 通过，共 130 项测试；新增雪花 ID 序列化、全局排行聚合，以及 AI 分页、CHAT/EMBEDDING 聚合和筛选项集成覆盖。
- `npm run build` 通过，Vite 完成 2380 个模块转换；仅保留项目既有大 chunk 警告。
- 新进程真实接口返回 136 条 AI 调用事实；模型统计同时包含 67 条 EMBEDDING 与多组 CHAT 调用，New-API 实时目录返回 `gemini-3.7-flash-high`。
- 提交列表返回原始 ID `2092649726601232386`，按该 ID 获取预览成功；临时地址返回 HTTP 200、`application/pdf`。
- 全局排行真实聚合返回 200 次成功提交、10 个题目和 90 支去重上榜队伍；长题目标识保持字符串，题目热度与平均分均有实际数据。
