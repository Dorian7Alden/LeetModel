## 操作审计架构

> 设计状态：目标设计已确认，audit-service、专用审计 Topic 和统一操作审计页尚未实施。已有 `ai_call_log`、`assistant_production_audit`、`assistant_tool_call` 和领域任务字段保持当前语义，不伪装成已完成的中央操作审计。


### 决策

采用“业务所有者分散产生、RocketMQ 可靠传递、audit-service 集中不可变归档”。不让业务服务在主事务提交前后同步 Feign 调用 audit-service，不引入分布式事务。

语义所有权与归档所有权分开：

- 业务服务拥有“这次操作实际改变了什么”的规则，只有它能生成可信的差异摘要和结果。
- audit-service 拥有统一审计记录、查询、保留、归档、完整性和访问控制，不能修改任何业务事实。
- admin-service 负责管理员鉴权、操作者注入和统一查询页，不写审计副本。


### 审计、领域历史与日志

| 数据 | 例子 | 是否进中央操作审计 |
|------|------|----------------------|
| 高风险人工/治理操作 | 用户禁用、角色变更、生产回滚、DLQ 重放 | 是 |
| 安全事件 | 登录成功/失败、鉴权拒绝、密码修改 | 是，按安全分类 |
| 普通领域事实 | 队伍成员、提交版本、评审结果 | 由领域表保留；只对高风险或需追责操作另写审计 |
| AI 调用计量 | Token、费用、模型、状态 | 保留在 ai-gateway 调用审计，不复制为人员操作审计 |
| 运行日志 | 异常栈、重试、降级 | 否 |


### 首期操作目录

| 分类 | 操作编码示例 | 所有者 | 风险 |
|------|--------------|--------|------|
| 身份安全 | `AUTH.LOGIN_SUCCESS/FAILED`、`USER.PASSWORD_CHANGE` | user-service | 中/高 |
| 用户与 RBAC | `USER.STATUS_CHANGE`、`USER.ROLE_CHANGE`、`ROLE.PERMISSION_CHANGE` | user-service | 高 |
| 内容管理 | `PROBLEM.CREATE/UPDATE/DELETE`、`PROBLEM.ATTACHMENT_DELETE`、`CONTEST.UPDATE` | problem-service | 中/高 |
| 论文与提交 | `SUBMISSION.FINALIZE`、未来的管理下载/导出 | submission-service | 高 |
| AI 任务治理 | `AI_QUEUE.CANCEL`、`EVALUATION.PAUSE/RESUME/CANCEL/RETRY` | ai-gateway/evaluation | 中/高 |
| AI 版本治理 | `ASSISTANT_CONFIG.ACTIVATE/ROLLBACK`、`WEIGHT_SCHEME.DEACTIVATE` | assistant/evaluation | 高 |
| 消息运维 | `CONSUMER.PAUSE/RESUME`、`OUTBOX.REPLAY`、`DLQ.REPLAY` | 消息所有者服务 | 高 |
| 派生数据 | `RANKING.REBUILD` | ranking-service | 中 |
| 审计治理 | `AUDIT.SEARCH_EXPORT`、`AUDIT.RETENTION_CHANGE` | audit-service | 高 |

普通列表读取、公开题库浏览、健康检查、自动 Worker 心跳不进操作审计。任何新操作先进版本化操作目录，再发布生产者，不使用 Controller 方法名当作稳定编码。


### 事件契约

新增独立 NORMAL Topic `leetmodel-operation-audit-v1` 和消费组 `cg-audit-archive-v1`。它不复用已有设计中“可重建、非权威”的 `OBSERVABILITY` 投影语义。审计事件使用公共消息信封、`eventId` 作为 Key、`OPERATION_AUDIT_RECORDED` 作为 Tag，Payload 自身带 `auditSchemaVersion`。

Payload 的稳定字段为：

| 字段组 | 内容 |
|--------|------|
| 事件 | `auditEventId`、`operationId`、`phase`、`occurredAt`、`sourceService`、`serviceVersion` |
| 操作 | `category`、`operationCode`、`riskLevel`、`outcome`、`reason`、`failureCode` |
| 操作者 | `actorType`、`actorId`、经白名单处理的 `actorRolesSnapshot` |
| 目标 | `targetType`、`targetId`、`targetVersion` |
| 变更 | 操作专属白名单 `beforeSummary`、`afterSummary` |
| 关联 | `traceId`、`swTraceId`、`requestId`、可选领域任务/消息关联 ID |
| 来源 | 经信任代理解析与脱敏的 IP、User-Agent 摘要 |

消息必须通过 64 KiB 公共限制，不携带完整请求/响应、完整实体快照、证件信息、密码、Token、论文、Prompt、回答、向量、消息 Payload 和幂等键。差异摘要不通过泛用反射序列化业务实体，每个 `operationCode` 明确字段白名单。

`auditEventId` 必须等于公共消息信封的 `eventId`，不再制造第二个传递标识。`phase` 与 `outcome` 分开表达：

| 场景 | `phase` | `outcome` |
|------|---------|-----------|
| 外部副作用已被批准、尚未确定结果 | `REQUESTED` | `PENDING` |
| 操作成功完成 | `COMPLETED` | `SUCCEEDED` |
| 执行失败且未产生预期结果 | `COMPLETED` | `FAILED` |
| 鉴权或业务规则拒绝 | `COMPLETED` | `REJECTED` |

纯数据库事务成功时只产生 `COMPLETED/SUCCEEDED`；外部副作用才需要先产生 `REQUESTED/PENDING`。同一 `operationId` 可以有多条阶段事件，每条事件有独立 `auditEventId`。


### 操作者可信链

- Gateway 必须删除公网请求伪造的内部操作者头，再根据已认证会话建立可信用户上下文；客户端提交的 `actorId`、角色和风险等级一律不可信。
- admin-service 只传递经过认证的操作者与 `operationId`，领域服务仍按自己的数据与权限规则重新授权，并由领域服务生成最终审计事件。
- 高风险操作必须提供结构化原因，原因限长、脱敏且不得代替稳定 `operationCode`；批量操作还要记录目标数量和独立批次 ID，不塞入完整 ID 列表。
- 定时任务、Worker、恢复器和服务账号使用 `actorType=SYSTEM/SERVICE` 与稳定 `actorId`；代表用户执行时同时记录发起者与执行主体，不能伪装成人工直接操作。
- `operationId` 在可信入口生成并跨同步调用、Outbox、外部副作用和最终审计传播。同一业务命令重试复用原操作幂等键，但每条阶段事件仍有唯一 `auditEventId`。


### 一致性与阶段

#### 数据库业务变更

```text
校验操作者与规则
  -> 锁定目标并计算白名单差异
  -> 同一本地事务修改业务事实 + 写 COMPLETED/SUCCEEDED 审计 Outbox
  -> 提交并返回
```

对权限提升、账号禁用、生产配置切换和人工重放等高风险事务，审计 Outbox 写入失败必须使业务事务回滚。audit-service 是异步下游，其实时可用性不参与业务事务。

#### 拒绝与失败尝试

授权拒绝、登录失败和高风险规则拒绝没有业务变更，由规则所有者使用独立短事务写 `COMPLETED/REJECTED` 审计 Outbox。未知系统异常先记脱敏运行日志；能够安全确定操作者与意图时再写 `COMPLETED/FAILED` 尝试，不用审计异常覆盖原始错误。

#### 外部副作用

Consumer `suspend/resume`、未来的外部密钥轮换等无法放入本地数据库事务的操作使用同一 `operationId` 的追加式两阶段事件：

```text
REQUESTED/PENDING -> 执行副作用 -> COMPLETED/SUCCEEDED 或 COMPLETED/FAILED
```

不把 `REQUESTED/PENDING` 行更新为终态。只有该事件但超过操作目录 deadline 仍无 `COMPLETED` 事件的操作进入“审计未完整”告警，人工核验真实外部状态，不根据审计自动重复执行副作用。


### 中央存储模型

audit-service 独占 `lm_audit`。目标表 `operation_audit_event` 只追加，不设 `deleted`、不提供普通更新和删除能力。核心约束与索引为：

- `audit_event_id` 等于消息信封 `eventId` 并全局唯一；Consumer Inbox 使用 `consumer_group + event_id` 唯一约束，归档表使用 `audit_event_id` 唯一约束，分别承担消费和存储幂等。
- `operation_id + occurred_at` 支持操作阶段时间线。
- `actor_id + occurred_at`、`target_type + target_id + occurred_at`、`operation_code + outcome + occurred_at` 支持调查。
- `trace_id`、`sw_trace_id` 仅作精确查询字段，不作 Prometheus label。
- JSON 摘要保留 schema version 并设置严格长度限制；常用查询字段不隐藏在 JSON 中。

归档保留时长由环境政策配置，必须长于运行日志和 Trace。尚无合规依据时不在设计文档伪造固定年限；实施前必须根据数量、存储和个人信息风险确认在线与归档期。


### 查询、权限与完整性

audit-service 只向受信内部管理契约提供查询，支持时间、服务、分类、编码、风险、操作者、目标、结果、`operationId`、`traceId` 和 `swTraceId`。admin-service 页面展示筛选列表、单次操作阶段、目标时间线和白名单差异，并提供 SkyWalking 追踪标识复制/跳转。

查询权限与普通管理员业务权限分离。首期页面只读；导出、保留策略修改、查询权限变更也要产生审计。数据库应用账号限制为追加与查询所需权限，定期备份并监测非授权更新/删除。如果未来出现强合规需求，再增加签名归档或 WORM，首期不实现高并发全局哈希链。


### 故障、告警与重放

| 故障 | 事实 | 处置 |
|------|------|------|
| 业务事务回滚 | 无成功业务事实、无 `COMPLETED/SUCCEEDED` 审计 Outbox | 调用方按原业务规则重试 |
| audit-service/Broker 不可用 | 本地审计 Outbox 积压 | Relay 退避，按最老年龄告警 |
| 重复投递 | Inbox 或唯一约束命中 | 幂等 ACK，不复制审计 |
| schema/白名单不支持 | BLOCKED 或 DLQ | 立即告警，禁止自动回灌 |
| 只有 REQUESTED/PENDING | 操作超过 deadline 无 COMPLETED 结果 | 告警并人工核对真实状态 |
| 中央归档长时间不可用 | 高风险审计水位超严重阈值 | 新高风险操作 fail-closed，普通业务继续 |

审计 DLQ 重放使用原 `auditEventId` 恢复中央归档，运维人员的“批准重放”本身使用新 `operationId` 和新审计事件记录。不把归档失败修改为成功或删除原 Outbox。


### 历史兼容与迁移

- `ai_call_log` 继续是 AI 资源与调用事实，不迁入操作审计主表。
- `assistant_production_audit` 和工具调用审计保留领域解释与历史查询；新操作与领域审计同事务写中央审计 Outbox。
- `evaluation_task.last_operation` 等字段保留为最新摘要，新的完整操作历史进中央审计。
- 历史操作只在能从已有不可变事实确定操作者、操作、目标、时间和结果时回填；不根据当前状态伪造历史审计。


### 验收

- 用户角色变更的业务事实和 `COMPLETED/SUCCEEDED` 审计 Outbox 只能同时提交或同时回滚。
- 重复消息只产生一条中央审计事件；乱序阶段仍可按 `operationId + occurredAt` 解释。
- Consumer 暂停与 DLQ 重放都有 `REQUESTED/PENDING` 和明确的 `COMPLETED` 终态，操作者和原因不再只拼接在文本中。
- 不可用的审计源、积压、非法 schema、DLQ 和未完整阶段在管理页和 Prometheus 中显式显示。
- 审计数据不含密钥、凭据、论文、Prompt、回答、知识片段、向量和消息 Payload。
