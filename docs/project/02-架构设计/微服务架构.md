> 创建日期：2026-07-23

### 一、拆分原则

后续任何微服务的新增、合并、拆分，均依据以下原则判断：

1. **单一业务能力**：一个服务只负责一个限界上下文，不把无关的业务逻辑塞进同一个服务
2. **数据主权独立**：每个服务独占自己的数据库，不允许跨服务直连数据库
3. **异步优先**：服务间能通过 MQ 解耦的，不做同步调用；能最终一致性的，不强求强一致性
4. **复用与治理分层**：稳定的客户端契约下沉为公共 Jar，需要统一运行时治理的能力独立部署为服务
5. **拆分可讲**：每次拆分要有明确的面试可讲点（服务间通信、异步解耦、限流熔断等），不为拆而拆

- **ai-assistant-service / ai-review-service / ai-suggestion-service / ai-evaluation-service** 通过 common-ai 调用模型，各自维护业务工作流和输出契约
- **common-ai** 作为 Jar 被引用，只提供 AI 网关客户端、统一契约和测试支持
- **ai-gateway** 独立部署，是 LeetModel 访问 new-api 的唯一出口，负责业务调度、统一错误、Token、成本和调用审计；供应商密钥与渠道治理归 new-api

- 评审、建议和后台评价使用 RocketMQ 可靠唤醒本服务数据库任务，排行由最终提交与评审完成事件触发；消息不替代领域任务和结果事实

### 六、关键设计决策

#### 决策 1：团队服务独立 + RBAC 角色分层

团队有独立的生命周期（创建 → 组队 → 提交 → 解散），解散后需保留历史记录。独立后可讲**服务间通信**话题（user 调用 team 校验成员）。

RBAC 角色分为三层：**管理员 > VIP 用户 > 普通用户**。VIP 角色控制改进建议等付费功能的访问权限，增加权限体系的层次感和面试深度。

#### 决策 2：作品管理与 AI 处理分离

submission-service 管理论文提交和文件存储，ai-review-service 和 ai-suggestion-service 负责各自的 AI 业务处理。具体调度方式由各业务能力单独设计：
- submission 将提交事实与评审 Outbox 同事务提交，不等待下游评审结果；默认由 RocketMQ 唤醒评审，`FEIGN_RELAY` 只作为读取同一 Outbox 的受控回退
- ai-review-service 通过数据库任务表和租约 Worker 调度执行评审，不将结果所有权回写给 submission-service
- 计算密集型 AI 操作独立部署，便于限流、重试、扩缩容

#### 决策 3：评审与建议分离（VIP 权限）

评审打分是核心功能，每次提交必须执行。改进建议为 VIP 功能，通过 RBAC 角色控制访问。独立部署便于：
- 权限控制：网关层根据用户角色（VIP/普通）拦截建议请求，suggestion 服务无需感知权限逻辑
- 差异化限流：VIP 建议服务可单独配置资源配额
- 独立演进：两种 AI 工作流的 Prompt 和模型可分别迭代
- 面试可讲：RBAC + 服务拆分的实际业务落地

#### 决策 4：AI 客服独立

对话式 AI 客服与题目 CRUD 是两种不同的交互模式。assistant 独立为服务：
- 定位为可拓展的对话式 AI 入口，后续可接入知识库等能力，当前专注选题推荐
- 需要会话状态管理和流式输出，与普通请求-响应模式技术特征不同
- 面试可讲：AI Agent + 工具调用（查题目库、查用户历史）的设计模式

#### 决策 5：排行榜异步更新 + 每题独立榜单

评审完成和最终提交变化分别通过 MQ 通知 ranking-service，并按题目合并重建：
- 解耦与削峰：排名重算不阻塞评审流程
- 每题独立榜单：每个题目维护独立的排名，展示多维度小分与总分
- 最终一致性：排名允许短暂延迟，换取系统解耦

#### 决策 6：管理后台为聚合层

admin 服务不拥有核心业务数据，调用各服务聚合统计数据。

管理后台不按业务领域拆成一组与现有微服务对应的管理微服务。用户、题目、团队和评审等数据仍由原业务服务拥有，管理员对这些数据的查询和修改仍由数据所属服务执行。

服务拆分遵循以下原则：

- 按数据所有权和业务规则拆分微服务。
- 按普通用户、管理员和内部服务拆分接口入口与权限。
- 语义完全一致的查询可以共用应用服务能力。
- 权限、数据范围或响应字段不同时，使用不同的接口契约，但不复制核心业务规则。
- 单一领域的实时统计由数据所属服务提供，跨领域视图由 admin 服务聚合。

```mermaid
flowchart LR
    U[普通用户] --> G[API 网关]
    M[管理员] --> G
    G -->|普通业务接口| D[业务服务]
    G -->|管理端接口| A[admin 服务]
    A -->|管理操作与单领域统计| D
    A -->|跨领域聚合| V[管理视图]
```

当后续出现独立的数据模型、大量历史分析、明显不同的负载特征或独立交付边界时，再评估拆分分析服务或独立管理能力。不仅因为调用者是管理员就拆分新微服务。

#### 决策 7：AI 客户端与运行时治理分层

项目同时建设 `common-ai` 和 `ai-gateway-service`。`common-ai` 是业务服务使用的公共 Jar，负责统一调用契约和 AI 网关客户端。AI 网关是独立服务，集中管理 LeetModel 业务调度、逻辑模型绑定、Relay Token、统一错误、Token、成本和调用审计；供应商、渠道密钥、渠道重试、额度和健康归 new-api。

业务 Prompt 和生成工作流程留在各自业务服务。AI 网关只提供模型调用治理，不吸收业务生成或稳定性评价逻辑。固定样本、重复实验、评分方差和标准差由 ai-evaluation-service 统一管理。AI 网关提供调用、用量、成本、耗时和状态数据，管理后台负责聚合展示。


### 当前实现基线

当前微服务架构按职责、数据所有权和业务规则拆分。MVP 主链、三级缓存和 RocketMQ 可靠异步链路均已完成验收；响应时间、跨服务调用开销和未来吞吐量仍需由实测数据驱动优化。

服务间可靠消息负责跨服务通知与唤醒，领域任务表、租约和结果表继续保存权威执行事实。三级缓存只覆盖公开题库和当前排行，不扩展到权限、运行中任务、上传状态或 AI 内容。

提交服务独占 lm_submission，负责 PDF 上传、版本历史和最终版本锁定。

评审服务独占 lm_review，负责持久化评审任务、异步执行、失败重试和结果查询。

AI 评价服务独占 lm_ai_evaluation，负责 REVIEW 与 ASSISTANT 的评价任务、固定样本集、重复运行结果、可信原始指标、权重和版本选择指数。它不通过另一个 AI 进行主观二次评价，也不预设论文改善建议必须进入自动评价。

评审异步执行采用 RocketMQ 可靠唤醒、Inbox 去重、数据库任务表和租约 Worker。跨服务事件与领域执行事实保持分层，Broker 故障恢复、重复投递和人工 DLQ 重放均按正式消息设计治理。
