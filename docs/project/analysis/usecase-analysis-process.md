## 一、参与者识别

从需求文档的功能描述中提取直接参与者，将具体角色抽象为参与者类型。

### 主要参与者

| 需求来源 | 原始角色描述 | 抽象为参与者 |

| 1. 注册与登录 | 注册账号并登录系统的用户 | 普通用户 |

| 8. 改进建议 | 可使用改进建议功能的用户 | VIP 用户（继承普通用户） |

### 次要参与者

| 需求来源 | 外部系统/服务 | 抽象为参与者 |
|----------|-------------|-------------|
| 4. AI 智能客服 | AI 客服对话系统 | AI 系统 |

## 五、用例图设计决策

### 包含关系（`«include»`）

登录账户（UC-02）被以下用例包含：

| 主用例 | 理由 |
|--------|------|
| 管理队伍（UC-03） | 组队操作需认证身份 |
| 浏览题目（UC-04） | 题目浏览需登录后访问 |
| AI 客服对话（UC-05） | 客服对话需识别用户以提供个性化推荐 |
| 提交作品（UC-06） | 提交需关联用户/队伍身份 |
| 管理作品（UC-07） | 只能查看自己的提交记录 |
| 请求改进建议（UC-09） | VIP 权限校验依赖认证 |
| 查看排行榜（UC-10） | 需登录后查看 |
| 管理后台（UC-11） | 管理员身份校验 |

### 泛化关系

VIP 用户 → 普通用户：VIP 继承普通用户的全部用例，额外拥有请求改进建议权限。

### 未使用扩展关系

当前用例间未使用 `«extend»`。扩展关系用于"仅在特定条件下触发的可选附加功能"——如"购买运费险扩展了管理订单"。当前需求中无符合条件的场景。

### 系统触发关系

以下为系统内部自动触发，非参与者直接操作，用虚线表示：

| 触发源 | 目标 | 说明 |
|--------|------|------|
| 提交作品（UC-06） | 评审打分（UC-08） | 提交成功后自动触发评审 |
| 评审打分（UC-08） | 查看排行榜（UC-10） | 评审完成后自动更新排名 |
