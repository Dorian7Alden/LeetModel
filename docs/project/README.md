## 设计颗粒度

`docs/project/` 下的文档用于纠正、说明、补充和参考，只保留对理解项目有长期价值的设计结论。

项目设计文档应当说清：

- 功能目标与范围
- 输入与输出
- 大致执行流程
- 服务职责与数据归属
- 关键业务规则与异常边界
- 需要长期保留的方案取舍

通常情况下，项目设计文档不应当复制已经可以由实现直接表达的细节：

- 接口路径、请求字段和响应字段以 Controller、DTO 和 VO 为准
- 类、方法、分支、算法和实现步骤以代码与测试为准
- 工程配置、依赖和运行参数以当前配置文件为准

当一轮任务本身就是详细系统分析与设计，并且表结构会直接影响职责、状态、一致性、追踪或扩展边界时，可以在设计文档中定义拟议的数据表、字段、类型、约束、索引和关系。此类内容必须标明是设计草案还是已确认设计，不得描述成已经落地；进入实现后，Flyway SQL 和当前数据库结构仍是最终事实，设计文档必须随实现差异同步修正。

文档与实现冲突时，先核对当前代码和运行行为，再修正文档。不为了保持旧文档而曲解现有实现。


## 微服务功能文档结构

微服务目录以功能为单位组织设计文档：

```text
微服务名/
├── README.md
├── 服务级说明.md
└── 功能名/
    ├── README.md
    ├── 输入输出.md
    ├── 执行流程.md
    ├── 业务规则.md
    └── 异常处理.md
```

微服务 README 维护服务定位、职责边界、数据归属、完整功能清单和文档导航。针对某个具体功能的文档应放入独立功能目录，功能目录内的 README 只维护该功能的目标、范围和原子文档索引。

不属于某个具体功能的服务级说明、公共规则、整体边界、跨功能决策和补充说明，可以直接存放在微服务目录。不得为了形式统一，把这类文档强行归入虚构的功能目录。

原子文档只描述一个明确事项。例如输入输出、主流程、状态变化、业务规则、异常处理或方案取舍应按实际内容分别成文。没有内容时不创建空文档，多个事项也不得为了减少文件数量而合并成长文档。

文档是否需要拆分由主题边界决定，不使用固定行数作为唯一标准。文档已经需要多个并列主题才能讲清时，应当拆分并由功能 README 建立导航。


## 当前阶段优先级

当前处于从 0 到 1 建立核心功能闭环的阶段。项目设计优先保证架构边界清晰、业务流程完整和功能可以实际运行。

微服务拆分主要依据：

- 服务是否拥有清晰且独立的职责
- 业务数据和事实由哪个服务拥有
- 业务规则应当由哪个服务解释和执行
- 不同能力是否具有清晰的变化原因和扩展边界

当前不因预测的网络开销、响应时间、调用次数或尚未出现的高并发问题放弃清晰的服务边界。只有已经阻断核心流程的性能问题需要在当前阶段处理。

功能闭环完成后，再根据真实调用数据、耗时、吞吐量和失败情况进行性能优化，不在系统还未跑通时对所有可能问题进行过度设计。
