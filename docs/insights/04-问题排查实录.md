# 04 问题排查实录

## 4.1 Redis 内存异常排查

### 问题描述

业务层面仅写入了不到 100 条小数据（Token 黑名单 key、测试 Hash key），但 Redis 进程内存占用超过 1G，占服务器总内存（1.72G）的 68.4%，内存占用完全不符合业务数据规模。

![Redis 内存占用异常截图](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504151909474.png)

排查初期的一个可疑线索：通过 Navicat 连接 Redis 时，可视化查询全部数据一直加载不出来，卡了 10 分钟都加载不出来，但用命令行 query 指令一下就出来了。可视化加载的反复重试可能导致内存无法释放。

![Navicat 可视化加载卡住](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504161003560.png)

### 排查过程

遵循「**从外到内、从现象到本质、先排除低级错误再深入底层**」的通用排查逻辑：

**步骤 1 — 系统层面锁定异常进程**

执行 `free -h` 确认总内存 1.72G，已用 1.5G，剩余仅 80M。执行 `ps` 按内存排序，定位到 `redis-server` 进程内存占比 68.4%，是唯一的异常项。

**步骤 2 — 进入 Redis 内部获取核心指标**

执行 `INFO memory`，关键发现：

| 指标 | 数值 | 说明 |
|------|------|------|
| `used_memory_human` | 1.17G | Redis 引擎分配的总内存 |
| `used_memory_rss_human` | 1.17G | 操作系统视角的物理内存 |
| `mem_fragmentation_ratio` | 1.00 | 内存碎片率正常 |
| `maxmemory` | 0B | 未设置内存上限 |
| `maxmemory_policy` | noeviction | 满后直接拒绝写入 |

- 碎片率 1.00，排除内存碎片异常。`used_memory` 与 `rss` 完全一致，说明是 Redis 内部合法分配，不是 OS 层面的泄漏。
- `maxmemory=0` 意味着无上限，存在溢出风险。
- 版本为 3.x，缺少 `MEMORY USAGE` 等诊断命令。

**步骤 3 — 验证业务数据量**

执行 `dbsize` 返回 7 个 key，与预期一致。`SCAN` 全量遍历确认无隐藏数据。排除 key 数量过多，问题锁定在单个 key 的内部数据量或非业务数据开销。

**步骤 4 — 排除高频异常场景**

- 客户端缓冲区：仅 1 个活跃连接，`omem` 均为 0，排除。
- 持久化缓冲区：AOF 未开启，无正在进行的 RDB 快照，排除。

**步骤 5 — 重启验证**

重启 Redis 后内存依然 1.17G，排除临时内存泄漏，问题锁定在持久化文件或内存中的业务数据本身。

**步骤 6 — 验证持久化文件**

RDB 文件仅 14M，与内存中 1.17G 存在近百倍差距。说明 RDB 是旧快照，1.17G 新数据未触发持久化落盘。

**步骤 7 — 排除多实例**

确认仅一个 Redis 进程，PID 与 systemd 管理的一致，排除重启错服务的低级错误。

**步骤 8 — 兜底验证**

先备份 RDB 文件，再执行 `FLUSHALL` 清空全库。内存从 1.17G 瞬间降至 793.70K。

**最终根因**：Redis 内存中存在大量未持久化到 RDB 文件的业务数据。虽然表面仅 7 个 key，但其中存在大 key（大概率是测试用的 Hash 写入了海量字段），或大量过期未被惰性删除的 key。

### 解决方案

**临时修复**：清空脏数据后从备份 RDB 恢复正常业务数据。

**永久优化**：
1. 设置 `maxmemory 256mb` + `maxmemory-policy allkeys-lru`，防止内存无限上涨
2. 放弃完整 JWT Token 作为 Key 名，改用 SHA256 哈希值，将 Key 长度从 300+ 字符压缩至 64 字符
3. 调整 RDB 快照触发规则，避免数据长期不落盘
4. 从 3.x 升级至 6.2+ 稳定版，支持 `MEMORY` 诊断命令和自动内存碎片整理

### 排查方法论（面试可复用）

固定排查路径：`top/ps 锁定异常进程` → `INFO memory 分析内存分布` → `确认数据量与大 key` → `排除客户端/缓冲区/持久化` → `重启验证临时/永久` → `兜底清空锁定根因`

**核心踩坑点**：
1. 绝对不要设 `maxmemory=0`，必须设内存上限和淘汰策略
2. 不能只看 key 数量，一个 Hash 内写百万字段也能占满内存
3. 不要用超长字符串（完整 JWT、URL）作为 Key 名
4. RDB 文件大小不能用来判断内存中的数据量（持久化是触发式的）
5. 老版本 Redis（3.x）缺少诊断能力，优先用 6.x+ 稳定版

**核心思维**：每一步操作都有明确的目的，每一个结论都有数据支撑，通过排除法逐步缩小范围，用兜底操作实锤根因，而非靠猜测解决问题。

## 4.2 Redis 持久化磁盘锁

### 问题描述

远端服务器 Redis 服务挂了，但受影响的接口似乎并未使用 Redis 缓存，而是走 MySQL，导致问题一开始难以定位。

![Redis 服务异常报错](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260503003500871.png)

### 排查过程

1. 服务器内存快满了，数据库查询变慢，导致原本可以正常运行的接口查询失败——刚才还能执行的接口，现在就无法正确返回数据了。

![服务器内存占用接近满载](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504004944956.png)

2. 通过服务器内存分析，发现 Redis 进程占用了大量内存。

![Redis 进程内存占用分析](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504005307825.png)

3. 进一步排查过程：

![排查过程记录](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504010603736.png)

### 根因

在 AI 协助排查下，最终确认不是 Redis 数据占用的问题（根本没什么数据）。Redis 被磁盘问题锁死了——**Redis 持久化（RDB）流程出问题时，内存无法正常释放**，导致 Redis 服务异常。不是 Redis 内存本身有问题，是磁盘 I/O 层面的故障导致了连锁反应。

![RDB 持久化磁盘问题根因](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504012428181.png)

### 解决

![解决过程记录](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504012704604.png)

通过排查 Redis 持久化日志定位磁盘异常，修复持久化流程后恢复正常。

## 4.3 数据库连接池报错掩盖真实错误

### 问题描述

Java 后端启动时，控制台打印大量的数据库连接池报错信息，直接把终端缓冲区占满，导致最原始、最关键的启动报错信息被冲掉，无法看到真正的问题。

配置中使用了阿里巴巴 Druid 连接池：

```yaml
spring:
  datasource:
    url: ${LM_MYSQL_URL}
    username: ${LM_MYSQL_USER}
    password: ${LM_MYSQL_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
    type: com.alibaba.druid.pool.DruidDataSource
```

### 解决

取消自定义连接池，换成默认连接池后，报错信息大幅减少，才看清真正的问题：**数据库连接的 URL 缺少协议前缀 `jdbc:mysql://`**，环境变量中直接以 IP 开头。

### 教训

自定义连接池（如 Druid）在连接失败时会输出非常冗长的堆栈，可能冲掉真正的错误信息。排查启动报错时，可以先切回默认连接池定位根因，再切回自定义连接池。

## 4.4 MyBatis 事务管理缺失

### 问题描述

日志中出现两次：

```
Creating a new SqlSession
SqlSession [...] was not registered for synchronization because synchronization is not active
```

![事务日志截图 — 两次独立 SqlSession](https://gitee.com/Seniorsy/pic-go/raw/master/typora/image-20260504004346327.png)

### 根因

两次数据库操作（查询用户 + 获取角色）在独立的 SqlSession 中执行，没有纳入 Spring 事务管理。一个请求内本该是"查询用户 → 匹配密码 → 获取角色"的原子操作，被拆成了两个独立会话，无法保证一致性。

原因通常是 Service 方法或上层调用方法未添加 `@Transactional` 注解，或者数据源没有正确配置事务管理器。

### 解决方向

为 Service 层方法添加 `@Transactional` 注解，确保同一请求内的多次数据库操作共享同一个 SqlSession，由 Spring 统一管理事务。
