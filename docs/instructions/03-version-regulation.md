## 项目版本号规范



### 适用范围

本规范适用于项目中所有需要按版本组织的内容，重点包括：

- `docs/system-design` 下的版本目录
- 版本计划、功能设计、迭代说明等文档
- 需要对外标识版本的文档标签或发布标记



### 版本号格式

```
v<主版本号>.<次版本号>.<修订号>
```

- 前缀 `v` 表示版本标签，必须保留。
- 版本号的数字部分必须为非负整数，且不能写成 `01`、`002` 这类带前导零的形式。
- 版本号按照从左到右的优先级递增，先比较主版本号，再比较次版本号，最后比较修订号。
- 示例：`v0.1.0`、`v1.0.0`、`v1.2.3`、`v2.0.0`



### 目录版本约定

`docs/system-design` 目录按版本拆分，每个版本使用一个独立目录承载该版本的计划与设计内容。

- 目录名必须与版本号保持一致，例如 `v0.1.0`
- 一个版本目录只对应一个版本，不允许混放其他版本内容
- 版本目录按照迭代顺序递增，新的版本目录必须基于已有版本继续向后演进
- 草稿内容仅用于临时记录，不作为正式版本目录的替代



### 主版本号（Major）

当发生 **不向下兼容的变更** 或架构级重大调整时，主版本号增加。

- 主版本号变化后，次版本号和修订号必须归零
- 适用于功能范围、核心交互、数据结构或整体架构发生明显变化的场景



### 次版本号（Minor）

当发生 **向下兼容的功能性新增** 时，次版本号增加。

- 次版本号变化后，修订号必须归零
- 适用于新增模块、扩展能力、补充版本计划等场景



### 修订号（Patch）

当发生 **向下兼容的问题修正** 时，修订号增加。

- 适用于 Bug 修复、描述修正、性能优化、文档勘误等场景
- 不改变原有版本的功能边界和使用方式



### 编写要求

- 【强制】同一套内容只能对应一个版本号，禁止重复定义或跳号定义。
- 【强制】版本号一旦进入正式文档，就应视为历史记录，修改时优先新增新版本，而不是直接覆盖旧版本。
- 【推荐】如果版本内容较多，优先先写版本计划，再写具体功能设计，保持目录结构和执行顺序一致。
