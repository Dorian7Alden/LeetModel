

## HTTP 响应规范



### 响应码定义规范

> 定义原则：单一职责，一个状态码有且仅代表一个场景



状态码结构：采用**自定义 5 位业务响应状态码**编码规则（A-BB-CC）

| 字段代号 |   含义说明   | 详细编码规则                                                 | 示例                                                         |
| :------: | :----------: | ------------------------------------------------------------ | ------------------------------------------------------------ |
|    A     | 响应场景类型 | 2xxxx：成功响应<br />4xxxx：客户端错误 / 业务逻辑阻断<br />5xxxx：服务端错误 / 第三方服务异常 | 20000：成功响应<br />4xxxx：客户端xxx错误<br />5xxxx：系统繁忙，请稍后重试 |
|    BB    | 业务模块编号 | x00xx：全局通用；xnnxx：其余业务模块<br />编号一经使用不可随意变更<br />新增业务模块需同步更新文档说明 | x00xx：全局通用模块<br />x01xx：鉴权模块<br />x02xx：用户模块<br /> |
|    CC    | 业务场景序号 | 各业务模块**独立编号**<br />从 01 开始依次递增<br />同一模块内序号不允许重复 | 用户模块下：<br />01：用户未登录<br />02：账号或密码错误     |

- 【强制】一旦定义，不可随意修改

- 【强制】不暴露系统内部错误的具体原因，外部统一处理方式：`系统繁忙，请稍后重试` ，内部日志记录完整信息
- 【禁止】同一个状态码表达多个含义
- 【禁止】多个状态码表达完全相同的业务场景



### 代码层面的状态码定义规范



统一在后端通过 `ResponseCode` 枚举维护状态码，不允许在业务代码中硬编码魔法数字。

#### 1）定义位置与唯一来源

- 【强制】`ResponseCode` 必须包含 `code`、`msg` 两个字段。
- 【禁止】在 Controller / Service / Interceptor 中直接写 `40001`、`40103` 等裸数字。
- 【禁止】重复定义语义相同的错误码（例如多个 “用户不存在” 码）。

#### 2）命名与分组规则

- 【强制】枚举名使用全大写下划线命名，格式建议：`模块_场景_动作`。
- 【推荐】按模块分段编排并添加注释块，便于维护（如全局、用户、赛事、第三方服务）。
- 【强制】新增错误码时必须校验 A-BB-CC 三段编码是否满足上文规则。

参考示例：

```java
public enum ResponseCode {
	// ========== 全局通用（00） ==========
	GLOBAL_SYSTEM_INTERNAL_ERROR(50000, "服务器内部异常，请稍后重试"),
	GLOBAL_PARAM_VALIDATION_ERROR(40001, "参数校验不通过"),

	// ========== 用户模块（01） ==========
	USER_NOT_FOUND(40103, "用户不存在"),
	USER_LOGIN_FAIL(40104, "账号或密码错误");

	private final Integer code;
	private final String msg;
}
```

#### 3）兼容性与变更约束

- 【强制】已对外发布的状态码视为 API 契约，禁止随意修改或复用。
- 【强制】若业务语义发生变化，新增状态码替代旧码，旧码进入 “废弃但保留” 状态。



### HTTP 响应结构规范



后端统一响应体使用 `Result<T>`，所有 Controller 正常返回、业务异常、系统异常都必须落到同一 JSON 结构。

#### 1）统一结构

```json
{
	"code": 200,
	"msg": "success",
	"data": {},
	"timestamp": 1713523200000
}
```

#### 2）字段定义

|   字段名    |   类型   | 是否必填 |     含义     | 规则说明                                                     |
| :---------: | :------: | :------: | :----------: | :----------------------------------------------------------- |
|   `code`    |   int    |    是    |  业务状态码  | 成功默认 `200`；失败返回对应业务错误码（如 `40001`、`40103`、`50000`） |
|    `msg`    |  string  |    是    | 响应描述信息 | 成功默认 `success`，或由业务自定义成功提示；失败时返回可读错误信息 |
|   `data`    | T / null |    是    | 业务数据载荷 | 查询类接口返回对象/列表；无业务数据时返回 `null`             |
| `timestamp` |   long   |    是    |  响应时间戳  | 毫秒级 Unix 时间戳，按东八区时间生成                         |

#### 3）典型响应示例

成功（带数据）：

```json
{
	"code": 200,
	"msg": "成功通过用户 id 查询到用户",
	"data": {
		"id": 1,
		"username": "demo"
	},
	"timestamp": 1713523200000
}
```

成功（无数据）：

```json
{
	"code": 200,
	"msg": "已经成功删除用户 id 为 1 的用户",
	"data": null,
	"timestamp": 1713523200000
}
```

失败（业务异常）：

```json
{
	"code": 40103,
	"msg": "用户不存在",
	"data": null,
	"timestamp": 1713523200000
}
```

失败（系统异常对外兜底）：

```json
{
	"code": 50000,
	"msg": "服务器内部异常，请稍后重试",
	"data": null,
	"timestamp": 1713523200000
}
```

#### 4）落地约束

- 【强制】所有接口返回必须使用统一响应体，禁止直接返回裸对象、字符串或 Map。
- 【强制】业务可预期错误统一抛出业务异常，由全局异常处理器转换为标准响应结构。
- 【强制】系统异常不得向前端暴露堆栈、SQL、第三方调用细节等内部信息。
- 【推荐】前端统一以 `code` 作为业务判断依据，不以 `msg` 文案做分支判断。
