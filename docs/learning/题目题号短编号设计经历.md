# 题目题号短编号设计经历

> 创作日期：2026-08-27
> 适用场景：面试“项目经验 / 工程思考”素材；也可作为“展示标识与内部主键分离”的实践参考。

## 一句话经历

一个数学建模平台最初把内部雪花主键直接当作“题号”展示，页面上到处是 19 位的长数字，非常影响使用。我把题号改成了短顺序编号：对外展示用 `code`，内部保留雪花主键；并在这个过程中发现并解决了一个“逻辑删除行仍占用唯一题号”的隐蔽问题。

## 背景与问题

平台首页、题库详情、队伍卡片、队伍广场、创建队伍、提交历史等页面，都会显示“题号”。当初直接用数据库主键填充这个字段，主键是 MyBatis-Plus 默认的雪花算法生成的 19 位长整数。用户反馈非常直接：“题号这么长，影响使用。”

表面看这是“显示层用错了字段”，但深入一步会追问：能不能直接删除这个主键、换成自增整数？为什么当时会用雪花算法？

## 领域推理：题目量非常有限

在动手前先确认领域规模，这决定了方案方向：

- 数学建模题目的历史总量通常不会超过 10000 道。
- 每年全部赛事新增题目合计通常不超过 100 道。
- 年代久远的题目参考价值低，用户实际可练习的题目数量非常有限。

结论：题号不需要承担“海量数据”的容量假设，可以用短整数编号。规模判断不是拍脑袋，而是来自对该业务“题目供给有限、新题为主、旧题低价值”的理解。

## 方案取舍

### 备选一：直接把主键改成自增整数

优点是一劳永逸，所有引用主键的地方自动变短。

代价是：

- 主键是雪花 ID，被 team/submission/review/ranking/suggestion 等多个服务的表作为 `problem_id` 引用，改主键意味着多个数据库的存量数据都要重映射。
- 需要跨 5+ 个服务做协调迁移，风险高、收益集中在“显示长度”上。
- 主键的用途是“稳定标识 + 服务间引用”，它本来就不该被用户感知。

### 备选二：保留内部主键，新增对外题号

新增一个 `code` 字段作为“题号”，用户看到的是它；内部 `id` 只作为稳定标识、URL 参数和服务间引用，不再展示。

收益：

- 内部主键稳定，无需跨服务迁移数据，风险低。
- 主键与展示标识职责分离：内部引用更稳定，对外展示更友好。
- 未来如果题目规模真的扩大，可以单独调整 `code` 策略，不影响内部引用。

因此选择“内部雪花主键 + 对外短题号”的做法。

## 生成规则与约束

- `code` 为整数，唯一，从 `1001` 起始。
- 生成逻辑：`next = 现有最大 code + 1`，`next > 10000` 返回业务错误 `40409`（题号已达上限）。
- 客户端不可指定，用户创建题目时后端自动生成；更新不允许修改 `code`。
- 存量数据通过 Flyway 迁移按 `id` 升序回填 `1001..`，内部主键不变，因此不影响任何跨服务引用。

## 跨服务透传

题号要展示在队伍、提交等归属到题目的地方，不能只改题目服务：

- `problem-service`：`ProblemVO.code`
- 内部契约：`ProblemPracticeDTO.code`、`ProblemOptionDTO.code`
- `team-service`：`TeamVO.problemCode`
- `submission-service`：`SubmissionVO.problemCode`

这带来一个常见工程问题：一个“展示字段”一旦要跨服务展示，就会散落到多个服务的 DTO 里。需要权衡是“每处都带一个冗余展示字段”，还是“查询时再去取”。对 MVP，我选择在队伍/提交 VO 上冗余带上 `problemCode`（反正这些服务本来就要查题目的标题，多带一个字段成本很低），避免前端到处再发请求。

## 踩坑：逻辑删除行仍占用唯一题号

上线后一测就发现创建题目失败，报 `Duplicate entry '1012' for key 'problem.uk_problem_code'`。

排查：

- `code` 有唯一索引，且索引覆盖**所有行（含逻辑删除）**。
- 但生成题号的查询用的是 MyBatis-Plus 的 `@TableLogic` 查询，它自动追加 `deleted=0`，只统计了未删除行。
- 早先删除过两道题，它们被软删除（`deleted=1`，行仍在），占据了 `1012`、`1013` 两个题号。
- 于是“下一个题号”算出 `1012`，插入时和软删行冲突。

修复：

- 用一条绕过逻辑删除过滤的原始 SQL 取全局最大 `code`：`SELECT COALESCE(MAX(code), 1000) FROM problem`。
- 这样逻辑软删行仍占位时，新题会从更大的编号继续，不再冲突。

这个坑的核心是：**唯一约束的语义范围（全表含软删）与业务查询的语义范围（只看未删）不一致**。凡是“全局唯一 + 软删除”的组合，都容易出现这类问题，生成唯一值时必须对齐唯一约束的真实范围。

## 面试可讲的点

1. 从用户反馈定位到“展示字段选错”，而不是急于改主键。
2. 用领域规模（题目量有限）作为方案取舍依据，而不是写死“雪花算法 = 长 id = 照旧”。
3. 区分“稳定内部标识”与“用户展示标识”，让二者各司其职。
4. 跨服务展示字段的取舍：冗余带一个展示字段，避免前端到处查题。
5. 软删除与唯一索引的语义冲突，以及如何用原始 SQL 对齐生成逻辑。

## 反思与边界

- 这个改动只针对“题目题号”。队伍、提交等其他实体仍是雪花长 ID，因为它们的量会随用户增长，且用户没有对它们提出同样的问题。如果后续也遇到相同反馈，可以复用同样的“内部标识 + 对外短编号”思路。
- 短编号到 `10000` 上限是依据当前领域规模设定的“安全边界”，不是性能优化。未来若题目规模真的增长，需要重新评估，而不是盲目复用这个上限。
- 唯一性生成依赖“取最大 + 1”，在单实例下够用；若要支持多实例并发创建，应改为依赖数据库的唯一约束 + 冲突重试，或专门维护一个序列。
