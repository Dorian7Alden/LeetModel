# 02 代码工程实践

## 2.1 代码组织

### 异常处理高内聚

异常处理相关的代码全部高内聚，放在一个统一的文件夹中，而不是按文件类型分散存放。异常处理属于横切关注点，集中管理便于维护和查找。

### 自顶向下，文件不过大

保持自顶向下的代码组织思想。不要把所有内容堆在一个文件里，单个文件不能承载过多职责。文件过大说明职责不清，应当拆分。

### 保持全局属性干净

全局属性应当内聚，避免散落各处。

### 配置参数聚合

散落的配置参数（如 Redis 命名空间）不要分散使用，统一写进 properties 配置文件中，集中管理。

### 减少硬编码

尽量减少硬编码内容。例如：发送邮箱的模板不应硬编码在业务逻辑中，应当抽取为可配置的形式。

## 2.2 Controller 规范

Controller 层代码遵循统一范式：**校验参数 → 调用服务 → 返回结果**。这是 Controller 的全部职责，不做多余的事。

编写代码时同步检查异常兜底，确保每个分支都有合理的异常处理路径。

## 2.3 测试规范

测试代码每个模块必须分开，不能把不同模块的测试集合在一起测。保持测试的隔离性和独立性。

## 2.4 协作规范

### 注释与 TODO

- 写 TODO 时顺带写清楚验收标准，避免后续回顾时不知道"做到什么程度算完成"。
- 提取开发的全局观：代码注释和 TODO 是项目认知的沉淀，不是负担。

## 2.5 数据类型陷阱

### 实体类 ID 类型选择

实体类的 ID 直接用 `Integer` 类型，不要用 `int`。使用 `int` 在与 `long` 类型之间转换时容易出错，`Integer` 转 `long` 也更安全。

## 2.6 并发安全

### 自增 ID 的并发问题

以下用户注册代码存在并发 Bug：

```java
public void register(RegisterDTO request) {
    if (userMapper.getUserByEmail(request.getEmail()) != null) {
        throw new BusinessException(ResponseCode.USER_ALREADY_EXISTS);
    }

    User newUser = new User();
    newUser.setUserId((long) (userMapper.getMaxUserId() + 1));  // 并发问题
    ...
    userMapper.insertUser(newUser);
}
```

**问题**：`getMaxUserId() + 1` 的方式在高并发下会产生重复 ID。两个线程同时读到同一个最大值，生成相同的 ID。

**正确做法**：使用数据库自增主键（`AUTO_INCREMENT`）或分布式 ID 方案，不要在应用层手动计算 ID。
