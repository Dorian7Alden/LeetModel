# 05 系统分析经验

> 来源会话：2026-07-23 ~ 2026-07-24 系统分析阶段
> 产出文档：需求分析文档、微服务架构设计文档

---

## 5.1 系统分析的整体流程

系统分析不是一步到位，而是分阶段、有先后顺序的递进过程。每一阶段有明确的输入、输出和颗粒度边界。

### 阶段划分

1. 需求定义：原则、功能描述、范围界定、用例识别
2. 架构拆分：服务边界、职责、调用关系、关键决策
3. 功能详细设计：各个模块、各个用例的详细功能设计
4. 后续的工作

**阶段间的关系**：
- 后一阶段依赖前一阶段的输出，不跳跃
- 前一阶段不越界写后一阶段的内容
- 每一阶段产出独立的文档，作为下一阶段的输入

### 各阶段的内容组成

**需求定义**包括：
- 设计原则 —— 项目的决策过滤器，约束所有后续选择
- 功能描述 —— 粗略的用例级描述，不含实现细节
- 范围界定 —— 明确做什么、不做什么
- 用例识别 —— 参与者分类、用例清单、用例图（Mermaid 三区布局）

**架构设计**包括：
- 拆分原则 —— 指导服务边界划分的依据
- 功能→服务映射 —— 打通需求与架构的可追溯性
- 项目结构 —— 模块目录树
- 服务职责边界 —— 每个服务的端口、职责、对外接口、消息队列角色
- 服务间调用关系 —— 同步调用图、异步调用图、模块依赖图
- 关键设计决策 —— 每个决策的问题、方案、依据

**功能详细设计**（后续）包括：
- 接口契约（路径、请求/响应结构）
- 数据模型（表结构、字段、索引）
- 业务流程（状态机、时序）
- 异常处理策略

### 颗粒度边界

| 阶段 | 颗粒度 | 不该出现的内容 |
|------|--------|--------------|
| 需求定义 | 用例级，"用户能做什么" | 技术名词、实现方案、具体字段 |
| 架构设计 | 服务级，"服务如何划分和协作" | 具体产品名（MQ/KV/搜索引擎的品牌）、接口路径、表结构 |
| 功能详细设计 | 接口级，"这个功能的具体契约" | —（这一层允许具体） |

每一层的职责是独立的——描述需求的时候就专注描述需求，不要同时想着怎么实现；设计架构的时候就专注划分边界，不要跳到具体的接口定义。

## 5.2 需求文档的结构设计

### 设计原则先行——文档需要"宪法"

在描述任何功能之前，先建立一套决策过滤器。我在需求文档中把 5 条设计原则放在第一章，它们回答了"用什么样的心态来评判功能该不该做、做到什么程度"。

实践表明这个顺序很关键：原则确立后，所有后续内容——功能描述、范围取舍、用例提取——都带着约束条件被阅读和理解。如果把原则放在附录，读者（以及后续的 AI）会先读完功能描述，再回头对照——效果大打折扣。

**每条原则都直接塑造了下游决策：**

| 原则 | 直接后果 |
|------|---------|
| 聚焦核心链路 | 架构设计优先保障提交→评审→排行管道 |
| MVP 优先 | 每个功能只写 3-5 条规则，不展开 |
| 技术导向 | 改进建议（VIP）被保留——不是为了产品完备性，而是 RBAC 训练需要 |
| 按需取舍 | 催生了"本期不做"章节 |
| 描述有度 | 零实现细节，保证了需求与架构的分离 |

### "不做"清单与"做"清单同样重要

"本期不做"不是附录，而是放在功能需求和用例识别之间的"闸门"。这个位置有深意：读者看完"我们要做什么"之后，紧接着看到"我们明确不做什么"，防止在理解阶段就产生范围蔓延。

9 条明确排除项，每一项都有理由——不是逃避，是有意识的取舍：

- **团队协作系统**被排除，因为论文由用户线下完成，平台不提供在线协作
- **支付系统**被跳过，因为 VIP 是 RBAC 训练特性，不是实际付费功能
- **手机验证码**被跳过，因为认证本身不是学习目标

经验：**AI 辅助开发时，明确"不做"比"做"更能防止范围蔓延**。AI 会自然地想加"忘记密码""社交登录"等常见功能——没有排除清单，它就会主动提出甚至生成代码，浪费审查时间。

### 用例后置——先理解需求，再建模

传统 UML 教材先画用例图再写功能。我反过来：先用自然语言描述功能，再从中提取用例。这样做的原因：

1. **功能驱动，而非图表驱动**：自然语言描述让需求保持接地气。用例作为结构化索引提取出来，供下游使用
2. **避免过早抽象**：先画图的话，模型可能反过来塑造需求——"图里画了什么"而不是"用户需要什么"
3. **赋能下游文档**：架构文档的映射表直接引用 UC 编号（UC-01 ~ UC-10），这种可追溯性只有在用例 ID 来自已稳定的需求时才可靠

## 5.3 需求描述的颗粒度

### 功能≠用例，提交≠管理

在迭代中发现，最初只有"提交作品"一个条目，但它实际上包含了两个不同的用户操作：

- **提交作品（UC-05）**：选题后上传 PDF，是核心操作，引入系统状态
- **作品管理（UC-06）**：查看提交历史、评审状态、评审结果，是数据浏览和检索

它们共享同一个后端服务（`submission`），但用例层面分离是正确的——不同的用户目标、不同的交互模式。**如果两个操作有不同的用例简述、不同的参与者和不同的状态转换，它们就应该是独立的用例。**

### 未确定的内容不要写

评审维度"如创新性、模型合理性、论文规范等"——这些示例被删除了，因为具体的维度名称还没定。评审状态"待评审→评审中→已完成/失败"——也被删除了，因为状态枚举还没定。

经验：**不明确的细节不在需求阶段罗列**。写上去看似"全面"，实则埋下冲突——后续详细设计时可能完全不同。需求文档只说"多维度打分""状态可查询"，具体维度、状态值留给功能设计文档。

### 功能描述的三段式模板

每个功能统一为三个部分：**用例简述 + 规则 + 备注**，效果好：

- **用例简述**：一段话描述过程，保持粗略
- **规则**：陈述句，每条都可转化为测试用例（"队伍上限 3 人"→ 测试创建 4 人队伍是否失败）
- **备注**：可选，写启发式设计方向，不写实现方案

## 5.4 需求与架构的分离

### 两文档的分工

| | 需求分析文档 | 微服务架构设计文档 |
|---|---|---|
| 回答的问题 | 做什么 | 怎么做 |
| 语言 | 领域/用户语言 | 技术/服务语言 |
| 身份 | 被依赖方 | 依赖方 |
| 抽象层次 | 纯 WHAT | 逻辑架构层 |

关键约束：**需求文档不写实现细节，架构文档不写具体技术选型**。

实践中最容易犯规的点：在需求里写"JWT 登录""RBAC 权限""RocketMQ 消息队列"。这些统统应该去掉——JWT 是鉴权的实现手段，不是需求；RocketMQ 是消息队列的具体产品，不是架构。需求只写"用户登录后使用系统功能"，架构只写"通过消息队列解耦"。

### 从需求文档删除的实现细节

在本会话中逐步清理的：

- ~~Spring Security + JWT 鉴权~~ → 认证鉴权
- ~~ES 搜索~~ → 全文搜索
- ~~OpenFeign~~ → 同步调用 / 对外接口
- ~~RocketMQ~~ → 消息队列
- ~~Elasticsearch 向量检索~~ → 检索引擎
- ~~SSE 流式输出~~ → 流式输出
- 评审维度具体名称、状态枚举值等示例

## 5.5 微服务拆分的方法论

### 拆分原则先于拆分结果

在列出服务目录之前，先确立拆分原则。原则是拆分的依据——每一处服务边界都应该可以回溯到至少一条原则：

| 原则 | 对应的实际决策 |
|------|--------------|
| 单一业务能力 | submission 不含 AI 评分逻辑，评分是独立业务能力 |
| 数据主权独立 | review 不直接读 submission 的数据库，通过接口回写结果 |
| 异步优先 | submission → MQ → review → MQ → ranking 整条链路 |
| 复用与治理分层 | common-ai 提供客户端契约，AI 网关承担统一运行时治理 |
| 拆分可讲 | 每次拆分的理由要能清晰陈述，不凭感觉拆 |

### 上下文驱动拆分——没有普适的拆分方案

同样的功能集合，在不同的项目背景下会有不同的拆分结果。拆分之前必须明确前提：

- **项目目标是什么？** 学习实践 vs. 生产交付 vs. 快速原型——同样的功能，服务数量可能相差数倍
- **约束条件是什么？** 时间、人力、技术栈熟练度
- **取舍标准是什么？** 什么情况下倾向于拆，什么情况下倾向于合

以本项目的 `suggestion` 服务为例：如果是一个追求最小复杂度的生产项目，它完全应该合并进 `review`——一个端点区分是否返回建议即可。但本项目是技术实践项目，保留 `suggestion` 独立服务为 RBAC 权限体系的实践提供了清晰的载体。两个选择都合理，但前提不同。

**经验：拆分之前，先把上下文和原则写清楚。** 原则定了，具体拆分的争议就有了讨论的基准线——不是争论"拆不拆"，而是争论"在当前原则下该不该拆"。

### 架构文档的抽象层次

架构文档操作在**逻辑架构层**。它传达：有哪些服务、各自职责是什么、如何通信。不规定：用哪个 MQ 产品、哪个 RPC 框架、哪个搜索引擎。这些属于技术选型文档。

在本项目中逐步清理掉的实现细节：OpenFeign → 同步调用、RocketMQ → 消息队列、Elasticsearch → 检索引擎、SSE → 流式输出。架构图上只保留抽象的通信方式描述，具体产品名留给技术选型阶段。

## 5.6 用例图的规范

### 三区布局

Mermaid 用例图使用 `graph LR` + 三个 `subgraph` 实现标准的三列布局：

```
左（主要参与者） | 中（LeetModel 系统） | 右（次要参与者）
```

- **左侧**：人类角色，主动发起交互获得价值
- **右侧**：系统角色，由人类触发而非主动行动——AI 系统不注册、不登录、不做选择，它响应事件
- **中间**：用例放在以项目名命名的系统边界内

### 连线约定

- **实线** → 用户驱动的交互
- **虚线** `-.->` → 系统自动触发或系统间协作
- 用例间的虚线（UC04→UC07→UC09）捕捉异步管道——这不是用户操作而是系统行为

### 三张架构图的职责分离

架构文档中的三张 Mermaid 图各司其职，不合并：

| 图 | 展示的耦合类型 | 布局 |
|----|-------------|------|
| 同步调用 | 运行时同步耦合（请求-响应） | TD，网关为根 |
| 异步调用 | 运行时异步耦合（事件驱动） | LR，强调流程顺序 |
| AI 依赖 | 编译期耦合（jar 依赖） | TB，分层架构 |

合并成一张大图会混淆三种正交的耦合关系。分开画本身就是"单一职责"原则在文档层的应用。

## 5.7 AI 协作的经验

### Plan 模式用于文档迭代

整个系统分析阶段，每一次对文档的修改都先写 plan、经我确认后再执行。这避免了 AI "自己觉得对就改了"的问题——文档设计是主观的，AI 的判断不一定符合设计者意图。

### 一次只做一件事

需求文档和架构文档的迭代是一步一步来的：先定技术选型，再拆服务，再写需求，再画用例图，再清理实现细节，再补充遗漏的用例……每次会话只聚焦一个方面，不并行推进。

### 抽象层次需要持续维护

AI 天然倾向于写具体的东西——具体的技术名词、具体的示例值、具体的实现方案。维护文档的抽象层次需要**反复纠正**：

- "这里不要写 JWT，写认证鉴权就行"
- "ES 搜索改成全文搜索"
- "RocketMQ 改成消息队列"
- "评审维度示例删掉，还没定"

这不是一次性清理完成的，而是在多次迭代中逐步发现的。经验：在每次文档调整后，都应该做一次"实现细节扫描"。

### 文档引用方向要正确

架构设计文档会参考需求文档，但反过来不行。被依赖方不需要知道谁依赖了它。这避免了循环引用和维护两个方向的关联。
