# 03 项目架构决策

## 3.1 决策方法论

### 架构评估：先理解，再评判

分析代码架构是否合理时，先分析当前的做法有没有它的道理。如果有道理就不改，没道理才改。也就是说，所有的决策冲突都应该有依据地进行抉择——A 可 B 也可的时候，必须给出抉择的原因，防止下次重复试错或随意更改。

核心原则：**每个架构决策都要有明确的依据，不能凭感觉选。**

## 3.2 RBAC 资源管控策略

### 按需管控，不是全部管控

并不是所有资源都需要添加权限码来管控，那样只会增加不必要的复杂度。RBAC 管控的是需要保护的资源，公共的、静态的资源不需要权限保护。

具体原则：

1. **绝对不要试图把所有资源都纳入 RBAC 管控。**
2. 确立公共资源白名单，明确哪些路径免鉴权，由拦截器直接放行。
3. 只对真正有访问控制需求的功能定义权限，采用"菜单级为主、操作级按需"的粒度。
4. 保持认证和授权分离——很多需要登录但不需要区分角色的功能，使用 `permitAll` 即可。
5. 对于"需要管但不能阻拦"的需求（如限流、日志），用中间件独立处理，不要变成权限码。

**口诀：按需管控，公共放行，粗粒度别心疼，细粒度看场景。** 这样 RBAC 才能清晰、高效且不臃肿，真正做到"管住该管的，放掉该放的"。

## 3.3 不使用全局 common-beans

### 决策结论

微服务项目不建立存放全部 Bean 对象的公共模块。公共模块只维护稳定的跨服务契约，数据库实体和服务内部接口对象留在各自的业务服务。

### 集中管理的短期收益

把 Entity、Request、Response、DTO 全部放入 `common-beans`，可以减少类放置位置的判断，也能避免多个模块重复声明相似结构。项目规模较小时，这种方式看起来直接且易于使用。

### 长期代价

所有微服务共同依赖同一个模型模块后，一个服务的模型变化可能迫使无关服务重新编译和发布。服务虽然独立运行，模型和发布节奏却被绑定，最终容易形成分布式单体。

共享数据库实体还会暴露数据表结构和敏感字段。其他服务可能直接依赖不属于自己的字段，甚至绕过服务接口访问数据库，破坏数据所有权边界。

全局模型模块也会逐渐成为公共垃圾桶。类的数量不断增加，但缺少明确的业务所有者，删除、改名和字段调整都需要评估全部服务，维护成本高于最初节省的判断成本。

### 放置规则

对象位置由数据所有权和调用边界决定：

| 对象 | 放置位置 | 判断依据 |
|------|---------|---------|
| Entity | 数据表所属的业务服务 | 只由数据所有者维护 |
| 本地 Request | 接收请求的业务服务 | 只服务于当前 HTTP 接口 |
| 本地 Response | 返回数据的业务服务 | 只服务于当前 HTTP 接口 |
| 跨服务 DTO | common-api | 同时被服务提供方和调用方依赖 |
| Feign Client | common-api | 属于跨服务调用契约 |
| 通用基础对象 | common-core | 与具体业务无关 |

### 执行方法

新增对象时只回答三个问题：

1. 是否映射数据库表。答案为是时放入数据所有者服务。
2. 是否只有当前服务使用。答案为是时放入当前服务。
3. 是否已经跨越微服务边界。答案为是时放入 `common-api`。

不要因为未来可能复用就提前公共化。真正出现第二个服务消费者时，再把稳定的传输契约提取到 `common-api`。

### 面试表达

项目没有建立全局 `common-beans`，因为共享所有模型会泄漏数据库结构并造成服务间编译耦合。项目只共享稳定的跨服务契约，Entity 和本地接口模型由业务服务自行维护，从依赖层面保护微服务边界。
