# API 网关概念


> 面试导向：用通俗类比解释网关，再展开技术细节。


## 一、网关是什么

API Gateway 是微服务架构中的**统一入口**。类比：办公楼的前台/门禁——外部访客只需要知道前台在哪（8080 端口），由前台根据来访目的（请求路径）引导到对应的部门（微服务）。没有前台的话，访客得自己记住每个部门的楼层和房间号。


## 二、核心职责

| 职责 | 说明 | 面试关联 |
|------|------|---------|
| **路由转发** | 根据请求路径匹配规则，转发到对应微服务 | 问"怎么实现路由"→ 答 Predicate 匹配 + `lb://service-name` 从注册中心发现实例 |
| **统一鉴权** | 在网关层校验 JWT Token，非法请求直接挡在门外 | 问"为什么不在每个服务单独鉴权"→ 减少重复代码、安全纵深防御 |
| **跨域处理** | 统一配置 CORS，业务服务无需各自处理 | 问"跨域怎么解决"→ Gateway 全局 `CorsWebFilter` |
| **负载均衡** | 结合 Nacos，自动在多实例间分发请求 | 问"负载均衡怎么做"→ `lb://` + Spring Cloud LoadBalancer |
| **限流熔断** | 控制请求流量，保护下游服务（Sentinel） | 本项目 MVP 阶段暂未接入，可说明后续扩展方案 |


## 三、一次请求的完整流程

```
前端 → Gateway(8080) → 路径匹配 → 鉴权校验 → Nacos 查服务实例 → 转发到业务服务
```

无鉴权请求（如登录）：Gateway 命中白名单路径，跳过 Token 校验，直接转发到 user 服务。

需鉴权请求（如查用户信息）：Gateway 解析请求头中的 JWT，校验签名和过期时间。有效则放行，无效则返回 401 不转发到后端。


## 四、Spring Cloud Gateway vs Zuul

| 维度 | Spring Cloud Gateway | Netflix Zuul |
|------|---------------------|-------------|
| 底层 | Netty + WebFlux（非阻塞 I/O） | Servlet 2.5（阻塞 I/O） |
| 性能 | 高并发下显著优于 Zuul | 线程池模型，线程数是瓶颈 |
| Spring 生态 | 官方推荐，与 Spring Cloud 深度集成 | 已进入维护模式 |

如果面试被问到"为什么选 Gateway"，回答：Spring 官方推荐、非阻塞 I/O 性能好、与 Nacos/Spring Cloud 无缝集成。
