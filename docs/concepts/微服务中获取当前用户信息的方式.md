# 微服务中获取当前用户信息的方式

> 日期：2026-08-22
> 相关模块：user-service、common-security

---

## 问题

开发 User 微服务时，获取当前用户的个人信息通常是怎么实现的？为什么不能直接让前端在接口里传 userId 参数？为什么需要 /me 接口和 UserContext？

## 结论

当前用户是谁，必须由服务端从认证信息里识别，不能由客户端通过参数告诉服务端。因此普通用户查询个人信息使用 /me 接口，服务端从 Token 中解析用户 ID，而不是接收外部传入的 userId。

## 为什么不能直接传 userId 参数

假设接口设计成：

```text
GET /api/users/{userId}
```

前端登录后把自己的 userId 传过来，这存在三个问题。

### 越权漏洞

用户 A 登录后拿到自己的 userId=1，只要把请求改成：

```text
GET /api/users/2
```

就能看到用户 B 的个人信息。后端无法区分这个请求是用户 A 在查自己，还是用户 A 在查别人。这种漏洞称为 IDOR，即不安全的直接对象引用。

### 客户端参数不可信

请求里的任何参数都属于用户输入。用户输入只能表达用户想要什么资源，不能表达用户是谁。身份必须来自服务端可控的凭证，也就是登录时签发的 Token。

### 服务端早已知道用户是谁

用户登录成功后，后端签发的 JWT 载荷里就带有 userId。用户再传一次 userId 是多余且不安全的。

## /me 接口的实现方式

接口变成：

```text
GET /api/users/me
```

路径里没有任何用户标识，处理流程为：

```text
请求头携带 Token
    ↓
Sa-Token 解析 Token，拿到 userId
    ↓
UserContext.getUserId()
    ↓
用 userId 去数据库查个人信息
```

对应项目中的代码：

```java
@GetMapping("/me")
public Result<UserVO> profile() {
    Long userId = UserContext.getUserId();
    UserVO vo = userService.getProfile(userId);
    return Result.ok(vo);
}
```

这样用户无论怎么改 URL，查到的都只能是自己，因为后端根本不接受外部传入的 userId。

## UserContext 与 common-security 的作用

### UserContext

UserContext 是对 Sa-Token 的封装，核心方法是：

```java
public static Long getUserId() {
    return StpUtil.getLoginIdAsLong();
}
```

它从当前请求上下文解析 Token 并返回登录用户 ID。业务代码依赖 UserContext 而不是直接依赖 StpUtil，以后更换认证框架时业务代码无需改动。

### common-security

在微服务架构中，user-service 只是其中一个服务。team-service 建团队时需要知道当前登录用户是谁，problem-service 判权限时也需要。每个服务都写一遍从 Token 解析用户 ID 的逻辑不现实。common-security 把 Sa-Token 配置、UserContext、TokenUtil、鉴权异常处理、权限注解支持统一沉淀为公共模块，各服务直接依赖即可。

## 什么时候才用按 ID 查询的接口

服务端内部调用或管理员调用时才使用带 userId 或 id 的接口，项目中有两类：

```text
GET /api/admin/users/{id}
GET /internal/users/{userId}/roles
```

这两类接口的共同点：

1. 调用方不是普通用户，管理员接口有 @SaCheckRole("admin") 校验。
2. 内部接口只通过 Feign 在服务间调用，不对客户端开放。

因此接口设计遵循：

- /api/users/me：给普通用户查自己，身份来自 Token。
- /api/admin/users/{id}：给管理员查任意用户，身份由管理员权限控制。
- /internal/users/{userId}/roles：给微服务间调用，不是给客户端使用。

## 面试可讲点

> "用户身份必须来自 Token，不能来自请求参数，否则就是 IDOR 越权漏洞。/me 接口是 REST 风格的当前用户资源，服务端从认证上下文解析用户 ID。微服务通过公共安全模块统一提供 UserContext 等能力，避免每个服务重复实现鉴权逻辑。需要按 ID 查任意用户时，必须走管理员接口并做权限校验，而不是让普通用户传 userId。"
