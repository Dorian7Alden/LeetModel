## 真实V3评审与建议链路多阶段失败

### 报错现象

使用完整 2025 MCM A 题面与匹配的 25 页论文 PDF 运行“提交 → V3 评审 → V3 建议”时，依次出现以下现象：

1. `DEEP_EVIDENCE_REVIEW_V3` 在结构审查阶段返回“请求与模型执行配置不一致”。
2. 建议任务创建成功，但 Outbox 长期停在 `PENDING`，领域任务停在 `WAITING`。
3. Outbox 恢复发布后，RocketMQ 消费端在业务解码前抛出 `ClassCastException`。
4. 模型调用实际在网关内成功，但调用方约 30 秒收到 50001，子任务被错误降级。
5. 建议汇总返回类别 `ALGORITHM`，服务端按已发布枚举校验时拒绝结果。


### 根因分析

#### V3 复用了 V2 模型执行配置

V3 评审和建议仍引用 V2 的执行配置版本，而 V2 配置只允许自身的 workflow 与 Prompt 版本。部分调用的 Token 与温度也和配置快照不一致，因此网关按不可变执行契约正确拒绝。

#### 可靠消息自动配置发生静默缺失

`common-messaging` 在同一自动配置链中使用方法级 `@ConditionalOnBean` 判断 `RocketMQTemplate` 和 `MessagePublisher`。条件评估早于相关 Bean 完成注册，最终进程只有 JDBC Outbox，没有发布器和 Relay。服务仍能启动，导致问题表现为永久 `PENDING`。

#### 注解监听器的泛型与框架转换边界不一致

领域消费者声明为 `RocketMQListener<byte[]>`。RocketMQ Spring 在无法从实际代理类型解析目标泛型时按 `Object` 处理，并把 Broker Body 转为字符串；编译器生成的桥接方法随后把字符串强转为 `byte[]`，在业务方法执行前失败。

#### Servlet 异步超时短于业务等待上限

AI 网关的 `CompletableFuture` 最长等待 120 秒，但 Spring MVC 沿用约 30 秒默认异步请求超时。模型任务没有取消，仍在后台成功并持久化；HTTP 层却先以 `AsyncRequestTimeoutException` 结束，调用方只能看到系统内部错误。

#### 模型同义类别未收敛

已发布建议 Schema 使用 `SOLUTION` 表示算法与求解，但模型偶发返回语义相同的 `ALGORITHM`。输出规范化只处理空值，没有在强校验前收敛该稳定同义词。


### 修复方案

1. 新增 `MODEL_CFG_REVIEW_TEXT_0003` 与 `MODEL_CFG_SUGGESTION_TEXT_0003`，分别绑定 V3 workflow、Prompt、Token、温度与真实模型；V1/V2 配置不变。
2. 可靠消息发布器改为依赖注入 `RocketMQTemplate` 创建，Relay 直接依赖 `MessagePublisher`；Relay 开启却没有传输能力时启动失败。
3. 所有注解式领域消费者统一声明 `RocketMQListener<String>`，通过 UTF-8 文本解码公共信封；低层 Broker 测试显式把 `MessageExt.body` 转为 UTF-8 字符串。
4. 设置 `spring.mvc.async.request-timeout=130s`，覆盖 120 秒业务等待窗口与响应收尾开销。
5. 在 V3 建议规范化阶段将 `ALGORITHM` 映射为已发布枚举 `SOLUTION`；未知类别仍由强校验拒绝。


### 验证结果

- `DEEP_EVIDENCE_REVIEW_V3` 完成，五维训练评分合计 45.0/100，三个分项任务成功，13 个证据锚点页码均在论文范围内。
- `GROUNDED_SUGGESTION_V3` 完成，7 个子任务成功，5 条建议均具备修改动作、验收条件和三类依据链。
- 第一次建议调用在 HTTP 超时后，网关仍保存了原子任务成功结果；修复后使用同一业务幂等键重试直接取得既有终态，未重复创建上游调用。
- 公共消息自动配置、UTF-8 消费边界、V3 执行配置与结果规范化均有定向测试覆盖。
