## Git 分支与提交规范

### 目标

Git 历史必须能够回答三个问题：当前分支为什么存在、每个提交改变了什么、分支合回 `dev` 时完成了什么目标。

项目采用“一个阶段、一条分支；一张任务卡、一个或多个原子提交；阶段完成、一次目标合并”的工作方式。分支负责隔离阶段目标，提交负责保留任务卡边界，合并提交负责概括整个阶段的最终交付。

Agent 按本规范完成本地任务流程时，可以自主创建和切换阶段分支、为已验收任务卡创建原子提交、将已验收阶段合入 `dev`，并删除已经确认合并的本地阶段分支，不要求用户逐次授权。远端写入、历史改写和破坏性操作仍受本文禁止事项约束。


### 分支原则

1. 【强制】每个分支只服务 `TODO.md` 中一个明确阶段。
   说明：阶段内可以包含多张任务卡，但必须按依赖串行推进、分别验收和原子提交，不得混入其他阶段工作。
2. 【强制】所有阶段分支都只能从 `dev` 创建，不得从 `master` 或其他开发分支创建。
3. 【强制】当前阶段全部任务卡完成并合回 `dev` 后，才能为下一阶段创建新分支。
4. 【强制】不把顺手发现但不阻断当前闭环的问题放进当前分支，应先记录为后续候选任务。
5. 【强制】分支名称必须表达单一、可完成、可验收的目标，不使用 `all`、`misc`、`rebuild`、`optimize-project` 等宽泛名称。
6. 【推荐】分支生命周期不超过一个路线图阶段。任务暂停时在 `TODO.md` 记录状态，不让分支代替任务管理。


### 长期分支模型

项目由独立开发者维护，只保留两个长期分支：

| 分支 | 定位 | 生命周期 |
|------|------|----------|
| `dev` | 唯一开发主线，承接全部已验收阶段分支 | 长期存在，不删除 |
| `master` | 稳定发布主线，只保存具有重大更新或明确版本价值的内容 | 长期存在，不删除 |

强制规则：

1. 所有日常开发都以 `dev` 为唯一基线，阶段分支只能从 `dev` 创建并且只能先合回 `dev`。
2. `master` 不作为任何开发分支的起点，不直接承接阶段分支。
3. 普通任务完成后只合入 `dev`，不会因为单项任务完成就同步 `master`。
4. 只有形成重大更新、阶段性稳定成果或明确版本发布价值时，才由用户决定将 `dev` 合入 `master` 并更新版本。
5. 正常状态下，`dev` 与 `master` 要么指向相同发布基线，要么 `dev` 包含尚未发布的新进度。不得出现只存在于 `master`、尚未同步回 `dev` 的开发提交。
6. 发布操作在 `master` 产生合并提交或版本提交后，必须立即把该发布基线同步回 `dev`，使两个长期分支重新保持一致，再继续下一轮开发。


### 分支命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 阶段开发 | `phase/<阶段>-<目标>` | `phase/s1-new-api-chat` |
| 阶段修复 | `fix-phase/<阶段>-<目标>` | `fix-phase/s3-ai-scheduling` |

分支名描述阶段及其目标，不描述日期；运行环境要求固定前缀时，可以在上述名称前增加该前缀。


### 分支创建

创建分支前必须确认工作基线和任务卡：

```bash
git switch dev
git status
git switch -c phase/<阶段>-<目标>
```

- 切换前确认当前分支没有尚未归属的修改。
- 需要同步远端时，先由用户授权对应网络和 Git 写操作。
- 工作区已有修改时，必须先确认这些修改属于即将创建的阶段分支；不得用切分支掩盖来源不明的改动。
- 即使 `master` 看起来更新，也不得从 `master` 创建开发分支；应先按发布同步规则使 `dev` 获得相同基线，再从 `dev` 创建阶段分支。


### 原子提交分组

同一阶段包含多张任务卡；每张任务卡可以包含多个提交，但不同类型内容必须分开提交，提交信息与暂存范围必须能够识别所属任务卡。

| 分组 | 识别规则 | 常用 scope |
|------|----------|------------|
| 后端代码 | `LeetModel-backend/` 下 Java、XML 等实现文件 | `back` 或具体服务 |
| 前端代码 | `LeetModel-frontend/src/` 下 Vue、JavaScript、CSS、TypeScript | `front` |
| SQL | Flyway SQL 和其他数据库脚本 | `sql` |
| 配置 | Compose、POM、`application*.yml`、构建配置和环境变量示例 | `config` |
| 文档 | `docs/`、README 和其他 Markdown 文件 | `ai`、具体模块或省略 |

强制要求：

- 代码、配置和文档分别提交。
- 前端代码和后端代码分别提交。
- 不同功能、缺陷或重构意图分别提交。
- 新文件与所属类型的修改一起提交。
- 不为减少提交数量混合无关内容。


### 普通提交格式

普通提交统一使用：

```text
type(scope): 中文描述
```

| type | 含义 | 适用场景 |
|------|------|----------|
| `feat` | 新增功能 | 新增模块、接口、页面、配置能力 |
| `fix` | 缺陷修复 | 修复异常、错误行为或兼容性问题 |
| `ref` | 重构优化 | 不改变功能目标的结构调整 |
| `docs` | 文档更新 | 设计、说明和规范调整 |
| `file` | 文件变更 | 文件移动、重命名、删除和整理 |
| `release` | 发布版本 | 版本发布和里程碑标记 |

规则：

1. 【强制】subject 使用中文，一行概括本次提交的单一意图。
2. 【强制】scope 使用简短模块名，不拼接大量模块。
3. 【推荐】subject 控制在 20 个中文字符以内。
4. 【推荐】功能、修复和重构提交使用明确 scope；无单一模块的文档提交可以省略 scope。
5. 【强制】不使用 `--no-verify`、`--no-gpg-sign` 等参数绕过仓库检查。
6. 【强制】不提交 `.env`、密钥、凭证或包含真实密码的文件。

示例：

```text
feat(config): 集成new-api本地服务
fix(user): 修复登录令牌刷新失败
ref(review): 拆分评审任务调度逻辑
docs(ai): 调整稳定性评价设计
file(docs): 重命名评价文档目录
release(version): 发布v2.1.0
```


### 提交前检查

每次提交前依次执行：

1. 使用 `git status --short` 确认变更范围。
2. 使用 `git diff` 检查未暂存修改。
3. 按代码、配置、文档和任务意图选择性暂存。
4. 使用 `git diff --cached --check` 检查格式问题。
5. 使用 `git diff --cached` 或统计信息确认暂存内容只有一个提交意图。
6. 执行与风险相称的测试或配置校验。
7. 按普通提交格式创建提交，不跳过钩子。


### 阶段合并回 dev

阶段内全部任务卡满足完成定义后，使用非快进合并将阶段分支合回 `dev`：

```bash
git switch dev
git merge --no-ff phase/<阶段>-<目标> -m "merge: 完成<阶段核心目标>"
```

合并提交是普通 `type(scope): 中文描述` 格式的唯一例外，固定使用：

```text
merge: 完成<阶段核心目标>
```

示例：

```text
merge: 完成new-api第三方网关集成
merge: 完成用户登录令牌刷新修复
merge: 完成AI评审稳定性评价调整
```

合并规则：

1. 【强制】合并消息描述整个阶段的核心目标，不罗列内部任务卡，不使用“合并代码”“完成开发”等空泛表述。
2. 【强制】使用 `--no-ff` 保留阶段分支边界和目标合并节点。
3. 【强制】合并前确认阶段内全部任务卡完成、相关测试通过、文档与实现一致且工作区干净。
4. 【强制】功能分支不得直接合入 `master`。发布流程再按版本规范将 `dev` 的已验收内容合入发布分支或 `master`。
5. 【强制】合并并确认无误后立即删除本地阶段分支。删除前必须使用 `git branch --merged dev` 确认分支已经完整合入 `dev`，再执行 `git branch -d <阶段分支>`；不得使用 `-D` 强制删除未合并分支。


### 从 dev 发布到 master

`dev` 积累的成果只有达到重大更新或版本发布条件时才进入 `master`。发布由用户明确决定，不随普通任务自动执行。

推荐流程：

```bash
git switch master
git merge --no-ff dev -m "merge: 发布vX.Y.Z"
git tag vX.Y.Z
git switch dev
git merge --ff-only master
```

发布规则：

1. 【强制】发布前确认 `dev` 中准备发布的任务均已验收，版本号和发布文档已按版本规范处理。
2. 【强制】只能将 `dev` 合入 `master`，不得绕过 `dev` 把阶段分支直接合入 `master`。
3. 【强制】`master` 的发布合并消息使用 `merge: 发布vX.Y.Z`，并按版本规范创建对应标签。
4. 【强制】发布后立即将 `master` 快进同步回 `dev`。同步完成后两条长期分支处于相同基线，后续任务继续从 `dev` 创建。
5. 【强制】`dev` 和 `master` 都是长期分支，不因一次发布、回滚或阶段结束而删除。


### 禁止事项

- 在一个阶段分支中混入其他阶段或路线图外任务。
- 为了省事直接在 `dev` 或 `master` 修改并提交。
- 从 `master` 或尚未合并的阶段分支继续切出新的开发分支。
- 把未验证的半成品合回 `dev`。
- 使用模糊的提交消息，例如 `update`、`fix`、`修改代码`、`完成开发`。
- 通过强制重置、覆盖式切换或删除未确认分支来处理冲突。
- 未经用户授权执行 push、rebase、force push、删除远端分支或其他远端写操作。
