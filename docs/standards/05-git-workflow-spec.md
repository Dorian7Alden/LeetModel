## Git 分支与提交规范

### 目标

Git 历史必须能够回答三个问题：当前分支为什么存在、每个提交改变了什么、分支合回 `dev` 时完成了什么目标。

项目采用“一项任务、一条分支、多个原子提交、一次目标合并”的工作方式。分支负责隔离任务目标，提交负责拆分实现步骤，合并提交负责概括整条分支的最终交付。


### 分支原则

1. 【强制】每个分支只服务 `TODO.md` 中一张已经确认的任务卡。
   说明：分支内所有代码、配置、测试和文档都必须直接服务同一个核心目标。
2. 【强制】所有任务分支都从 `dev` 创建，不直接在 `dev` 或 `master` 开发。
3. 【强制】当前任务完成并合回 `dev` 后，才能为下一个任务创建新分支。
4. 【强制】不把顺手发现但不阻断当前闭环的问题放进当前分支，应先记录为后续候选任务。
5. 【强制】分支名称必须表达单一、可完成、可验收的目标，不使用 `all`、`misc`、`rebuild`、`optimize-project` 等宽泛名称。
6. 【推荐】分支保持短生命周期。任务暂停时在 `TODO.md` 记录状态，不让分支代替任务管理。


### 分支命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能开发 | `feat/<模块>-<闭环>` | `feat/ai-new-api-integration` |
| 缺陷修复 | `fix/<模块>-<问题>` | `fix/user-token-refresh` |
| 局部重构 | `ref/<模块>-<目标>` | `ref/review-task-scheduler` |
| 文档维护 | `docs/<目标>` | `docs/git-branch-workflow` |

功能分支使用 `feat/`，不得使用工具或开发者名称作为前缀。分支名描述任务目标，不描述执行者、日期或所用工具。


### 分支创建

创建分支前必须确认工作基线和任务卡：

```bash
git switch dev
git status
git switch -c feat/<模块>-<闭环>
```

- 切换前确认当前分支没有尚未归属的修改。
- 需要同步远端时，先由用户授权对应网络和 Git 写操作。
- 工作区已有修改时，必须先确认这些修改属于即将创建的任务分支；不得用切分支掩盖来源不明的改动。


### 原子提交分组

同一任务可以包含多个提交，但不同类型内容必须分开提交。

| 分组 | 识别规则 | 常用 scope |
|------|----------|------------|
| 后端代码 | `LeetModel-backend/` 下 Java、XML 等实现文件 | `back` 或具体服务 |
| 前端代码 | `LeetModel-frontend/src/` 下 Vue、JavaScript、CSS、TypeScript | `front` |
| SQL | Flyway SQL 和其他数据库脚本 | `sql` |
| 配置 | Compose、POM、`application*.yml`、构建配置和环境变量示例 | `config` |
| 文档 | `docs/`、README 和其他 Markdown 文件 | `ai`、具体模块或省略 |

强制要求：

- 代码、配置和文档分别提交。
- 前端代码和后端代码分别提交。
- 不同功能、缺陷或重构意图分别提交。
- 新文件与所属类型的修改一起提交。
- 不为减少提交数量混合无关内容。


### 普通提交格式

普通提交统一使用：

```text
type(scope): 中文描述
```

| type | 含义 | 适用场景 |
|------|------|----------|
| `feat` | 新增功能 | 新增模块、接口、页面、配置能力 |
| `fix` | 缺陷修复 | 修复异常、错误行为或兼容性问题 |
| `ref` | 重构优化 | 不改变功能目标的结构调整 |
| `docs` | 文档更新 | 设计、说明和规范调整 |
| `file` | 文件变更 | 文件移动、重命名、删除和整理 |
| `release` | 发布版本 | 版本发布和里程碑标记 |

规则：

1. 【强制】subject 使用中文，一行概括本次提交的单一意图。
2. 【强制】scope 使用简短模块名，不拼接大量模块。
3. 【推荐】subject 控制在 20 个中文字符以内。
4. 【推荐】功能、修复和重构提交使用明确 scope；无单一模块的文档提交可以省略 scope。
5. 【强制】不使用 `--no-verify`、`--no-gpg-sign` 等参数绕过仓库检查。
6. 【强制】不提交 `.env`、密钥、凭证或包含真实密码的文件。

示例：

```text
feat(config): 集成new-api本地服务
fix(user): 修复登录令牌刷新失败
ref(review): 拆分评审任务调度逻辑
docs(ai): 调整稳定性评价设计
file(docs): 重命名评价文档目录
release(version): 发布v2.1.0
```


### 提交前检查

每次提交前依次执行：

1. 使用 `git status --short` 确认变更范围。
2. 使用 `git diff` 检查未暂存修改。
3. 按代码、配置、文档和任务意图选择性暂存。
4. 使用 `git diff --cached --check` 检查格式问题。
5. 使用 `git diff --cached` 或统计信息确认暂存内容只有一个提交意图。
6. 执行与风险相称的测试或配置校验。
7. 按普通提交格式创建提交，不跳过钩子。


### 合并回 dev

任务满足完成定义后，使用非快进合并将分支合回 `dev`：

```bash
git switch dev
git merge --no-ff feat/<模块>-<闭环> -m "merge: 完成<分支核心目标>"
```

合并提交是普通 `type(scope): 中文描述` 格式的唯一例外，固定使用：

```text
merge: 完成<分支核心目标>
```

示例：

```text
merge: 完成new-api第三方网关集成
merge: 完成用户登录令牌刷新修复
merge: 完成AI评审稳定性评价调整
```

合并规则：

1. 【强制】合并消息描述整条分支的核心目标，不罗列内部提交，不使用“合并代码”“完成开发”等空泛表述。
2. 【强制】使用 `--no-ff` 保留任务分支边界和目标合并节点。
3. 【强制】合并前确认任务卡完成、相关测试通过、文档与实现一致且工作区干净。
4. 【强制】功能分支不得直接合入 `master`。发布流程再按版本规范将 `dev` 的已验收内容合入发布分支或 `master`。
5. 【推荐】合并并确认无误后删除本地任务分支，避免已完成分支长期堆积。


### 禁止事项

- 在一个分支中连续完成多个互不依赖的任务。
- 为了省事直接在 `dev` 或 `master` 修改并提交。
- 使用工具名、Agent 名或开发者名作为分支前缀。
- 把未验证的半成品合回 `dev`。
- 使用模糊的提交消息，例如 `update`、`fix`、`修改代码`、`完成开发`。
- 通过强制重置、覆盖式切换或删除未确认分支来处理冲突。
- 未经用户授权执行 push、rebase、force push、删除远端分支或其他远端写操作。
