## 文档撰写规范



### 文件与标题



1. 【强制】所有文档撰写均用 markdown 文件

    - 说明：统一文档格式标准，轻量高效，便于 AI 读取，便于管理。

2. 【强制】文档中应该有文档名字

    - 说明：每个文档中都应该给出文件的名字，而不是只有文档的内容

3. 【推荐】文档名设置为 2 级标题

    - 说明：一般情况下，文档标题设置为 2 级（##）。仅仓库根目录下的 README.md 文件的文档标题可以设置为 1 级，突出强调的作用。

4. 【强制】非项目根目录的 md 文档标题等级以 3 级标题开始

    - 说明：标题等级从 3 级标题开始，字体不会太大，也不会太小，便于迁移文档时升级标题等级，降级标题等级。

    - 正例：

   ```markdown
   ## doc-name
   ```



### Title 1



#### Subtitle



content



#### Subtitle



content



### Title 2



content

...

   ```


### 排版与间距



1. 【强制】标题元素的上下文应该用 1 个空行隔开

   - 说明：标题元素上下文使用 1 个空行隔开，使得内容排版更加清晰，防止标题大量堆叠

   - 正例：

   ```markdown

   ### Title 1


   content

   content


   ### Title 2


   ### Title 3

   ```

2. 【强制】禁用行末添加两个空格 + 回车表示换行

    - 说明：为了统一规范，以及优雅地编辑源码，禁止通过在行末使用两个空格加上回车（1 个换行符）的形式达到在渲染模式下的换行

    - 反例：

   ```markdown
   line1  
   line2
   
   ```

    - 正例：

   ```markdown
   line1
   
   line2
   
   ```

3. 【强制】在 Markdown 文件中，不同的内容元素实现空行的方式是在不同的内容元素之间添加 $2n+1$ 个空行（换行符）

    - 说明：在 Markdown 语法中，一个空行不会被渲染出空行

    - 反例：（渲染模式下，并不会渲染出空行，只有换行的效果）

   ```markdown
   line 1
   
   line 2
   ```

    - 正例：（"line 1" 作为段落元素，上面应该有 1 个换行符，不会被渲染成空行，"line 3" 的下面同理；"line 1" 与 "line 2" 之间有 3 个换行符，但只会渲染出 1 个空行；"line 2" 与 "line 3" 之间有 5 个换行符，但只会渲染出 2 个空行）

   ```markdown
   line 1
   ```



line 2





line 3

   ```
   - 反例：（首个内容元素 "### 标题 1" 标题元素的上面没有其他元素了，只需要一个换行符即可，末尾元素 "line2: content content content content content" 段落元素的下面没有其他元素了，只需要一个换行符即可；"line2: content content content content content" 与 "### 标题 2" 之间共有 3 个换行符，会被渲染出 1 个空行，这是为了文档内容排版而调整的）

   ```markdown



   ### 标题 1

   line1: content content content content content

   line2: content content content content content



   ### 标题 2

   line1: content content content content content

   line2: content content content content content



   ```

4. 【强制】不同的板块内容使用 3 个换行符分隔开

    - 说明：在 markdown 语法中，每行内容前后可以有一个空行，渲染的时候不会显示空行，因此在源码模式下，不同内容块的内容之间为 3 个空行时，可以在渲染的时候显示一个空行，将内容分格开

    - 正例：（源码模式下，是不同的板块间才有 3 个换行）

   ```markdown
   ### 标题 1
   
   line1: content content content content content
   
   line2: content content content content content
   ```



### 标题 2

line1: content content content content content

line2: content content content content content

   ```
5. 【推荐】不同的板块内容，用 "---" 分割线分割开来

   - 说明：当两个内容关联性不强时，可以用分割线将其隔开，内容块与标题之间不需要分隔线
   - 正例：（分割符与上下文的元素之间在渲染模式下应该用 1 个**空行**隔开）

   ```markdown

   ### Title 1

   content 1 , a lot of words



   ---



   content 2 , a lot of words



   content 3 , a few words



   ### Title 2

   ...

   ```

- 反例：（在内容块的字符很少时，不需要使用分割线，只需要换行即可；每行的满载字符数在 60 个字符，多余 60 个字符就会自动换行渲染到下一行）

   ```markdown
   content 1 , only a few words



   ---



   conetnt 2 , only a few words

   ```

6. 【推荐】尽可能将关联性不强的部分使用空行或者分割线分隔开，保持文档布局清晰

    - 说明：合理地使用空行以及分割线来控制内容排版有利于增强内容的可读性，但不是每段都需要空行以及分割线，适当使用，类似于语文中写作文时分段落一样，合理地段落数量有助于增强阅读效果，过度地分段只会适得其反



### 内容编写



1. 【推荐】当内容有歧义或不易理解等需要添加注释、备注、说明的其他情况下，使用 ">" 进行注释说明

    - 说明：当有些操作或行为可能引起问题时，可以进行注释说明。由于markdown 没有注释。

    - 正例：

   ```markdown
   ### title 1
   
   > 这个名词的意思是指...
   
   这是一段很难阅读的文本。
   ```



### title 2

这是一段很难的阅读文本。

> 可以理解为...。详细内容参考...

   ```
2. 【推荐】字母、数字、特殊符号等字符宽度只有 1 时与汉字连接的时候应该用一个空格隔开。中文标点不用加空格

   - 说明：视觉上更加舒适，工整。中文符号视觉上自带空格

   - 正例：

   ```markdown
   英语字母 alpha 数字 123 标点。beta. 标点符号 . 内联公式 $a + b = c$ 文本
   ```

3. 【推荐】在使用中文撰写文档的时候使用中文标点符号，写英文文档、源代码注释、数学公式等全部都应该用英文标点

    - 说明：写文档时，中文偏多，应该用中文符号，英文文档用英文符号（ASCII 字符），给源代码写注释时，都写英文符号

    - 正例：（写文档时）

   ```markdown
   正在写文档，这是一段文本内容。我真高兴！有什么问题吗？多个元素：元素 1 、元素 2 、元素 3 。内容一；内容二；内容三。他说：容”。
   ```

    - 正例：（写源代码注释时）

   ```python
   # 这是一段注释, 这是一段注释
   print("hello world") #
   ```

    - 正例：（写英文文档）

   ```markdown
   This is an article. What do you mean ? I don't know. What a day ! That's it.
   ```

    - 正例：（写数学公式）

   ```tex
   \text{若 } x>0,\; y<0,\; \text{则 } f(x,y)=x^2+y^2.
   ```



### 图片资源



1. 【强制】文档内插入图片时，图片链接只能使用在线链接，禁止使用相对路径

    - 说明：文档内插入图片必须使用稳定可访问的在线链接，严禁使用本地相对路径或绝对路径，避免文档迁移、跨平台分享时出现图片加载失效问题。

    - 正例：![image-20260117021324172](https://gitee.com/kualk/pic-go/raw/master/imgs/image-20260117021324172.png)

    - 反例：![系统整体架构图](images/system-architecture-full.png)

2. 【强制】markdown 文档中的图片资源大小超过 1MB 时必须压缩后再使用。

    - 说明：超过 1MB 的图片会拖慢文档加载速度，增加仓库体积。建议使用在线压缩工具（如 TinyPNG）处理后再上传。

3. 【参考】给 typora 或其他 markdown 编辑器通过 pic-go 配置 gitee 个人仓库的图床

    - 说明：配置图床后，当给文档编辑器粘贴图片时，会自动将该图片上传至个人的 gitee 仓库，作为稳定的图床链接

    - 参考教程：https://juejin.cn/post/7089308017266524197

4. 【强制】整理或编辑文档时，不得删除文档中的图片链接

    - 说明：文档中的图片链接是重要的视觉辅助说明材料，整理、编辑、合并或迁移文档内容时，必须保留原有的图片链接，不得遗漏或删除。若图片链接已失效，应标注而非直接删除。

    - 正例：整理文档内容时，将图片链接随上下文一起迁移到目标位置。

    - 反例：合并两篇文档时，只复制了文字内容而丢弃了 `![架构图](https://...)` 等图片引用。



### README 规范



README.md 的标准格式见 `templates/readme-template.md`。核心规则如下：



1. 【强制】每个目录必须包含 README.md，按模板结构撰写：职责边界 + 内容表。

    - 说明：README.md 作为目录的元数据文件，披露结构、说明作用、引导下级。模板定义最小必需结构，各 README 可按需追加额外章节。

2. 【强制】README.md 只描述本层内容，不展开子目录的内部文件。

    - 说明：每层 README 只管自己这一层，子目录内容交给子目录的 README 披露。形成逐层索引的链式结构，像链表的指针一样，该是下一个就是下一个，不越级引用导致孤儿节点。

3. 【强制】README.md 中罗列的内容清单应集中在 README.md 中，其他文档通过引用方式指向，不得重复说明。

    - 说明：避免同一信息在多处维护，减少不一致风险。各文档各司其职，明确职责边界，思路才清晰。
