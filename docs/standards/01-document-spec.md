## 文档撰写规范



### 文件与标题



1. 【强制】所有文档撰写均用 markdown 文件

    - 说明：统一文档格式标准，轻量高效，便于 AI 读取，便于管理。

2. 【强制】文档中应该有文档名字

    - 说明：每个文档中都应该给出文件的名字，而不是只有文档的内容

3. 【推荐】文档名设置为 2 级标题

    - 说明：一般情况下，文档标题设置为 2 级（##）。仅仓库根目录下的 README.md 文件的文档标题可以设置为 1 级，突出强调的作用。

4. 【强制】非项目根目录的 md 文档标题等级以 3 级标题开始

    - 说明：标题等级从 3 级标题开始，字体不会太大，也不会太小，便于迁移文档时升级标题等级，降级标题等级。

    - 正例：

   ```markdown
   ## doc-name
   ```



### Title 1



#### Subtitle



content



#### Subtitle



content



### Title 2



content

...

   ```


### 排版与间距



1. 【强制】标题元素的上下文应该用 1 个空行隔开

   - 说明：标题元素上下文使用 1 个空行隔开，使得内容排版更加清晰，防止标题大量堆叠

   - 正例：

   ```markdown

   ### Title 1


   content

   content


   ### Title 2


   ### Title 3

   ```

2. 【强制】禁用行末添加两个空格 + 回车表示换行

    - 说明：为了统一规范，以及优雅地编辑源码，禁止通过在行末使用两个空格加上回车（1 个换行符）的形式达到在渲染模式下的换行

    - 反例：

   ```markdown
   line1  
   line2
   
   ```

    - 正例：

   ```markdown
   line1
   
   line2
   
   ```

3. 【强制】在 Markdown 文件中，不同的内容元素实现空行的方式是在不同的内容元素之间添加 $2n+1$ 个空行（换行符）

    - 说明：在 Markdown 语法中，一个空行不会被渲染出空行

    - 反例：（渲染模式下，并不会渲染出空行，只有换行的效果）

   ```markdown
   line 1
   
   line 2
   ```

    - 正例：（"line 1" 作为段落元素，上面应该有 1 个换行符，不会被渲染成空行，"line 3" 的下面同理；"line 1" 与 "line 2" 之间有 3 个换行符，但只会渲染出 1 个空行；"line 2" 与 "line 3" 之间有 5 个换行符，但只会渲染出 2 个空行）

   ```markdown
   line 1
   ```



line 2





line 3

   ```
   - 反例：（首个内容元素 "### 标题 1" 标题元素的上面没有其他元素了，只需要一个换行符即可，末尾元素 "line2: content content content content content" 段落元素的下面没有其他元素了，只需要一个换行符即可；"line2: content content content content content" 与 "### 标题 2" 之间共有 3 个换行符，会被渲染出 1 个空行，这是为了文档内容排版而调整的）

   ```markdown



   ### 标题 1

   line1: content content content content content

   line2: content content content content content



   ### 标题 2

   line1: content content content content content

   line2: content content content content content



   ```

4. 【强制】不同的板块内容使用 3 个换行符分隔开

    - 说明：在 markdown 语法中，每行内容前后可以有一个空行，渲染的时候不会显示空行，因此在源码模式下，不同内容块的内容之间为 3 个空行时，可以在渲染的时候显示一个空行，将内容分格开

    - 正例：（源码模式下，是不同的板块间才有 3 个换行）

   ```markdown
   ### 标题 1
   
   line1: content content content content content
   
   line2: content content content content content
   ```



### 标题 2

line1: content content content content content

line2: content content content content content

   ```
5. 【推荐】不同的板块内容，用 "---" 分割线分割开来

   - 说明：当两个内容关联性不强时，可以用分割线将其隔开，内容块与标题之间不需要分隔线
   - 正例：（分割符与上下文的元素之间在渲染模式下应该用 1 个**空行**隔开）

   ```markdown

   ### Title 1

   content 1 , a lot of words



   ---



   content 2 , a lot of words



   content 3 , a few words



   ### Title 2

   ...

   ```

- 反例：（在内容块的字符很少时，不需要使用分割线，只需要换行即可；每行的满载字符数在 60 个字符，多余 60 个字符就会自动换行渲染到下一行）

   ```markdown
   content 1 , only a few words



   ---



   conetnt 2 , only a few words

   ```

6. 【推荐】尽可能将关联性不强的部分使用空行或者分割线分隔开，保持文档布局清晰

    - 说明：合理地使用空行以及分割线来控制内容排版有利于增强内容的可读性，但不是每段都需要空行以及分割线，适当使用，类似于语文中写作文时分段落一样，合理地段落数量有助于增强阅读效果，过度地分段只会适得其反



### 内容编写

1. 【强制】禁止为了缩短文档随意删除解释说明

    - 说明：解释说明是 Agent 判断歧义、边界和例外的重要依据。整理文档时只合并确定重复的内容，必须保留范围边界、例外条件、恢复条件、取舍原因和可能影响判断的上下文。无法确认是否仍有决策价值时，先保留并向用户确认。

2. 【强制】文档采用最低必要原则

    - 说明：不重复复制代码能够直接表达的实现细节，但最低必要不等于只保留结论。支撑判断所需的原因和解释属于必要内容。

3. 【强制】禁止使用括号补充辅助说明

    - 说明：需要保留的说明应写成完整正文，避免关键信息被误判为可忽略的附注。

4. 【推荐】标题保持简洁，内容不明确时暂不写入文档

    - 说明：不使用推测填充文档，不为了形式完整制造无法验证的内容。

5. 【推荐】同一目录下文档数量不超过五份时不强行编号，超过五份后再根据实际顺序统一编号

    - 说明：编号用于降低内容较多时的定位成本，不为少量文件增加无意义的维护负担。

6. 【推荐】`docs/project/` 下的目录和文档优先使用简洁、统一的中文名称

    - 说明：技术专有名词保留通用写法，同一目录内避免无理由混用中英文命名。

7. 【推荐】适合使用 Mermaid 表达的流程、状态和关系优先使用 Mermaid

    - 说明：当图形能够比连续文字更清楚地表达结构时使用图形，不为简单内容强行绘图。

#### 设计文档组织逻辑

1. 【强制】复杂设计文档采用“先总体、后分述”的组织方式

    - 说明：读者应先建立对整个设计主题的认识，再进入局部规则、流程和异常细节。不得一开始就连续堆积字段、公式、分支或实现步骤，迫使读者自行拼接整体设计。
    - 复杂设计文档是指一个主题下同时包含多个相互关联的考虑方面，例如职责、对象、流程、状态、策略、数据、异常和取舍。是否属于复杂文档由理解成本决定，不按固定篇幅机械判断。

2. 【强制】总体部分先说明设计主题需要考虑哪些方面

    - 总体部分至少说明当前文档解决什么问题、主要考虑方面、各方面之间的关系以及已经确认的核心边界。
    - 适合图形表达时，优先使用思维导图、架构概览图、关系图或汇总表建立整体认知。
    - 总体图只表达重要方面和关系，不在总览中塞入全部细节。

3. 【强制】分述部分与总体概览保持对应

    - 总体概览中的主要分支，应在后续找到对应的详细章节。
    - 后续新增一个重要方面时，必须同步更新总体概览，不能只在文档中部追加孤立章节。
    - 分述章节尽量按照总体概览的顺序展开，避免读者在章节之间反复跳转。

4. 【强制】总体概览图与详细流程图分开表达

    - 总体概览图回答“这个主题需要考虑什么”。
    - 详细流程图回答“各个步骤按什么顺序发生、如何衔接和分支”。
    - 不能只画一张从开始到结束的流程图，就认为已经说明了整个设计需要考虑的方面。

5. 【推荐】复杂设计文档优先采用以下阅读顺序

   ```text
   文档目标与当前边界
       ↓
   总体概览图
       ↓
   核心结论汇总
       ↓
   按概览分支逐项说明
       ↓
   详细流程、状态或数据关系
       ↓
   异常、非目标与关键取舍
   ```

    - 说明：该顺序用于保证从全局到局部的阅读逻辑，不要求所有文档机械套用完全相同的标题。应根据主题删减没有实际内容的部分。

6. 【推荐】详细章节先写结论，再解释处理方式

    - 每个章节先用明确语言说明当前决定，再补充原因、具体规则、例外和影响。
    - 仍未确认的内容必须标明待确认状态，不能与已经确定的设计混写。

7. 【推荐】短小且只回答一个问题的原子文档不强制绘制总体图

    - 说明：如果文档主题单一、关系简单，几段文字或一张表已经能够完整说明，就直接表达结论。不得为了满足形式要求制造没有信息价值的图和章节。

#### 微服务功能文档结构

1. 【强制】针对具体功能的文档必须在对应微服务目录下建立独立功能文件夹

    - 功能描述文档不得直接散落在微服务目录根部。
    - 服务级说明、公共规则、整体边界和跨功能决策可以直接存放在微服务目录。
    - 不得为不属于具体功能的文档强行创建功能文件夹。

2. 【强制】功能文件夹内的 `README.md` 只负责功能概述和文档导航

    - 功能概述应简要说明目标、范围以及与其他功能的关系。
    - 详细内容由同目录下的原子文档分别承载。

3. 【强制】一个原子文档只描述一个明确事项

    - 输入输出、执行流程、状态变化、业务规则、异常处理和方案取舍应按实际主题分别成文。
    - 禁止在一份文档中堆积整个功能的所有说明。
    - 禁止新增笼统的 `服务设计.md` 承载多个功能。

4. 【强制】微服务 README 必须维护完整功能清单和功能目录索引

    - 尚未详细设计的功能先列入功能清单。
    - 没有实际内容时不创建功能目录或空文档。
    - 进入设计后再创建功能目录，并逐篇补充原子文档。

5. 【推荐】原子文档使用能够直接表达问题的简短名称

    - 推荐使用 `输入输出.md`、`执行流程.md`、`业务规则.md`、`异常处理.md`、`状态变化.md` 和 `方案取舍.md`。
    - 是否拆分以主题是否单一为准，不以固定行数作为唯一判断依据。

6. 【强制】目录嵌套不超过三层

    - 功能文档推荐结构为 `微服务名/功能名/原子文档.md`。
    - 功能目录下不继续按章节建立多层子目录。



1. 【强制】`docs/project/` 下的设计文档默认保留功能概述、输入输出、大致流程、边界、规则和关键取舍

    - 说明：设计文档用于纠正、说明、补充和参考，不作为实现细节的副本。

2. 【强制】项目设计文档不无目的复制已经落地的数据表、接口字段、类方法、算法步骤和普通实现分支

    - 说明：数据库详细设计以 Flyway SQL 为准，接口契约以 Controller、DTO 和 VO 为准，功能实现以代码与测试为准。

3. 【强制】当前任务明确要求详细系统设计时，可以记录影响职责、状态、一致性、追踪或扩展边界的拟议表、字段、类型、约束、索引和关系

    - 说明：拟议数据结构必须标明设计状态并与当前实现区分。实现完成后仍以 Flyway SQL 和实际数据库结构为最终事实，设计文档同步修正差异。

4. 【强制】文档与当前实现冲突时，核对代码和运行行为后修正文档

    - 说明：不为了维持过时设计而曲解当前实现。


5. 【推荐】当内容有歧义或不易理解等需要添加注释、备注、说明的其他情况下，使用 ">" 进行注释说明

    - 说明：当有些操作或行为可能引起问题时，可以进行注释说明。由于markdown 没有注释。

    - 正例：

   ```markdown
   ### title 1
   
   > 这个名词的意思是指...
   
   这是一段很难阅读的文本。
   ```



### title 2

这是一段很难的阅读文本。

> 可以理解为...。详细内容参考...

   ```
5. 【推荐】字母、数字、特殊符号等字符宽度只有 1 时与汉字连接的时候应该用一个空格隔开。中文标点不用加空格

   - 说明：视觉上更加舒适，工整。中文符号视觉上自带空格

   - 正例：

   ```markdown
   英语字母 alpha 数字 123 标点。beta. 标点符号 . 内联公式 $a + b = c$ 文本
   ```

6. 【推荐】在使用中文撰写文档的时候使用中文标点符号，写英文文档、源代码注释、数学公式等全部都应该用英文标点

    - 说明：写文档时，中文偏多，应该用中文符号，英文文档用英文符号（ASCII 字符），给源代码写注释时，都写英文符号

    - 正例：（写文档时）

   ```markdown
   正在写文档，这是一段文本内容。我真高兴！有什么问题吗？多个元素：元素 1 、元素 2 、元素 3 。内容一；内容二；内容三。他说：容”。
   ```

    - 正例：（写源代码注释时）

   ```python
   # 这是一段注释, 这是一段注释
   print("hello world") #
   ```

    - 正例：（写英文文档）

   ```markdown
   This is an article. What do you mean ? I don't know. What a day ! That's it.
   ```

    - 正例：（写数学公式）

   ```tex
   \text{若 } x>0,\; y<0,\; \text{则 } f(x,y)=x^2+y^2.
   ```



### 图片资源



1. 【强制】文档内插入图片时，图片链接只能使用在线链接，禁止使用相对路径

    - 说明：文档内插入图片必须使用稳定可访问的在线链接，严禁使用本地相对路径或绝对路径，避免文档迁移、跨平台分享时出现图片加载失效问题。

    - 正例：![image-20260117021324172](https://gitee.com/kualk/pic-go/raw/master/imgs/image-20260117021324172.png)

    - 反例：![系统整体架构图](images/system-architecture-full.png)

2. 【强制】markdown 文档中的图片资源大小超过 1MB 时必须压缩后再使用。

    - 说明：超过 1MB 的图片会拖慢文档加载速度，增加仓库体积。建议使用在线压缩工具（如 TinyPNG）处理后再上传。

3. 【参考】给 typora 或其他 markdown 编辑器通过 pic-go 配置 gitee 个人仓库的图床

    - 说明：配置图床后，当给文档编辑器粘贴图片时，会自动将该图片上传至个人的 gitee 仓库，作为稳定的图床链接

    - 参考教程：https://juejin.cn/post/7089308017266524197

4. 【强制】整理或编辑文档时，不得删除文档中的图片链接

    - 说明：文档中的图片链接是重要的视觉辅助说明材料，整理、编辑、合并或迁移文档内容时，必须保留原有的图片链接，不得遗漏或删除。若图片链接已失效，应标注而非直接删除。

    - 正例：整理文档内容时，将图片链接随上下文一起迁移到目标位置。

    - 反例：合并两篇文档时，只复制了文字内容而丢弃了 `![架构图](https://...)` 等图片引用。



### README 规范

README.md 是当前目录的说明和导航入口，不使用固定模板。只有在内容明确且具有导航或约束价值时增量维护，不为了填满结构写入重复或无用内容。

1. 【强制】`docs/` 下具有实际内容的目录使用 README.md 建立逐层导航

    - 说明：README.md 说明当前目录的职责、范围、结构和直接子项。源代码目录不强制使用 README 索引机制。

2. 【强制】README.md 只描述本层内容，不展开子目录的内部文件

    - 说明：每层 README 只管自己这一层，子目录内容交给子目录的 README 披露。形成逐层索引的链式结构，像链表的指针一样，该是下一个就是下一个，不越级引用导致孤儿节点。

3. 【强制】README.md 中罗列的内容清单应集中在 README.md 中，其他文档通过引用方式指向，不得重复说明

    - 说明：避免同一信息在多处维护，减少不一致风险。各文档各司其职，明确职责边界，思路才清晰。

4. 【推荐】README.md 按实际需要维护以下内容

    - 当前目录的职责、范围和存放内容。
    - 当前目录下文件或子目录的索引和摘要。
    - 当前目录的结构、命名、归类和职责边界规则。
    - 与当前目录直接相关的关键解释和补充说明。
