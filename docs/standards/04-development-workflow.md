## 单目标开发流程



### 适用范围

- 日常功能开发
- 缺陷修复
- 重构优化
- 文档维护
- AI 协作开发



### 规则定义

> 【强制】：必须遵守的内容

1. 【强制】同一时间只能有一个唯一当前任务。
   说明：`TODO.md` 的唯一当前任务是进入代码开发的唯一依据，其余条目都是候选任务。

2. 【强制】开始开发前必须先形成一张任务卡。
   说明：任务卡必须包含目标、入口、主流程、完成标准、修改范围和非目标，并由用户明确确认。

3. 【强制】一个任务使用一个独立分支，不得直接在 `dev` 分支开发。
   说明：分支只承载当前任务卡，不混入其他功能、顺手重构或无关文档整理。

4. 【强制】当前任务完成验收并合并后，才能选择下一个任务。
   说明：禁止并行推进多个业务功能，禁止建立长期存在的总重构分支。

5. 【强制】开发实现必须严格遵守任务卡范围。
   说明：新发现的问题只有在阻断当前主流程时才能纳入当前分支，其余问题记录为候选任务。

6. 【强制】优先完成已有能力的端到端验收，不因局部实现不完善直接推倒重写。
   说明：代码重构必须服务于当前闭环，并且能够在当前分支独立验证。

7. 【强制】功能完成必须以真实业务结果为准。
   说明：构建成功、单元测试通过、接口存在或文档完成都不能单独证明从 0 到 1 完成。

8. 【强制】一个任务可以包含多个原子提交。
   说明：代码、配置和文档仍按 Git 规范分开提交，但所有提交必须共同服务同一张任务卡。


### 任务卡

开发前使用以下结构描述当前任务：

```markdown
目标：

入口：

主流程：

完成标准：

修改范围：

非目标：
```

目标必须描述用户或调用方最终能够获得的结果。主流程必须覆盖真实入口、关键状态变化和最终结果。完成标准必须能够实际执行和观察。


### 分支规则

- 功能开发使用 `feat/<模块>-<闭环>`。
- 缺陷修复使用 `fix/<模块>-<问题>`。
- 局部重构使用 `ref/<模块>-<目标>`。
- 文档维护使用 `docs/<目标>`。
- 分支名称必须表达单一任务，不使用 `refactor-all`、`project-rebuild` 等宽泛名称。
- 分支合并后再创建下一个业务分支。


### 完成定义

当前任务只有满足任务卡约定且至少完成以下检查后才能标记完成：

1. 最短业务流程从真实入口运行到最终结果。
2. 关键数据和状态变化符合预期。
3. 至少验证成功路径和一个关键异常路径。
4. 相关自动化测试通过。
5. 涉及的服务能够在真实运行方式下启动。
6. 没有依赖未实现的关键步骤才能使用。
7. 文档状态与当前代码和运行结果一致。



### 开发执行清单

1. 读取 `CONTEXT.md`、`TODO.md` 和本次任务相关规范。
2. 确认 `TODO.md` 中只有一个唯一当前任务。
3. 调查当前代码、契约和真实运行状态。
4. 编写任务卡并获得用户确认。
5. 从 `dev` 创建只服务当前任务的独立分支。
6. 按最短主流程逐步实现，每一步都保持可验证。
7. 将不阻断当前闭环的新问题记录为候选任务，不扩大当前范围。
8. 按完成定义进行自动化测试和真实运行验收。
9. 按代码、配置和文档类别完成原子提交。
10. 合并当前分支后更新唯一当前任务，再选择下一项工作。
