## 06-git-commit-workflow



### 适用范围

本文档定义 Git 提交的**工作流程**——即如何分组变更、判断 type、编写 subject。
提交消息的**格式语法**（type/scope/subject 规则）见 Git commit 描述规范。



### 变更文件分组规则

> 【强制】提交前必须按以下规则将变更文件分组，每组独立提交。

| 分组 | 识别规则 | scope |
|------|----------|-------|
| 后端代码 | `LeetModel-backend/` 下的 `.java`、`.xml` 源文件 | `back` 或具体模块名 |
| 前端代码 | `LeetModel-vue/src/` 下的 `.vue`、`.js`、`.css`、`.ts` | `front` |
| SQL | `sqls/` 目录下文件 | `sql` |
| 配置 | `pom.xml`、`application*.yml`、`package.json`、`vite.config.*`、`.env` 示例文件 | `config` |
| 文档 | `docs/`、`*.md` 文件 | 省略或模块名 |

新文件（untracked）与对应分组的已修改文件一起提交。



### type 判断依据

> 【推荐】根据变更的实际内容选择 type，不确定时优先选 `feat`（新增多）或 `ref`（改动多）。

| type | 判断依据 |
|------|---------|
| `feat` | 新增接口、页面、功能模块 |
| `fix` | 修复 bug、异常、兼容性问题 |
| `ref` | 重构代码结构、提取公共逻辑、优化实现（不改变功能） |
| `docs` | 文档、规范、说明文件 |
| `chore` | 依赖版本、构建脚本、环境配置 |
| `file` | 文件移动、重命名、删除 |



### subject 编写要求

> 【强制】subject 使用中文简述，一行概括这组变更的核心意图。

1. 聚焦一个变更点，不写流水账（"A 和 B 和 C" 说明拆分不够细）。
2. 控制在 20 字以内。

示例：

```text
feat(back): 用户批量更新接口与参数校验
fix(back): 修复登录 token 过期未刷新问题
ref(front): 提取公共表格组件，减少重复代码
docs: 补充 Controller 开发规范
chore(config): 升级 Spring Boot 至 3.2
```



### 强制规则

1. 【强制】前后端代码不得混在同一个提交中。
2. 【强制】文档、配置、代码三者独立提交，不同类型不混在一起。
3. 【强制】提交格式固定为 `type(scope): 中文subject`，type 和 scope 必须使用约定值。
4. 【强制】不要跳过钩子——不使用 `--no-verify`、`--no-gpg-sign` 等参数。如果钩子失败，修复问题后重新提交。
5. 【强制】不要提交敏感文件——`.env`、`credentials.*`、含密钥/密码的文件。



### 边界情况

| 场景 | 处理方式 |
|------|---------|
| 工作区无变更 | 无需提交 |
| 只有已暂存（staged）变更 | 同样分析分组，按规范提交 |
| 只有一种类型的变更 | 按规范格式单次提交即可 |
| 变更量大无法一笔概括 | 需要进一步拆分，先部分暂存 |
| 文件路径不在常规分组中 | 根据文件内容和性质判断归属 |
