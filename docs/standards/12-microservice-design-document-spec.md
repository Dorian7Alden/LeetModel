## 微服务设计文档规范

### 适用范围

本规范适用于 `docs/project/03-微服务设计/` 下的服务设计、功能设计和跨服务协作说明。

文档只描述当前实现和已确认的目标设计。设计目录可以先于 Maven 模块创建或更名，但实际模块名、接口和数据结构以当前代码为准。


### 服务归属

1. 【强制】先确定数据所有者。拥有数据库、业务事实和状态流转的服务，是对应能力的默认归属方。
2. 【强制】再确定业务规则所有者。功能应放在能独立校验规则、完成事务并解释结果语义的服务中。
3. 【强制】不按页面、使用者身份或 Controller 数量拆分微服务。普通用户和管理员可以调用同一领域服务的不同接口。
4. 【强制】纯聚合、路由和治理能力不拥有业务事实，不得将下游服务数据复制为新的事实源。
5. 【强制】当变更影响多个服务的调用关系、数据所有权或服务拆分时，同步更新 `docs/project/02-架构设计/` 中的对应架构文档。
6. 【推荐】从 0 到 1 阶段优先保证职责和数据边界清晰，不因预测的性能问题过早合并已经具有独立语义的服务。


### 目录结构

可独立部署的服务使用英文目录名，服务内的功能目录和功能文档优先使用中文名。

```text
service-name/
├── README.md
├── 服务级说明.md
└── 功能名/
    ├── README.md
    └── 原子文档.md
```

1. 【强制】微服务根目录只保存服务 README，以及不属于单一功能的公共说明、整体边界和跨功能决策文档。
2. 【强制】针对某个具体功能的文档必须放入对应功能目录，不得散落在微服务根目录。
3. 【强制】功能目录 README 只说明功能目标、范围、非目标和文档导航，不承载完整功能设计。
4. 【强制】尚未开始详细设计的功能只记录在服务 README 的功能清单中，不创建空功能目录或空文档。
5. 【强制】不再新增笼统的 `服务设计.md`。现有综合文档在对应功能重新设计时逐步拆分，确认有效内容已迁移后再删除旧文档。
6. 【推荐】不属于具体功能的文档不强行建立功能目录，但必须由服务 README 建立导航。


### 服务 README

每个微服务目录的 README 必须维护以下内容：

- 服务定位与核心业务目标。
- 服务在项目中的整体结构与宏观工作流程图。
- 服务负责的能力与规则。
- 服务明确不负责的事项。
- 服务拥有的数据、配置和业务事实。
- 上游、下游与跨服务调用边界。
- 当前服务完整的功能清单，包括尚未展开设计或实现的功能。
- 当前服务下的功能设计文档索引。

新增或调整功能时，必须先更新服务 README 的职责边界和功能清单，再更新或新增功能文档。

#### 整体结构与宏观工作流程图

1. 【强制】每个可独立部署微服务的 README 必须维护一张服务级整体结构与宏观工作流程图，让读者在进入详细设计文档前先理解该服务在项目中的位置和主要协作关系。
2. 【强制】图中根据当前服务的实际情况展示上游调用方、下游服务、外部依赖、数据与配置支撑，以及当前服务内部的核心功能模块。
3. 【强制】图中只表达核心模块和主要交互方向，不展开接口字段、算法步骤、表结构、完整异常分支和其他原子文档细节。
4. 【强制】当前实现与目标设计必须在节点标签、连线样式或图后说明中明确区分，不能把尚未实现的服务和流程画成当前事实。
5. 【强制】服务 README 的整体图发生职责、依赖或主要流程变化时必须同步更新，不能只修改下层原子文档。
6. 【推荐】优先使用 Mermaid 维护可随代码评审的图。图后使用简短文字说明主流程、关键边界和容易误解的节点，不重复详细设计文档。
7. 【推荐】公共 Jar、SDK 和工具模块不强制套用微服务整体图；如果它们是服务调用链中的关键边界，应在相关微服务图中明确标识其不是独立服务。


### 原子文档

1. 【强制】一篇原子文档只回答一个明确问题。出现多个并列主题时继续拆分，不使用固定行数机械判断。
2. 【强制】功能的输入输出、执行流程、业务规则、状态、异常和取舍分别写入短小的原子文档。
3. 【强制】一份功能设计只维护在一个归属位置，不在多个服务目录复制。
4. 【强制】微服务设计文档默认只保留功能级流程、边界、规则和取舍，不复制已经落地的普通实现细节。表结构、完整接口字段和代码执行细节以实体、DTO、接口定义、Flyway 脚本和当前代码为准。
5. 【强制】当当前任务明确要求先完成详细系统设计时，可以为影响数据所有权、状态流转、一致性、追踪或扩展边界的数据结构建立原子文档，定义拟议表、字段、类型、约束、索引和关系。文档必须标记设计状态，并明确区分当前实现与目标设计；实现完成后以 Flyway SQL 和实际数据库结构为最终事实，同步处理设计差异。
6. 【推荐】一组相关功能需要共享输入、输出或版本约束时，先建立功能概述，再为具体功能或版本建立原子文档。
7. 【强制】内容复杂的微服务设计文档内部按照 [01-document-spec.md](01-document-spec.md) 的“设计文档组织逻辑”先建立总体概览，再按概览分支逐项说明。总体概览图和详细流程图承担不同职责，不能互相替代。


### 文档归类

- 单一微服务内的功能设计放入对应服务的功能目录。
- 跨多个微服务的完整调用链、全局状态流转和服务拆分决策放入 `docs/project/02-架构设计/`。
- 不可独立运行的公共 Jar 设计放入 `docs/project/03-微服务设计/common/` 下对应的 Maven 模块目录。
- 服务 README 负责服务概述、职责边界、数据归属、跨服务边界、功能清单和文档导航。
- 强制规则、项目级工作流程和文档格式不放入微服务设计目录，分别由 `docs/standards/` 中的对应规范维护。


### 跨服务协作

1. 【强制】跨服务只通过明确的 API、Feign 契约或业务事件协作，不直接访问其他服务数据库。
2. 【强制】接口提供方负责校验自己拥有的业务规则，调用方不复制该规则。
3. 【强制】调用方只保存必要的关联标识和业务快照，不将其他服务的数据镜像为本地主数据。
4. 【强制】聚合查询发生局部失败时必须显式标记数据不可用，不使用零值或空集合伪装真实结果。


### 维护流程

1. 阅读目标服务 README，确认数据所有者、规则所有者和跨服务边界。
2. 先更新服务 README 的职责边界和完整功能清单。
3. 确认功能已进入详细设计后，创建或更新对应功能目录。
4. 在功能 README 中说明目标、范围、非目标和文档导航。
5. 将流程、规则、状态、异常和取舍按明确问题拆分为原子文档。
6. 如果影响跨服务边界，同步更新架构设计。
7. 核对当前代码、配置、数据库迁移和服务间契约，不将旧文档当作当前事实。
8. 确认旧综合文档的有效内容已迁移后，再删除旧文档并更新全部索引。


### 检查清单

- [ ] 服务 README 包含定位、负责事项、不负责事项、数据归属、跨服务边界、完整功能清单和文档导航。
- [ ] 服务 README 包含整体结构与宏观工作流程图，能够看出上下游、核心模块、数据配置和外部依赖。
- [ ] 整体图保持宏观，没有复制原子文档细节，并且区分当前实现与目标设计。
- [ ] 具体功能文档位于对应功能目录，没有散落在服务根目录。
- [ ] 尚未设计的功能没有创建空目录或空文档。
- [ ] 功能 README 只维护目标、范围、非目标和导航。
- [ ] 每篇原子文档只回答一个明确问题。
- [ ] 文档不无目的复制已经落地的完整表结构、接口字段或代码执行细节；详细设计任务中的拟议数据结构已标明设计状态，并与当前实现明确区分。
- [ ] 复杂设计文档先给出总体概览，后续章节与概览分支对应，并另行说明详细流程。
- [ ] 跨服务数据和规则不被复制为本地主数据。
- [ ] 影响多个服务的变更已同步架构设计。
- [ ] 文档索引与当前目录结构一致。
