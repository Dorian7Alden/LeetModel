## Git commit 描述规范



### Git commit 描述规范



> 【强制】：必须遵守的内容
>
> 【推荐】：最好遵守的内容，特殊条件下可以自行调整



1. 【强制】Git commit 描述统一采用 `type(scope): 中文描述` 格式。
   说明：固定提交结构，便于检索、回滚和版本追踪。

2. 【强制】type 必须使用以下约定值之一。

   | 类型 | 含义 | 适用场景 |
   | --- | --- | --- |
   | feat | 新增功能 | 新增模块、接口、页面、交互能力 |
   | ref | 重构优化 | 提取公共逻辑、调整代码结构、优化实现 |
   | docs | 文档更新 | 补充或修正文档、说明、规范 |
   | fix | 缺陷修复 | 修复 bug、异常、兼容性问题 |
   | file | 文件变更 | 文件移动、重命名、删除、整理 |
   | release | 发布版本 | 版本发布、里程碑标记 |

3. 【强制】scope 用于标识相关领域或模块，建议使用简短词汇，如 `front`、`back`、`user`、`admin`、`problem`、`tag`。
   说明：scope 不宜过长，优先使用能快速识别范围的短模块词。如果目录名或文件名本身具有可识别性，也可以直接作为 scope 使用。

4. 【推荐】功能新增、缺陷修复、重构类提交尽量带 scope；文档、文件调整、发布类提交在没有明确模块时可以省略 scope。
   说明：功能类提交带上 scope 后，更容易定位影响范围。

5. 【推荐】subject 使用中文简述，聚焦一个变更意图，不要写成流水账，也不要在一条 commit 中混合多个任务。
   说明：保持提交信息可读、可扫读、可追踪。

6. 【强制】不同类型的内容必须分开提交，不可混在一次提交中。
   - **代码、文档、配置** 三者各自独立提交
   - 代码提交须进一步拆分**前端**与**后端**，一次提交只包含前端或后端代码
   - 说明：拆细提交粒度，便于 review、回滚和定位问题。

7. 【推荐】release 类型建议写成 `release(version): 发布 vX.Y.Z`，例如 `release(version): 发布 v0.1.0`。
   说明：发布提交需要直观体现版本号，便于检索发布记录。



### 示例



正例：

```text
feat(front): 新增首页轮播图展示
ref(back): 重构题目查询服务
docs(user): 补充登录接口说明
fix(problem): 修复题目详情空指针问题
file(config): 移动配置文件到新目录
release(version): 发布 v0.1.0
```



反例：

```text
feat: add feature
fix(user): 修复
docs(front-back-user-admin-problem): 补充说明
release: 发布版本
```
