

# LeetModel AI评审机制 — 系统设计思路

---

## 一、先厘清核心设计难题

在动手之前，必须直面数学建模评审与传统OJ（如LeetCode）的**本质差异**：

| 维度 | LeetCode（代码OJ） | LeetModel（建模实训） |
|------|--------------------|-----------------------|
| 答案性质 | 确定性，有标准输出 | **开放性，答案不唯一** |
| 评判方式 | 测试用例通过率 | **多维度主观+客观混合** |
| 输出物 | 代码 | 建模方案/代码/论文（异构） |
| 评审粒度 | 对/错二元 | **分档评级+细粒度诊断** |

> **这意味着：不能照搬OJ的"跑测试用例"模式，必须设计一套"结构化Rubric + LLM语义理解 + 规则引擎"的混合评审架构。**

## 三、出题侧必须前置设计的东西（评审的根基）

> **核心原则：评审质量的上限，由出题时的评审标准设计决定，而非由AI能力决定。**

每道训练题在出题时，必须同步产出以下**评审配套物料**：

### 3.1 结构化评分量规（Rubric）

```yaml
题目ID: MCM2024-Q1
角色: 建模手
评审维度:
  - 维度: 问题理解与分析
    权重: 20%
    评分档位:
      优秀(9-10): "准确识别核心矛盾，清晰定义了需要解决的子问题"
      良好(7-8): "识别了主要问题，但子问题拆解不够清晰"
      及格(5-6): "对问题有基本理解，但遗漏关键约束条件"
      不及格(0-4): "问题理解有重大偏差"
    关键检查点:
      - "是否识别出了 XXX 这个核心约束"
      - "是否区分了 YYY 和 ZZZ 两个子问题"
      
  - 维度: 假设合理性
    权重: 15%
    ...
    
  - 维度: 模型选择与构建
    权重: 30%
    可接受模型空间:
      - 标准解法: "多目标规划模型"
      - 可接受替代: ["层次分析法+线性规划", "灰色关联+整数规划"]
      - 创新加分: "引入不确定性量化的随机规划方法"
    ...
```

### 3.2 标准解法 + 解空间定义

```
标准解法（参考答案）: 完整的建模/代码/论文样本
可接受解空间: 列举可替代的模型/算法/论述路径
关键得分点（Key Points）: 必须命中的核心要素清单
常见误区（Anti-patterns）: 典型错误模式及对应扣分规则
数值参考范围: 合理结果的数值区间（用于编程手评审）
```

### 3.3 为什么这一步至关重要

- LLM 做开放性评审时，如果没有Rubric锚定，评分会**漂移和不一致**
- Rubric 将主观评价转化为**结构化的维度对标**，LLM 只需做"学生作答 vs Rubric描述"的匹配判断
- 这也是确保**评审可解释性**的基础

## 四、三种角色的评审方案详细设计

### 4.1 建模手评审

#### 提交物
建模方案文档（问题分析、假设、模型构建过程、模型求解思路）

#### 评审维度

```
┌────────────────────────────────────────────────┐
│              建模手评审维度 (6维)                │
├──────────────────┬─────────┬───────────────────┤
│ 维度              │ 权重    │ 评审方式           │
├──────────────────┼─────────┼───────────────────┤
│ ① 问题理解与分析  │ 15%     │ LLM语义评审       │
│ ② 假设合理性      │ 15%     │ LLM + 关键点匹配  │
│ ③ 模型选择恰当性  │ 25%     │ LLM + 解空间匹配  │
│ ④ 模型构建完备性  │ 20%     │ LLM + 结构检查    │
│ ⑤ 求解思路可行性  │ 15%     │ LLM语义评审       │
│ ⑥ 创新性          │ 10%     │ LLM评审(加分项)   │
└──────────────────┴─────────┴───────────────────┘
```

#### 评审Prompt设计策略（核心）

```markdown
## System Prompt 框架

你是一位数学建模竞赛资深评委。请根据以下评分量规（Rubric），
对学生提交的建模方案进行评审。

### 评审规则：
1. 严格依据Rubric中每个维度的档位描述进行对标打分
2. 每个维度必须给出：分数 + 档位 + 具体依据（引用学生原文）
3. 对照【关键得分点清单】逐一标注是否命中
4. 对照【常见误区清单】检查是否存在典型错误
5. 模型选择评审时，对照【可接受模型空间】判断，
   不在列表中的模型不直接判错，而是评估其合理性

### Rubric：
{动态注入该题的评分量规}

### 参考解法：
{动态注入标准解法摘要}

### 学生提交：
{学生建模方案}

### 输出格式（JSON）：
{结构化输出schema}
```

#### 关键技术决策

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 是否用多次调用取均值 | ✅ **3次调用取中位数** | 降低LLM单次评审的随机性 |
| 是否分维度独立评审 | ✅ **每个维度独立Prompt** | 避免长上下文中的注意力稀释 |
| 如何处理模型创新性 | 标准解法外的模型，交LLM评估合理性 | 不能因为"不在标准答案里"就判错 |

### 4.2 编程手评审

#### 提交物
代码文件 + 运行结果（图表/数据/输出）

#### 评审维度

```
┌────────────────────────────────────────────────────┐
│              编程手评审维度 (6维)                    │
├──────────────────┬─────────┬───────────────────────┤
│ 维度              │ 权重    │ 评审方式              │
├──────────────────┼─────────┼───────────────────────┤
│ ① 代码正确性      │ 30%     │ 沙箱执行+结果校验     │
│ ② 结果准确性      │ 20%     │ 数值范围校验+趋势校验 │
│ ③ 算法实现合理性  │ 15%     │ LLM代码审查          │
│ ④ 代码质量        │ 15%     │ 静态分析+LLM评审     │
│ ⑤ 可视化质量      │ 10%     │ LLM多模态评审        │
│ ⑥ 数据处理规范性  │ 10%     │ 规则引擎+LLM        │
└──────────────────┴─────────┴───────────────────────┘
```

#### 编程手评审的独特之处（相对最像传统OJ）

```
评审流水线:

提交代码
  │
  ├──▶ [静态分析] 
  │     · 语法检查
  │     · 代码规范(PEP8/变量命名)
  │     · 依赖库白名单检查
  │     · 代码复杂度度量
  │
  ├──▶ [沙箱执行]
  │     · 安全沙箱环境运行
  │     · 捕获输出结果(数值/文件/图片)
  │     · 资源消耗记录(时间/内存)
  │     · 异常/报错捕获
  │
  ├──▶ [结果校验]
  │     · 数值结果 vs 参考范围区间
  │     · 输出图表 vs 预期趋势/模式
  │     · 关键中间变量检查点
  │
  └──▶ [LLM代码评审]
        · 算法选择是否匹配建模需求
        · 代码逻辑是否正确实现了模型
        · 数据预处理是否合理
        · 可视化是否清晰表达了结果
```

#### 结果校验的设计（关键难点）

数学建模不像算法题有精确答案，需要设计**弹性校验**：

```python
# 结果校验策略示例
validation_rules = {
    "数值结果": {
        "method": "range_check",       # 范围检查，而非精确匹配
        "reference": 42.5,
        "tolerance": "15%",            # 允许15%偏差
        "trend_check": True            # 检查变化趋势是否一致
    },
    "优化结果": {
        "method": "optimality_check",  # 检查是否达到合理的优化水平
        "baseline": 100,               # 基准解的目标函数值
        "acceptable_ratio": 0.85       # 达到基准解85%即可接受
    },
    "分类结果": {
        "method": "metric_check",
        "metrics": ["accuracy", "f1"],
        "thresholds": {"accuracy": 0.75, "f1": 0.70}
    }
}
```

```

## 五、需要重点考虑的设计问题

### 5.1 评审一致性问题（最核心的挑战）

**问题**：同一份作答，LLM两次评审可能给出不同分数。

```
┌─────────────────────────────────────────────────────┐
│                 一致性保障机制                        │
├─────────────────────────────────────────────────────┤
│                                                      │
│  策略1: Multi-Call Aggregation（多次调用聚合）         │
│  · 同一维度调用3次，取中位数                           │
│  · 若3次评分方差 > 阈值，触发第4次评审或人工介入        │
│                                                      │
│  策略2: Rubric Anchoring（量规锚定）                  │
│  · 强制LLM先判断档位(优秀/良好/及格/不及格)           │
│  · 再在档位内精确打分                                 │
│  · 大幅减少分数漂移                                   │
│                                                      │
│  策略3: Few-shot Calibration（少样本校准）             │
│  · 在Prompt中嵌入2-3个已评审样本作为锚点               │
│  · "以下是一个7分的示例: ..."                         │
│  · "以下是一个4分的示例: ..."                         │
│                                                      │
│  策略4: 定期一致性检验                                │
│  · 用同一批标准样本定期测试评审系统                     │
│  · 监控评分分布的漂移                                 │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 5.2 评审公平性 — 开放性题目的"多解性"处理

```
核心原则: 不能因为学生的解法不在标准答案中就判低分

处理策略:
  ┌─────────────────────────┐
  │ 学生使用了非标准模型     │
  └────────────┬────────────┘
               │
    ┌──────────▼──────────┐
    │ 是否在"可接受模型    │──── 是 ──▶ 正常评分
    │ 空间"列表中？        │
    └──────────┬──────────┘
               │ 否
    ┌──────────▼──────────┐
    │ LLM评估该模型的      │
    │ · 理论合理性          │──── 合理 ──▶ 正常评分
    │ · 与问题的匹配度      │            (可标记待人工复核)
    │ · 是否能得出有效结论  │
    └──────────┬──────────┘
               │ 不合理
    ┌──────────▼──────────┐
    │ 给出低分 + 详细解释   │
    │ 说明为何该模型不适用  │
    └─────────────────────┘
```

### 5.3 评审可解释性（用户信任的关键）

**用户凭什么相信AI的评分？** 必须做到评审结果可追溯。

```
每个评分维度的输出结构:

{
  "dimension": "模型选择恰当性",
  "score": 8,
  "level": "良好",
  "evidence": "学生选用了TOPSIS模型对方案进行评价，该模型适用于多属性决策问题，与题目要求匹配。",
  "strengths": [
    "正确识别了这是一个多准则决策问题",
    "TOPSIS模型选择合理"
  ],
  "weaknesses": [
    "未考虑指标权重的客观确定方法，仅使用了主观赋权",
    "缺少对模型灵敏度的讨论"
  ],
  "suggestion": "建议结合熵权法进行客观赋权，并与主观权重做对比分析",
  "reference_comparison": "标准解法使用了AHP+熵权法组合赋权，在权重确定上更为严谨"
}
```

### 5.5 评审性能与成本控制

```
成本优化策略:

  轻量检查(规则引擎, ≈0成本)        ──▶ 先跑
     │ 通过基础检查
     ▼
  中等评审(小模型/单次LLM调用)       ──▶ 快速出分
     │ 用户请求详细报告 / 分数争议
     ▼  
  深度评审(大模型/多次调用/分维度)    ──▶ 精细诊断

  * 日常练习: 中等评审即可
  * 模拟赛/重要考核: 自动触发深度评审
  * 用户申诉: 升级为深度评审 + 人工复核队列
```

    · 参考: 优秀案例学习
```

### 6.3 分数体系设计

```
单题评分:
  · 各维度加权 → 百分制原始分
  · 原始分 → 五档评级: S / A / B / C / D

角色能力分(长期):
  · 类似ELO Rating, 根据题目难度+得分动态调整
  · 建模手Rating / 编程手Rating / 论文手Rating 独立计算

综合建模能力分(可选):
  · 三个角色Rating的加权综合
```

## 九、一句话总结设计哲学

> **出题定标准（Rubric），规则筛确定性，LLM判开放性，多次保一致性，结果可解释。**

整套系统的核心不是"让AI打分"，而是**将数学建模这种高度开放性的评审任务，通过Rubric工程和混合评审架构，转化为AI可稳定、可解释执行的结构化评估任务**。
