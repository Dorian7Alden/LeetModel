### AI 总结过程

> 最终的有效解决方式就是，flush 一下数据库即可



#### 一、问题背景
我在JavaWeb开发测试Redis数据库时，发现严重的内存异常问题：
- 业务层面仅写入了**7条小数据**（6个Token黑名单key、1个测试Hash key），无大批量数据写入
- 系统层面Redis进程内存占用高达**1.17G**，占服务器总内存（1.72G）的68.4%，内存占用完全不符合业务数据规模
- 核心诉求：定位内存异常根因，解决问题，沉淀可复用的Redis问题排查方法论，用于后端面试场景

#### 二、核心排查思路
遵循「**从外到内、从现象到本质、先排除低级错误再深入底层**」的通用问题排查逻辑，固定排查路径：
1.  系统层面锁定异常进程，确认内存占用的真实性
2.  进入Redis内部，通过核心指标定位内存去向
3.  逐一排除高频异常场景（大key、缓冲区、持久化、多实例等）
4.  兜底验证锁定根因，完成修复与长期优化

#### 三、分步排查过程（真实操作+分析结论）
##### 步骤1：系统层面锁定异常主体，确认内存异常真实性
**操作动作**：
1.  执行 `free -h` 查看服务器整体内存占用，确认总内存1.72G，已用1.5G，剩余仅80M
2.  执行 `ps -eo pid,ppid,cmd,%mem --sort=-%mem | head` 按内存占用排序进程，定位到`redis-server`进程内存占比68.4%，是内存异常的核心主体

**现象反馈**：Redis进程是内存占用的唯一异常项，排除其他业务进程、系统进程的影响。
**分析结论**：问题锁定在Redis服务本身，而非服务器系统或其他应用。

---

##### 步骤2：进入Redis内部，获取核心内存指标，初步缩小排查范围
**操作动作**：
1.  登录Redis命令行，执行 `INFO memory` 获取Redis内存核心统计数据
2.  执行 `MEMORY USAGE` 查看单个key内存占用，报错 `ERR unknown command 'MEMORY'`

**现象反馈**：
| 核心指标 | 数值 | 关键信息 |
|----------|------|----------|
| used_memory_human | 1.17G | Redis引擎自身分配的总内存 |
| used_memory_rss_human | 1.17G | 操作系统视角的进程物理内存占用 |
| mem_fragmentation_ratio | 1.00 | 内存碎片率正常 |
| maxmemory | 0B | 未设置Redis最大内存上限 |
| maxmemory_policy | noeviction | 内存满后不淘汰数据，直接拒绝写入 |
| mem_allocator | jemalloc-3.6.0 | Redis版本为3.x（极老版本，4.0+才支持MEMORY命令） |

**分析结论**：
1.  碎片率1.00，**完全排除内存碎片导致的异常**；used_memory与rss完全一致，说明内存是Redis引擎内部合法分配，而非操作系统层面的内存泄漏。
2.  未设置maxmemory，Redis无内存上限，存在内存溢出的核心风险。
3.  Redis版本过老，缺少内存诊断的核心命令，调整排查思路，改用兼容老版本的诊断方式。

---

##### 步骤3：验证业务数据量，排除“数据远超预期”的误判
**操作动作**：
1.  执行 `dbsize` 查看当前库key总数，返回结果为7，和业务预期一致
2.  执行 `INFO keyspace` 查看全库数据，确认仅db0有数据，其他数据库无隐藏数据
3.  执行 `SCAN 0 COUNT 10` 全量遍历key，确认所有key为6个Token黑名单key、1个`test:hset`测试key
4.  执行 `TYPE 对应key名称` 确认key类型，Token黑名单均为string类型，测试key为hash类型

**现象反馈**：表面key数量极少，无大批量key，排除key数量过多导致的内存占用。
**分析结论**：问题不在key的数量，而在**单个key的内部数据量**，或Redis非业务数据的内存开销。

---

##### 步骤4：排除高频异常场景，进一步缩小排查范围
###### 子步骤4.1 排除客户端缓冲区堆积问题
**操作动作**：
1.  执行 `INFO clients` 查看客户端连接，仅1个活跃连接，无阻塞客户端
2.  执行 `CLIENT LIST` 查看连接详情，所有连接的`omem`（输出缓冲区内存）均为0

**分析结论**：完全排除客户端输入/输出缓冲区堆积导致的内存暴涨。

###### 子步骤4.2 排除持久化相关内存占用
**操作动作**：执行 `INFO persistence` 查看持久化状态
**现象反馈**：`aof_enabled:0`（未开启AOF持久化），`rdb_bgsave_in_progress:0`（无正在执行的RDB快照），无持久化缓冲区占用。
**分析结论**：排除持久化操作、重写缓冲区导致的内存占用。

---

##### 步骤5：重启验证，区分临时/永久内存问题
**操作动作**：执行 `systemctl restart redis` 重启Redis服务，重启后重新执行 `INFO memory`
**现象反馈**：重启后内存占用依然为1.17G，无任何下降。
**分析结论**：排除临时内存泄漏、临时缓冲区堆积的问题，Redis启动时就加载了1.17G的数据，问题根源在**持久化文件**或**内存中的业务数据**。

---

##### 步骤6：验证持久化文件，发现核心矛盾点
**操作动作**：
1.  执行 `CONFIG GET dir` + `CONFIG GET dbfilename` 找到RDB持久化文件路径：`/var/lib/redis/dump.rdb`
2.  退出Redis命令行，在Linux终端执行 `ls -lh /var/lib/redis/dump.rdb` 查看文件大小

**现象反馈**：RDB文件仅**14M**，和内存中1.17G的占用存在近100倍的差距，完全不符合RDB文件加载到内存的正常膨胀比例。
**分析结论**：
1.  RDB文件是旧的快照，内存中1.17G的新数据未触发RDB持久化规则，没有落盘到文件中；
2.  需排除「启动了多个Redis实例，重启错了服务」的低级错误。

---

##### 步骤7：排除多实例低级错误，确认服务唯一性
**操作动作**：
1.  执行 `ps -ef | grep redis-server` 查看所有Redis进程，仅1个PID为3191的进程
2.  执行 `systemctl status redis -l` 查看systemd管理的Redis主进程PID，和上述PID完全一致

**分析结论**：完全排除多实例、重启错服务的低级错误，问题锁定在Redis内存中的数据本身。

---

##### 步骤8：兜底验证，100%锁定根因
**操作动作**：
1.  先备份RDB文件：`cp /var/lib/redis/dump.rdb /var/lib/redis/dump.rdb.backup`
2.  登录Redis执行 `FLUSHALL` 清空全库所有数据
3.  立即执行 `INFO memory` 查看内存占用

**现象反馈**：清空数据后，`used_memory_human` 从1.17G瞬间降至**793.70K**，内存完全释放。
**最终根因实锤**：
Redis内存中存在**大量未持久化到RDB文件的业务数据**，虽然表面仅7个key，但其中存在大key（大概率是测试用的`test:hset`写入了海量字段/超大value），或大量过期未被惰性删除的key；RDB文件是旧的快照，新写入的1G+数据未触发持久化规则，导致文件大小和内存占用严重不符。

#### 四、最终解决方案
##### 1. 临时修复（快速恢复正常）
1.  清空脏数据后，通过备份的RDB文件恢复正常的业务测试数据
2.  重启Redis服务，确认内存占用恢复到正常的几十KB级别，符合业务数据规模

##### 2. 永久优化（防止问题复现，符合生产规范）
1.  **增加Redis内存上限**：
    执行 `CONFIG SET maxmemory 256mb` + `CONFIG SET maxmemory-policy allkeys-lru` + `CONFIG REWRITE`，给Redis设置内存上限和淘汰策略，避免内存无限制上涨。
2.  **优化Key设计**：
    放弃「完整JWT Token作为Key名」的设计，改用JWT的SHA256哈希值作为Key，将Key长度从300+字符压缩至固定64字符，降低90%以上的Key内存开销。
3.  **规范持久化策略**：
    调整RDB快照触发规则，避免数据长期不落盘，导致内存与持久化文件数据严重不一致。
4.  **升级Redis版本**：
    从3.x老版本升级至6.2+稳定版，修复老版本内存管理缺陷，支持`MEMORY`诊断命令、自动内存碎片整理等核心特性。

#### 五、面试加分项：排查方法论与踩坑总结
##### 1. Redis内存异常排查的固定通用流程（面试可直接复用）
`系统top/ps锁定异常进程` → `Redis INFO memory分析内存分布` → `确认数据量与大key` → `排除客户端/缓冲区/持久化问题` → `重启验证临时/永久问题` → `兜底清空数据锁定根因`

##### 2. 核心踩坑点与避坑经验
1.  绝对不要给Redis设置`maxmemory=0`，相当于没有刹车，极易占满服务器内存触发OOM，生产环境必须设置内存上限和合理的淘汰策略。
2.  不要忽略单个大key的影响：一个Hash/Set内写入百万级字段，哪怕只有1个key，也能占满整个服务器内存，排查时不能只看key数量。
3.  Redis的Key本身会占用内存，绝对不要用超长字符串（如完整JWT、URL）作为Key名，优先用哈希值缩短Key长度。
4.  RDB持久化是触发式的，内存中的数据和RDB文件内容不一定一致，不能用RDB文件大小判断Redis内存中的数据量。
5.  老版本Redis（3.x及以下）存在内存管理缺陷，缺少核心诊断能力，测试/生产环境优先使用6.x+稳定版。

##### 3. 问题排查的核心思维
面试中重点体现：排查问题不是盲目试命令，而是**每一步操作都有明确的目的，每一个结论都有数据支撑，通过排除法逐步缩小范围，最终用兜底操作实锤根因**，而非靠猜测解决问题。
