### 临时待整理的内容




如何理解日志系统。日志系统主要是在干嘛？

评审要根据不同的赛事要求来进行评审。美赛、国赛。并在题目中明确说明是什么赛事的评审要求，给用户看的评审要求，以及给AI看的评审要求不一样。

我有一个缺点，有一个错觉：希望把一个东西整理之后，对其进行标注，防止下次重复整理，对原始内容留一个存档，而且原始内容可能更改，所以得知道哪些没有被整理过，这十分麻烦，导致我迟迟不开始整理内容，生怕内容更新了。直接不允许更改原始内容，只能增量文档这种原则？搞一个版本号，增量管理，不动原始内容，这样还更加有成就感，更多的文档。（git管理版本不好用，这里的不好用体现在对于内容版本的不直观，不能快速的对比多个版本，倒不如直接把每个版本罗列出来，最原始的版本管理。git管理代码好，但是管理文档就这样原始的列版本号更便于文档的快速调整，文档的变更太多了，有些参考内容就是得追溯历史版本，用git来做历史版本反倒不直观了。每次发布都令起一个版本，可以在文档命名上添加一个特殊标记，比如：完全舍弃，这样快速的节省文档的阅读成本，有些内容被完全丢弃了，但是可以体现出写文档的探索过程，试错，有些文档过期了，但是也有一些存在的参考价值）

搭建项目时，遇到 nacos 版本不对的问题。 SpringCloudAlibaba 中指定的是 2.3.2 的版本，但是我从官网下载的是最新版3.2.1，导致启动 nacos-discover 报错了


临时想到一个点：前期先不做缓存设计，只需要保证功能正确能跑进行，然后后面再来考虑缓存优化，加快网络请求响应等。哪些是否为热点数据、热点操作，可以通过操作日志来进行分析，哪些接口经常调用，哪些数据经常被访问，然后对这些数据进行缓存才最有性价比。不过目前肯定是不可能有真实的操作日志数据的，就简单模拟一下热点数据就行了。

使用 agent 工具心得记录：使用 agent 完成开发的时候，还是个人的开发经验、使用经验比较有优势。有经验的人，可以在上下文缺乏的场景下，给出好的方向，做出更好的判断，有更好的建议，可以对 ai 进行调整，有自己的想法，批判性的使用。使用 agent 工具，是极其困难让 大模型 完全理解你的个人想法的，也基本不现实，上下文是永远也不可能完整的，ai 信息输入处理的密度跟频率跟人类完全不一样，人类处理信息来源太多了，时时刻刻都在输入跟思考，ai 只能知道我们明确说明的内容。综上，使用 agent 工具的时候，至少目前这个阶段，专业人士一定是更有优势，占主导地位的，做出一个好的产品或者设计。
